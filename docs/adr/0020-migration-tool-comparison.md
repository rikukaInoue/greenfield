# 0020. マイグレーションツール比較: golang-migrate と goose（草案）

ステータス: **草案**。6.2（#60）の実測に基づく比較所感であり、乗り換えの決定はしていない。
アップストリーム先（プロダクション）がツールを選ぶ際の判断材料として書く。

## 背景

internal-05 の設計はツール非依存を主張している（check #20）。本当にそうかを、
photo の実マイグレーション（expand 3本 / contract 2本、INSTANT・COPY 混在）を
goose v3.28.0 で運用して確かめた。比較対象は現行の golang-migrate v4。
すべて MySQL 8.4 に対する実測（2026-09-28、使い捨てコンテナ）。

## 設計の要件は両方で成立する（check #20 の答え）

| 要件 | golang-migrate（現行） | goose v3 |
|---|---|---|
| 系統（expand/contract）×モジュールで履歴テーブルを分ける | `MigrationsTable` | `database.NewStore(dialect, table)` + Provider。`photo_goose_expand` / `_contract` に分かれることを実測 |
| バイナリへの埋め込み | iofs | `fs.FS` を直接受ける |
| migrate サブコマンドからの適用 | ラッパー実装済み | Provider API で同型に書ける（スパイクで確認） |

ファイル形式だけ異なる: golang-migrate は `.up.sql` / `.down.sql` の2ファイル、
goose は1ファイルに `-- +goose Up` / `-- +goose Down` 注釈。photo の5本は機械変換で
そのまま通った（複数文も注釈なしで可。文中にセミコロンを含むプロシージャ等のみ
`StatementBegin` が要る）。

## 差分1: 途中失敗の状態管理（最大の思想差）

3文のうち2文目が失敗するマイグレーションで実測。**部分適用が残るのは両者同じ**
（MySQL の DDL は非トランザクショナル。1文目の `ADD COLUMN a` は当たったまま）。
違うのは「その事実の記録のしかた」。

|  | golang-migrate | goose |
|---|---|---|
| 失敗の記録 | **dirty フラグを立てる**。以後の全操作を拒否 | **何も記録しない**（そのバージョンの行を書かないだけ） |
| リトライ | dirty 解除（Force）が要る → 解除機構を自作する必要 | そのまま再実行され、部分適用と衝突する DDL エラー（Duplicate column）で落ちる |
| 手修復後 | Force で正しいバージョンを指し直す | リトライだけで通る（実測: DROP COLUMN a → 再実行 → 成功） |

どちらも「壊れたら止まる」は満たす。しかし golang-migrate の dirty は**解除の自作を
強制**し、そこがバグの温床になった実績がある: 先頭マイグレーションの失敗時に
`Prev` のエラーを「最初だった」と読み違えて **Force(-1) で履歴を全消しする**バグを
resetDirty に作り込んだ（#125、check #24 の実測で発見）。goose では先頭失敗を実測すると
履歴は空のままで、前方修正してリトライするだけで通る — **#125 の形のバグが構造的に
書けない**。

## 差分2: 欠番の検出（並行開発で効く）

v1, v3 適用済みの DB に v2 が後から届く状況（並行ブランチのマージで普通に起きる）:

|  | 挙動（実測） |
|---|---|
| golang-migrate | **`no change` で黙って無視**。v2 は適用されず、エラーも警告も出ない |
| goose | **既定で明示エラー** `detected 1 missing (out-of-order) migration lower than database version (3): version 2`。`WithAllowOutofOrder(true)` で適用に切り替え可 |

このリポジトリは並行エージェントでの開発が常態で、連番ファイルの交錯は現実に起きうる。
golang-migrate の挙動は「検査が常に通る側に倒れる」形そのもので、気づくのは
schema:check-live の乖離検出まで遅れる。**goose は境界で止める**。

## 差分3: 並行適用のロック

|  | 実装 | 既定 |
|---|---|---|
| golang-migrate | `GET_LOCK`（advisory lock） | **有効** |
| goose | テーブルベース lock（lease 30s + heartbeat 5s、プロセス死亡後は lease 失効で自動解放） | **無効**（`WithSessionLocker` の明示が必要） |

goose を採るなら**ロックの明示が必須**。2ランナー同時 migrate の一次防御は
deploy.yml の concurrency group だが、手元からの適用は守られないため。
なお goose のテーブル lock は lease 失効つきで、GET_LOCK の「接続が残ると
解放されない」問題が無い分、設計としては新しい。

## 差分4: 細部

- **空の系統**: 新サービスは contract が空。golang-migrate は Up 時 `fs.ErrNotExist`
  （ラッパーが握り済み）、goose は **Provider 構築時に `no migrations found`** で落ちる。
  ラッパーでの特別扱いはどちらでも要るが、場所が変わる
- **Go マイグレーション**: goose は第一級サポート（未使用・未測定。データ移送を
  伴う contract で効く可能性だけ記す）

## 所感（決定ではない）

設計はツール非依存で成立する — これが check #20 の答えで、**選定は本当にオプション**。
その上で所感: 失敗状態の表現（dirty + 自作解除 vs 記録なし + 自然衝突）と欠番検出の
2点で、**goose のほうが運用の自傷リスクが小さい**。#125 は「dirty 解除を自作させる」
API 形状が誘発したバグであり、goose にはその面が無い。乗り換えのコストは
ファイル形式の機械変換 + ラッパーの書き直し + ロックの明示で、いずれも小さい。
ただし現行で実害は出ていないため、このビルドでは乗り換えない。

## アップストリーム（還流）

プロダクションでツールを選ぶ際: (1) 並行開発の規模が大きいほど欠番検出の価値が上がる、
(2) dirty 解除の運用手順を自作しているなら、それ自体がリスク資産であることを認識する、
(3) どちらを選んでも「系統×モジュールで履歴テーブルを分ける」「embed して
サブコマンドで適用」の形は保てる。
