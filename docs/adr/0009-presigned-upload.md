# 0009. 画像は署名付きURLでアップロードし、pending → ready で確定する

## 背景

画像の受け取り方には (a) サーバ経由（multipart をアプリが受けて転送）と
(b) 署名付きURL（クライアントが直接ストレージへ PUT）がある。

オブジェクトストレージは外部システムであり、`Atomic` の3条件のうち
「相手が管理下にあり短いタイムアウトを付与できる」を満たさない。
したがって画像の書き込みは業務トランザクションに載せられず、DB とオブジェクトのどちらかが
先になる。2通りの不整合を分けて考える必要がある。

- **オブジェクトはあるが DB に行がない** → 誰からも参照されない。無害。回収で消せる
- **DB に行はあるがオブジェクトがない** → 表示が壊れる。有害

## 決定

署名付きURL方式を採り、状態を3段で進める。

```
1. POST /photos              行を pending_upload で作成 + 所有者タプル + 署名付き PUT URL を返す
2. PUT <署名URL>             クライアントがストレージへ直接（アプリを経由しない）
3. POST /photos/{id}:commit  HeadObject で実体を確認してから ready へ遷移
```

- `pending_upload` の行は表示経路（一覧・詳細・サービス間API）に出さない。公開もできない
- 実体が無ければ `:commit` は 409 を返し、遷移しない。よって「有害な側」の不整合は表に出ない
- 放置された `pending_upload` は `photo reclaim` がオブジェクト → 行 → タプルの順に削除する。
  途中で止まってもオブジェクトが先に消えるだけなので、再実行で回収できる

これは関係タプルの扱い（ADR 0004、チェック #6）と同じ構図であり、
別ドメインへの同期コマンドの pending 状態パターンとも同型である。

## 影響

- 投稿は2往復（作成 + commit）になる。`POST /photos` の応答に `upload_url` を足したので、
  既存の契約に対する破壊的変更にはならなかった
- 画像取得も署名付きURL（期限10分）を Read Model の組み立て後に付与する。
  バケットは非公開のままでよい
- `content_type` を先に受け取って署名に含めるため、クライアントは PUT 時に同じ値を送る必要がある

## 還流

`conventions/internal-03` の整合性クラスの判定に「外部ストレージへの書き込み」の例を追加する。
判定の軸は「逆方向の不整合が無害かどうか」であり、無害な側を先に書くと順序が決まる。
