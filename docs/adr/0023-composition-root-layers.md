# 0023. 合成ルートをプロセスとモジュールの 2 段に分け、DI ライブラリはまだ入れない

## 背景

[ADR 0003](0003-app-composition-root.md) で `services/<name>/app` を合成ルートにし、
`cmd/<name>` と `dev/allinone` のどちらも `app.Run` を呼ぶ形にした。
DI ライブラリ(fx / dig / wire)を入れるべきかを検討する中で、実物を確認して次のことが分かった(2026-10-18)。

**1. allinone のプロセス側は、ロガーとシグナルしか持っていない。**
トレーサーとエクスポーターの初期化、メトリクスのレジストリ、リスナーの起動、グレースフルシャットダウンは、
各サービスの `app.Run` が持っている。そのため allinone では、**photo と gear がそれぞれトレーサーと
エクスポーターを立て、1 プロセスに 2 つ並ぶ**。

**2. モジュールの組み立てが、プロセスの初期化順に暗黙に依存している。**
トレーサーはパッケージ変数(`var tracerProvider`)に入れられ、`openDB` がそれを読む。
`app.Run` には「deps の前に組む」というコメントがあり、順序の保証がコードの構造ではなくコメントにある。

**3. サービス間で起動処理がコピーされている。**
photo と gear の `Run` / `RunWith` を、サービス名を揃えて比べると 93 行のうち 80 行が一致した。
`openDB` / `configureDB` / `envOr` などの補助関数も両方にある。

**4. 環境ごとの組み立て関数が、実装の選択をまとめて切り替えている。**
`LocalDeps` と `OIDCDeps` の違いは認証・認可ストア・gear へのトークンの 3 つだけで、残りの組み立ては
重複している。また `OIDC_ISSUER` の有無ひとつで認証と認可が同時に切り替わるため、
「本物の Keycloak で認証し、認可だけ偽物にする」といった組み合わせが作れない。

**5. google/wire は 2025-08 にアーカイブされている。** 保守は終了している(フォークの goforj/wire が保守中)。

この検討の過程で外部からレビューを受け、次の指摘を取り入れた。

- DI ライブラリの導入を**依存の数**で決めるのは弱い。15 個でも順序や差し替えが入り組めば辛く、
  40 個でも一直線なら手書きで困らない
- 差し替えを「環境」で一括に切ると、**環境と実装の選択が混ざる**
- 共通の起動処理に `Routes` を必須にすると、HTTP を持たないワークロード
  (photo の outbox relay、将来の SQS コンシューマや定期実行)が収まらない
- 構造の検査を文字列検索で書くと、誤検知と見逃しが出る

## 決定

### 合成ルートを 2 段に分ける

| | 責務 | 置き場所 |
|---|---|---|
| **プロセスの合成ルート** | ロガー、シグナル、トレーサーとエクスポーター、メトリクスのレジストリ、シャットダウンの順序 | `cmd/<name>`、`dev/allinone`(共通部品は core) |
| **モジュールの合成ルート** | そのサービスの依存の組み立て(handler / usecase / repository)と、ワークロードの登録 | `services/<name>/app` |

- **プロセスの資源は 1 プロセスに 1 つ**。allinone でもトレーサーとエクスポーターは 1 つだけ立てる
- モジュールの合成ルートは、プロセスの資源(トレーサー、メトリクス)を**引数で受け取る**。
  パッケージ変数で受け渡さない(初期化順の暗黙の依存をなくす)
- 独立起動と allinone は、**モジュールの合成ルートを変更せずに共有する**。違うのはプロセス側だけ

### 共通の起動処理は「部品」として core に置く

一枚岩の `Run` にはしない。core に置くのは組み合わせて使える部品だけにする。

- テレメトリの初期化(トレーサー、エクスポーター、メトリクス)
- グレースフルシャットダウン(受付停止 → 処理中の完了待ち → 資源を閉じる、の順序)
- ワークロードの起動と停止の管理

**ワークロードの種類は別に表す。** HTTP のリスナー、outbox relay、キューのコンシューマ、定期実行は、
どれも「起動して、停止の合図で止まるもの」として登録する。HTTP のルーティングを共通の起動処理に要求しない。

2 サービスの一致(93 行中 80 行)は部品を共通化する根拠にはなるが、
**全サービスの実行モデルを固定する根拠にはしない**。

### 差し替え可能な基盤は、能力ごとに明示的に渡す

環境名(local / OIDC)で一括に選ばず、差し替える能力ごとに設定から実装を選び、
共通の組み立てに明示的に渡す。

```go
type Infrastructure struct {
    Authenticator authz.Authenticator
    AuthzStore    AuthzStore        // authz.Authorizer / RelationWriter / Lister を満たすもの
    GearClient    usecase.GearLink
}

func assemble(ctx context.Context, cfg Config, infra Infrastructure, proc Process) (*Deps, error)
```

認証と認可を別々に選べるので、テストや結合検証で組み合わせを作れる。
対象は必要になった能力から足す(DB やフラグ基盤など)。

### DI ライブラリはまだ入れない

導入の判断は**依存の数ではなく、組み立ての複雑さ**で行う。次のどれかが手で保てなくなったら検討する。

- 組み立てコードの変更頻度
- 環境や機能による実装の差し替えの数
- 資源の生成・破棄の順序の複雑さ
- 合成ルートの重複
- 依存関係の追跡やテストのしにくさ

検討するときは、まず合成ルートの分割と責務の整理を行い、それでも配線の負担が残る場合に、
コード生成型(wire 系)と実行時解決型(fx / dig)を比較する。**新規に入れるときは保守状況を確認する**
(google/wire は保守終了。使うならフォーク)。比較用に photo を各ライブラリで置き換えた試作を別途作る。

### 構造の検査は構文木で行う

モジュールの境界は従来どおり `GOWORK=off` のビルドで検査する([ADR 0006](0006-ci-gowork-off.md))。
コード上の使い方の決まり(例: `app/` が `http.Server` を直接作らない、パッケージ変数で資源を受け渡さない)は、
文字列検索ではなく `go/parser` / `go/ast` による静的検査で行う。

## 影響

- ADR 0003 の「`app/` が合成ルート」は、**モジュールの合成ルート**の意味に読み替える。
  `cmd/*` と `dev/allinone` は**プロセスの合成ルート**になる
- 次の変更が必要になる(#293 で扱う)
  - トレーサー・エクスポーター・メトリクスの初期化をプロセス側へ移し、`tracerProvider` のパッケージ変数をなくす
  - `LocalDeps` / `OIDCDeps` を、能力ごとの選択 + 共通の `assemble` に分ける
  - `Run` / `RunWith` を core の部品とワークロードの登録に分け、photo / gear のコピーをなくす
  - 上記の決まりを `go/ast` で検査する
- allinone でトレーサーを 1 つにすると、スパンのサービス名(`service.name`)がプロセス単位になる。
  どのサービスの処理かは、スパンの属性で区別する必要がある(実装時に決める)

## 還流

`conventions/internal-01` の合成ルートの記述を、プロセスとモジュールの 2 段に改める。
DI ライブラリの導入基準(依存数ではなく組み立ての複雑さ)と、構造の検査を構文木で行う方針を追記する。
