# 0023. 合成ルートはプロセスが持ち、サービスは組み立て関数を、ランタイムはワークロードを持つ

## 背景

[ADR 0003](0003-app-composition-root.md) で `services/<name>/app` を合成ルートにし、
`cmd/<name>` と `dev/allinone` のどちらも `app.Run` を呼ぶ形にした。
DI ライブラリ(fx / dig / wire)を入れるべきかを検討する中で、実物を確認して次のことが分かった(2026-10-18)。

**1. allinone のプロセス側は、ロガーとシグナルしか持っていない。**
トレーサーとエクスポーターの初期化、メトリクスのレジストリ、リスナーの起動、グレースフルシャットダウンは、
各サービスの `app.Run` が持っている。そのため allinone では、**photo と gear がそれぞれトレーサーと
エクスポーターを立て、1 プロセスに 2 つ並ぶ**。

**2. サービスの組み立てが、プロセスの初期化順に暗黙に依存している。**
トレーサーはパッケージ変数(`var tracerProvider`)に入れられ、`openDB` がそれを読む。
`app.Run` には「deps の前に組む」というコメントがあり、順序の保証がコードの構造ではなくコメントにある。

**3. サービス間で起動処理がコピーされている。**
photo と gear の `Run` / `RunWith` を、サービス名を揃えて比べると 93 行のうち 80 行が一致した。
`openDB` / `configureDB` / `envOr` などの補助関数も両方にある。

**4. 環境ごとの組み立て関数が、実装の選択をまとめて切り替えている。**
`LocalDeps` と `OIDCDeps` の違いは認証・認可ストア・gear へのトークンの 3 つだけで、残りの組み立ては
重複している。また `OIDC_ISSUER` の有無ひとつで認証と認可が同時に切り替わるため、
「本物の Keycloak で認証し、認可だけ偽物にする」といった組み合わせが作れない。

**5. 実行形態が既に 3 種類あり、それぞれ別の経路で組み立てている。**
`cmd/photo` はサブコマンドで、常駐の HTTP(`app.Run`)、常駐の outbox relay(`photo relay` → `app.RunRelay`)、
1 回で終わる処理(`migrate` / `reclaim` / `reclaim-links` / `republish`)を出し分けている。
relay は `newRelay` の中で自分で DB を開いており、他とは別の組み立て経路になっている。
また `RunWith` には「起動 → 停止の合図かエラーを待つ → `Shutdown`」という監督の処理があるが、
HTTP の `ListenAndServe` / `Shutdown` に直接書かれていて、HTTP 以外に使えない。

**6. google/wire は 2025-08 にアーカイブされている。** 保守は終了している(フォークの goforj/wire が保守中)。

この検討の過程で外部からレビューを受け、次の指摘を取り入れた。

- DI ライブラリの導入を**依存の数**で決めるのは弱い。15 個でも順序や差し替えが入り組めば辛く、
  40 個でも一直線なら手書きで困らない
- 差し替えを「環境」で一括に切ると、**環境と実装の選択が混ざる**
- **依存の組み立て方と、アプリケーションの実行のしかたを分ける**。共通の起動処理に `Routes` を
  必須にすると、HTTP を持たない実行形態(relay、SQS コンシューマ、定期実行)が収まらない
- **合成ルートの所有者はプロセスのエントリポイント**で、サービス側の組み立てはその下位にある。
  DDD のモジュールとデプロイ単位としてのサービスは、必ずしも一致しない
- 1 プロセスにまとめても、**全サービスに同じ DB の権限を渡すべきではない**(データの所有権の問題)
- 構造の検査を文字列検索で書くと、誤検知と見逃しが出る

## 決定

### 単位を分けて考える

| 単位 | 責務 |
|---|---|
| **モジュール** | 内部の依存関係の組み立てと、公開する契約 |
| **サービス** | 提供するワークロードの組み合わせ |
| **プロセス** | 共有する資源、起動・終了の管理 |

greenfield では今のところモジュールとサービスが 1 対 1(photo / gear)だが、同じものとは扱わない。
1 つのサービスが複数のモジュールを束ねることも、モジュールの境界を保ったまま
サービスの切り方(デプロイ単位)を変えることもありうる。

### 責務の分割: プロセスに合成ルート、サービスに組み立て関数、ランタイムにワークロード管理

| 層 | 所有者 | 責務 |
|---|---|---|
| **合成ルート**(Composition Root) | プロセスのエントリポイント(`cmd/*`、`dev/allinone`)。**1 プロセスに 1 つ** | 設定、テレメトリ、共有する資源の用意。どのサービスを起動するか。ワークロードの登録 |
| **組み立て関数**(Assembler、合成ルートの下位) | 各サービス(`services/<name>/app`) | サービス内部の repository / usecase / handler を組み立て、**ワークロードを返す**。自分では起動しない |
| **ランタイム**(Runtime) | core の部品 | 登録されたワークロードの起動・停止・グレースフルシャットダウン |

```go
// services/photo/app/assemble.go — サービス側: 内部を組み立て、ワークロードを返す
func Assemble(deps Dependencies) (Workloads, error) {
    repo := repository.NewPhotoRepository(deps.DB)
    cmds := usecase.NewPhotoCommands(repo, deps.Authz, ...)
    return Workloads{
        HTTP:  handlers(cmds, ...),          // external / internal / admin
        Relay: outboxrelay.New(deps.DB, deps.Bus),
    }, nil
}
```

```go
// cmd/photo/main.go — プロセス側: 資源を用意し、ワークロードを選んで載せる
func main() {
    proc := bootstrap.Process(ctx, "photo")        // 設定・テレメトリ・シグナル
    photo, err := app.Assemble(proc.DependenciesFor("photo"))
    runtime.Run(ctx,
        httpserver.New(photo.HTTP),
        photo.Relay,                               // 別プロセスにするなら載せない
    )
}
```

```go
// dev/allinone/main.go — 同じ組み立て関数を、1 プロセスにまとめて載せる
func main() {
    proc := bootstrap.Process(ctx, "allinone")
    photo, _ := photoapp.Assemble(proc.DependenciesFor("photo"))
    gear, _  := gearapp.Assemble(proc.DependenciesFor("gear"))
    runtime.Run(ctx,
        httpserver.New(photo.HTTP), httpserver.New(gear.HTTP),
        photo.Relay, gear.Relay,
    )
}
```

- **独立起動と allinone は、サービスの組み立て関数を変えずに共有する**。違うのはプロセス側だけ
- テレメトリ(トレーサー、エクスポーター、メトリクス)は**プロセスに 1 つ**。組み立て関数には引数で渡し、
  パッケージ変数で受け渡さない(初期化順の暗黙の依存をなくす)
- **ランタイムは「アプリケーションフレームワーク」ではなく、プロセススーパーバイザ(Process Supervisor、
  プロセス内の実行単位を管理するもの)と位置づける**。HTTP、ルーティング、ハンドラといった
  実行形態の概念をランタイムの契約に入れない。抽象化を最初から充実させることより、
  **HTTP 固有の概念を共通の契約に混ぜないこと**を優先する。今は HTTP しか無くても、
  `Routes` を必須にしないだけで、後から実行形態を足す自由度が大きく変わる
- 共通の処理は一枚岩の `Run` ではなく、組み合わせて使える部品として core に置く
  (テレメトリの初期化、スーパーバイザ、HTTP サーバーのワークロード実装)。
  2 サービスの一致(93 行中 80 行)は部品を共通化する根拠にはなるが、全サービスの実行モデルを固定する根拠にはしない

### 1 プロセスでも、データの権限は共有しない

**何を共有するかは、デプロイ形態だけでなくデータの所有権でも決まる。** 1 プロセスにまとめたからといって、
全サービスに同じ DB 接続(同じ権限)を渡さない。

- 共有してよいもの: テレメトリ、設定の読み込み、プロセスのライフサイクル
- **共有しないもの: DB 接続**。プロセスの合成ルートは、サービスごとにそのサービスの資格情報(DSN / DB ロール)で
  接続を開き、そのサービスの `Dependencies` にだけ渡す
- greenfield は既に、サービスごとの DB ロールと GRANT で他のサービスのテーブルに触れないようにしている
  (検証チェック #1)。`DependenciesFor(name)` はこの性質を保つ形にする

### ワークロードの契約

```go
type Workload interface {
    Run(ctx context.Context) error
}
```

HTTP サーバーも relay もコンシューマもこの契約を満たせる(relay は既に `RunRelay(ctx, cfg) error` の形)。
`Run` だけの契約は単純な分、終わり方の意味を決めておく必要がある。

| 状況 | ワークロードがすること | スーパーバイザがすること |
|---|---|---|
| `ctx` が取り消された(停止の合図) | 新しい仕事の受付を止め、処理中の仕事を猶予時間内に終えて **`nil` を返す** | 全ワークロードが返るのを待つ。全体の上限時間を超えたら待つのをやめる |
| 回復できない失敗 | **エラーを返す** | 他のワークロードの `ctx` を取り消し、プロセスを異常終了にする |
| 停止の合図の前に返った(`nil` でも) | — | **異常として扱う**。常駐のワークロードが自分から終わるのは想定外 |

- 猶予時間はワークロードが持つ(HTTP なら `ctx.Done()` を受けて `Shutdown` に猶予付きの context を渡す)。
  スーパーバイザは全体の上限時間だけを持つ
- 停止の順序は「**全ワークロードの停止 → 資源(DB など)を閉じる → テレメトリを送り切る**」。
  ワークロードが動いている間に DB を閉じない
- **1 回で終わる処理**(migrate / reclaim / republish)は常駐のワークロードではない。
  スーパーバイザに載せず、プロセスの合成ルートが直接呼んで、その結果で終了する(今のサブコマンドの形を保つ)
- HTTP のハンドラとコンシューマは**同じ usecase を使う**。ドメインのロジックは実行形態から独立する

**`Start` / `Stop` に分けない理由。** `Run(ctx)` は Go の慣習(`errgroup` など)にそのまま乗り、
今の HTTP と relay はどちらもこれで表せる。分ける必要が出るのは、
「リスナーが待ち受けを始めたことを知ってから次を起動したい」のような**準備完了の通知**が要るときで、
そのときは契約を変えず、任意で実装するインターフェース(例: `Ready() <-chan struct{}`)を足す。

### 差し替え可能な基盤は、能力ごとに明示的に渡す

環境名(local / OIDC)で一括に選ばず、差し替える能力ごとに設定から実装を選び、
組み立て関数の `Dependencies` に明示的に入れる。

```go
type Dependencies struct {
    DB            *sql.DB           // このサービスの資格情報で開いた接続
    Authenticator authz.Authenticator
    AuthzStore    AuthzStore        // authz.Authorizer / RelationWriter / Lister を満たすもの
    GearClient    usecase.GearLink
    Telemetry     telemetry.Handles
}
```

認証と認可を別々に選べるので、テストや結合検証で組み合わせを作れる。
対象は必要になった能力から足す。

### DI ライブラリはまだ入れない

導入の判断は**依存の数ではなく、組み立ての複雑さ**で行う。次のどれかが手で保てなくなったら検討する。

- 組み立てコードの変更頻度
- 環境や機能による実装の差し替えの数
- 資源の生成・破棄の順序の複雑さ
- 合成ルートの重複
- 依存関係の追跡やテストのしにくさ

検討するときは、まず合成ルートの分割と責務の整理を行い、それでも配線の負担が残る場合に、
コード生成型(wire 系)と実行時解決型(fx / dig)を比較する。**新規に入れるときは保守状況を確認する**
(google/wire は保守終了。使うならフォーク)。比較用に photo を各ライブラリで置き換えた試作を別途作る。

### 構造の検査は構文木で行う

モジュールの境界は従来どおり `GOWORK=off` のビルドで検査する([ADR 0006](0006-ci-gowork-off.md))。
コード上の使い方の決まり(例: 組み立て関数が `http.Server` を作らない、資源をパッケージ変数で受け渡さない)は、
文字列検索ではなく `go/parser` / `go/ast` による静的検査で行う。

## 影響

- ADR 0003 の「`app/` が合成ルート」は、**サービスの組み立て関数**の意味に読み替える。
  合成ルートは `cmd/*` と `dev/allinone`(プロセスのエントリポイント)が持つ
- 次の変更が必要になる(#293 で扱う)
  - テレメトリの初期化をプロセス側へ移し、`tracerProvider` のパッケージ変数をなくす
  - `LocalDeps` / `OIDCDeps` を、能力ごとの選択(`Dependencies`)+ サービスの `Assemble` に分ける
  - `Run` / `RunWith` の監督の処理を、HTTP から切り離したスーパーバイザとして core に出し、photo / gear のコピーをなくす
  - HTTP リスナーと outbox relay を `Workload` として表す。relay が自分で DB を開く経路(`newRelay`)をなくし、
    組み立て関数から受け取る
  - 上記の決まりを `go/ast` で検査する
- allinone でテレメトリを 1 つにすると、スパンのサービス名(`service.name`)がプロセス単位になる。
  どのサービスの処理かは、スパンの属性で区別する必要がある(実装時に決める)

## 還流

`conventions/internal-01` の合成ルートの記述を、「プロセスに合成ルート、サービスに組み立て関数、
ランタイムにワークロード管理」の 3 層に改める。モジュール・サービス・プロセスの区別、
1 プロセスでもデータの権限は共有しないこと、ワークロードの契約(終わり方の意味と停止の順序)を追記する。
DI ライブラリの導入基準(依存数ではなく組み立ての複雑さ)と、構造の検査を構文木で行う方針を追記する。
