# 0014. SSR はフラグを評価せず、判定結果を API から受け取る

## 背景

`conventions/internal-08` は「SSR 側の判定でも同じ key を使って表示と API の判定を一致させる」と定める。
#96 でこれに沿い、SSR にも OpenFeature + flagd provider を配線して `ops.photo_disable_uploads` を評価した。

運用してみると、同じフラグを Go と TS の2か所で評価する形は揃え続けるのが難しかった。

- 取得元・評価方式を両方で揃える必要がある。Go 側を in-process 評価へ移す変更（ADR 0013）に
  SSR が追従しないと、SSR だけ flagd に繋がらず常に既定値になり、表示と API が黙ってずれる
- JS の flagd provider は接続が切れると評価のたびに再接続を待ち、1評価 6〜7秒かかった。
  SSR のプロセスに provider の接続状態を抱えること自体が不安定要因になる
- 割合展開を両方で行うなら、ハッシュを2言語で完全一致させ続ける必要がある

一方で、SSR が知りたいのはフラグそのものではなく「この閲覧者が今それをできるか」だった。
リリース用のフラグ（オンラインマイグレーションの読み切替など）は API の契約を変えないため、
SSR はそもそも知る必要がない。

## 決定

**フラグは、それで振る舞いが変わるデプロイ単位だけが所有し、評価する。同じフラグを複数箇所で評価しない。**

- API の振る舞いを変えるフラグはサービス（Go）だけが持つ。SSR は評価しない
- 画面に出す必要がある判定は、サービスが評価した結果を**「できること」**として API の応答で返す。
  フラグ名は契約に載せない（フラグは消えるが、「できること」はフラグ以外の理由でも使え、フラグより長生きする）
  - 例: `GET /photos` の `can_create`。`usecase.PhotoCommands.CanCreate` が `Create` と同じ判定を返す
- 必須の真偽値として返す。項目の有無で表すと「止まっている」と「その項目を返さない版」を区別できない
- 画面だけに効くフラグが必要になったら、SSR が自分のものとして持つ（サービスと共有しない）

SSR から OpenFeature・flagd provider・フラグ宣言を外した。

## 影響

- 表示と API の判定は構造的にずれない（評価は1箇所）。フラグ基盤の方式（flagd / AppConfig 等）を
  変えても SSR は無変更
- 画面を開いてから投稿するまでの間にフラグが切り替わると、表示と実際が一時的に食い違う。
  投稿時にサービスが改めて判定し 503 を返すので実害はない（最終判定は常に API）
- 投稿画面へ URL で直接来た場合は事前に判定しない。送信時の 503（`photo.uploads_disabled`）で案内する
- 画面と API の両方を同時に変える機能は、フラグを分けず expand / contract の順序で出す
  （API を後方互換で先に出し、画面は応答に項目があるときだけ使う）

## 還流

`conventions/internal-08` の「SSR 側の判定でも同じ key を使って表示と API の判定を一致させる」を次へ置き換える。

> フラグは振る舞いを変えるデプロイ単位だけが評価する。表示に必要な判定はサービスが評価し、
> フラグ名ではなく「できること」として API で返す。SSR はサービスのフラグを評価しない。
