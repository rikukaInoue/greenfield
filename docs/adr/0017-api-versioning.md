# 0017. API のバージョニング

## 背景

規約（api-design §3.1）は「互換性のない変更はパスバージョンを上げ（`/v1` → `/v2`）、新旧を並行提供して
利用側の移行を待つ」と定める。並行提供をどの層で実現するかは決めていない。

素直に作ると、v2 のために usecase や domain まで複製したり、usecase に「v1 ならこう、v2 ならこう」の分岐が入ったりする。
そうなると業務ルールがバージョンの数だけ分かれ、旧版の廃止が業務ロジックの削除になる。

また、実装前の 0.4 の検査は「破壊的変更ならメジャーを上げる」だけで、上げた後に旧版を提供し続けているかは見ていなかった。
メジャーを上げて同じファイルを書き換えれば、旧版を消して置き換えても CI が通る。

## 決定

**バージョンを持つのはアダプタ（handler）だけ。usecase と domain はバージョンを持たない。**
v2 は同じ usecase につながる**別のアダプタ**であり、新旧の違いは入出力の変換（パス・ステータス・項目）に閉じる。

```
                ┌ handler/external    （v1: /photos,     200）┐
HTTP リスナー ──┤                                              ├─→ usecase ─→ domain
                └ handler/external/v2 （v2: /v2/photos,  201）┘
```

- `httpapi.API.AddMajor(n, version)` が同じリスナー・同じルータの上にメジャー n の huma API を作る。
  パスは `/v<n>` 配下、OpenAPI は別ドキュメント（スキーマの登録先もメジャーごとに分ける）
- スペックはメジャーごとに別ファイル: `<listener>.openapi.json`（メジャー1、接頭辞なし）/
  `<listener>.v<n>.openapi.json`（メジャー n、全パスが `/v<n>/`）
- **ファイル名とメジャーを1対1に結ぶ**。`info.version` のメジャーがファイル名と食い違えば CI が落ちる
- **既存ファイルへの破壊的変更は、メジャーを上げても通さない**。破壊的変更は次のメジャーのファイル（新しいアダプタ）として足すしかない
- 旧版のファイルを消せるのは、base で全操作が `deprecated` のときだけ（廃止予告のリリースを1回挟む）
- 新しいメジャーを足すときは、1つ前のメジャーが残っていること（並行提供）

## 影響

- 旧版の廃止は「アダプタ1つとスペック1ファイルの削除」で済み、業務ロジックに触れない
- 新旧で振る舞いを変えたくなったら（業務ルール自体の変更）、それはバージョニングではない。
  usecase の変更として扱い、両方のアダプタに効く
- アダプタが増えるほど handler のテストも増える。変換だけを検査すればよい（業務の検査は usecase 側に1つ）
- 利用側の移行（frontend の v2 化、Go client の再生成）は、提供側とは別の PR にする。
  並行提供中は旧版で動き続けるので、移行を急がせない

## 還流

api-design §3.1 / §3.4 に次を足す。

1. パスバージョンの並行提供はアダプタ層で行い、usecase / domain にバージョンを持ち込まない
2. スペックのファイル名とメジャーを結び、既存ファイルへの破壊的変更はメジャー更新でも通さない
   （「メジャーを上げれば通る」だと旧版を消して置き換えられる。並行提供を機械で強制できない）
3. 旧版の削除は、全操作を deprecated にしたリリースの後に限る
