# フィーチャーフラグ

<!-- 区分: 内部設計 / ステータス: Draft -->

**位置づけ**。フラグは「時間軸の制御」に限定する。段階リリースの途中経過（Release）、緊急停止（Ops）、実験（Experiment）。**主体の権利（プラン・契約・権限による恒久的な出し分け）はフラグでやらない**。それはauthzの管轄であり（billingエンタイトルメントの合成を含む単一の `Can`、§6.1）、一般に言われるPermission型フラグは本設計では不採用とする。判定機構を二重にしないためである。判定質問: 「最終的に全員に出すものの途中か？」— YESならフラグ、NO（契約で分かれ続ける）ならauthz。

**粒度**。1フラグ = ユーザーから見える1つの振る舞い。PRやデプロイの単位にはしない。複数PRにまたがる機能でもフラグは1つとし、完成までOFFのままトランクへマージし続ける（フラグがフィーチャーブランチの代替になる）。

**種類（寿命で分ける）**

| 種類 | 用途 | 寿命 |
|---|---|---|
| Release | 段階リリース | 数日〜数週間。100%到達で削除 |
| Ops | キルスイッチ（外部依存の縮退等） | 長期 |
| Experiment | A/Bテスト | 実験期間のみ |

**展開順と単位**。社内ユーザー → 協力テナント → 割合（1% → 10% → 50% → 100%）。割合のtargeting keyはテナントID（B2B文脈）を既定とし、テナントに属さない主体はユーザーID。ハッシュで固定し、同一主体が展開中にON/OFFを行き来しないようにする。keyの値はPrincipal（Subject / org）から取り、SSR側の判定でも同じkeyを使って表示とAPIの判定を一致させる。

**Expand/Contract（internal/05）との役割分担**。マイグレーションと二重書きはフラグなしで常時実行し、**新カラムからの読み込みだけ**を `release.` フラグで切り替える。問題があればフラグOFFで即座に旧経路へ戻る（再デプロイ不要）。100%で安定したらフラグを削除し、それを合図にcontractキューへ進む。これによりデプロイのロールバックとリリースの巻き戻しが分離される（デプロイ=ECS、リリース=フラグ、という2本のレバー。§10.3のdeploy/release分離の実装手段）。

**実装（Go / OpenFeature）**。標準interfaceが存在するため自前の差し込み口は作らず、OpenFeature SDKを直接語彙とする。プロバイダ（flagd / Unleash）は `cmd/*` の配線で注入し、差し替えはプロバイダ交換のみ。規約: (1) デフォルト値はフラグ基盤停止時にも安全な側（既存動作）にする。(2) 判定はリクエスト入口のミドルウェアで1回行い、結果をctxに積む（ハンドラ・usecaseは評価済みの値を読むだけ。1リクエスト内で値が揺れない）。(3) フラグ同士を依存させない。(4) フラグの配信反映はEventual（数秒の窓）であり、瞬時の一斉切替が必要な用途（整合性が壊れるもの）には使わない。

**運用ルール**。命名は `<種類>_<機能名>`（例: `release_order_new_pricing`、`ops_disable_billing_sync`）。区切りは "." でなく "_"——AWS AppConfig のフラグキーが `^[a-z][a-zA-Z0-9_-]{0,63}$` で "." を受け付けない（7.5 実測）ため、マネージド基盤で使えない文字を規約から外した。Releaseフラグには期限と担当者を必須とし、期限切れを通知する。100%到達後は次のスプリントでフラグとコード（旧経路）を削除する——「念のため残す」を許さない点で移行の削除KPI（§8.4）と同じ規律。テストは各フラグのON/OFF両方で通す。組み合わせ爆発を避けるため直積はやらず、対象フラグの2値 × 他フラグはデフォルト、を単位とする。

**バックエンド**。flagdまたはUnleash（セルフホスト）で開始し、必要になったら商用SaaSへ。OpenFeature経由であるためアプリのコードは変わらない。flagdの場合、フラグ定義はリポジトリ内のファイルとしてgit管理し、変更をPRレビューに載せる（誰がいつ何%にしたかが履歴に残る）。
