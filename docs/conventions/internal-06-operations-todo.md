### 10.1 可観測性

#### 構造化ログ（確定。#142 で実装）

ログは `core/logger` が組み、`core/middleware` が出す。**サービスは自分でハンドラを組まない。**

**1ストリーム1形式・1出力先。** 本番はJSONを**stdout**へ出す。stderrと混ぜると行の順序が保証されないため、レベルは出力先ではなく**フィールド**で表現する。人間向けテキストは開発機の逃げ道として `LOG_FORMAT=text` でのみ選べる（既定はJSON）。時刻は**RFC3339のUTC固定**（slogの既定は実行環境のタイムゾーンで出るため `ReplaceAttr` で潰す）。全行に `service.name` / `service.version` / `deployment.environment.name` が載る。

**フィールド名はOTel Semantic Conventionsに合わせる**（`http.request.method` / `url.path` / `http.response.status_code` / `http.server.request.duration_ms` / `server.address` / `user_agent.original`）。独自語彙（`method` / `path` / `status`）で始めると、APMやダッシュボードを入れた時に全部マッピングし直すことになる。**ログのスキーマ変更は破壊的変更として扱う**（ダッシュボードとアラートが壊れる）。

**相関IDの主キーは `traceparent`（W3C Trace Context）とする。** 受信したtrace-idを引き継ぎ、サーバ処理には**常に新しいspan-idを採番する**（受信したspanは親になる）。壊れた `traceparent` は黙って捨てて採番し直す（不正値で400を返すと経路上の壊れたプロキシ1つでサービスが落ちる。W3Cも未知・不正は無視して新しいトレースを始めるよう定める）。`X-Request-Id` は**外向けの取っ手として残す**: 来ていれば `request_id` として記録し、無ければtrace-idを流用し、いずれも応答ヘッダに返す（サポート問い合わせで「このIDで調べて」が成立する）。`X-Request-Id` を主キーにしないのは、デファクトだが標準ではなく**組織の外に出ると繋がらない**ため。

**アクセスログは1リクエスト1行**（canonical log line）。処理中に何行も出さず、完了時に1行へ詰める。検索が1行で完結し、ログ量が桁で減り、「遅いリクエスト」を `http.server.request.duration_ms > N` で即座に出せる。**後から行数を減らすのは難しいので最初に1行と決める。** 処理中に足したい情報はcontextのロガーに属性として載せ、逐次の実況はDebugに置く。起動時のルート一覧もDebug（常時出すと起動ごとに数十行増える）。

**レベルの意味を定義する。** Error = **人が動く必要がある**（アラート対象）。Warn = 劣化したが処理は継続した。Info = 業務イベント + リクエスト完了。Debug = 開発時のみ、ただし**実行時に `LOG_LEVEL` で上げられること**。400番台のクライアントエラーはErrorではなくInfo/Warn（ユーザーの入力ミスでアラートを鳴らすとアラートが信用されなくなる）。`LOG_LEVEL` の不正値でプロセスを落とさない（ログの設定ミスで起動しないほうが困る）。

**エラーはログするかreturnするか、どちらか一方。** 途中の層は `fmt.Errorf("...: %w", err)` で文脈を足して返すだけにし、ログするのはHTTP境界など「ここで判断した」場所だけ。両方やると同じ失敗が層ごとに何度も出る。

**秘密・個人情報は許可リスト方式。** 出していいフィールドを列挙する。禁止リスト（「`password` という名前を消す」）は必ず漏れる。`Authorization` / Cookie / トークン / パスワード / **DSN**（`user:pass@host` の形で平然と出る）/ リクエストボディ丸ごとは出さない。**クエリ文字列も出さない**（`url.path` のみ記録する。クエリにトークンや個人情報が乗りうる）。ログは複製されバックアップに入り保持期間まで残るため、**削除できない前提**で扱う。

**`core/logger` 以外の `core/*` はログしない。** 既定ロガーをライブラリから叩くと使う側が出力を制御できない。contextからロガーを取るか、エラーを返して呼び出し側に委ねる。

**基盤ミドルウェアは選択させず必ず入れる。** `httpapi.New` が相関ID→アクセスログ→パニック復帰の順で、**認証より外側に**積む。選択可能にすると「アクセスログの無いリスナー」が作れてしまい、認証で401になったリクエストが記録から消える。`Options.Middlewares`（認証の後に適用）では位置が足りない。

**パニックはRFC 9457のproblemに変換する。** これが無いと、`net/http` は接続単位でrecoverするのでプロセスは落ちないが、**クライアントが受け取るのはEOF（接続切断）**になり、「エラーはproblemで返す」から外れる唯一の経路になる。パニックは標準 `log` パッケージに出る（`http: panic serving`）ためslogの外に落ちて相関IDとも紐づかない。応答を書き始めた後のパニックは救えないので、本文を継ぎ足さずログだけ残す（壊れたJSONを作らない）。

**既知の例外: flagdのログは寄せられない**（flagd v0.7.0）。`flagd.WithLogger(logr.Logger)` は**rpcリゾルバにしか渡らず**、我々が使うin-processリゾルバ（ADR 0013）は `NewInProcessService` が無条件に自前のzapロガーを作る（`process.Configuration` に渡す口が無い。`in_process/service.go:145`、sinkは `os.Stderr` 固定・レベルInfo固定）。結果としてflagdは `{"level":"info","ts":...}` をstderrへ、アプリは `{"time":"...Z","level":"INFO",...}` をstdoutへ出す。**1形式に揃える方針の唯一の例外**であり、上流がin-process側にロガーを通すまで直せない。`WithLogger` を渡す配線は**あえて入れていない**（我々の経路ではno-opで、「書いてあるが効いていない」コードを増やすだけになる）。

#### メトリクス（確定。#59 で実装）

昇格シグナル3種を Prometheus 形式で公開する。計測コードは `telemetry/`（**core とは別モジュール**。core に入れると全利用者が prometheus クライアントの依存を抱える）に置き、使ってよいのは各サービスの合成ルートのみ。`/metrics` は契約・認証の面と混ぜず**専用ポート**（`METRICS_ADDR`。未設定なら出さない）。観測スタックは `mise run obs:up`（prometheus + grafana、ダッシュボード `昇格シグナル` は git 管理でレビューに載せる）。

| シグナル | メトリクス | 何の合図か |
|---|---|---|
| プール使用率 | `db_pool_in_use / open / max / wait_total` | 接続の飽和 → インスタンス分離・プール見直し |
| authz レイテンシ | `http_server_request_duration_seconds`（authz） | 認可の往復が高い → キャッシュ・配置の見直し |
| outbox 滞留 | `outbox_pending` / `outbox_oldest_age_seconds` | relay が追いつかない → 配送の並列化・バス見直し |

SQL 由来の gauge は「読めない」を **-1** で返す（0=滞留なし と 欠測 を混同しない。fail open にしない）。

#### トレース（確定。#214）

OTel SDK は `telemetry` に置き、**core には入れない**（`core/middleware.Correlate` は stdlib の手書き伝播のまま。全利用者に exporter とその依存を抱えさせない、という当初判断を維持した）。差し替えたのは伝播でなく**採番の向き**で、Correlate が採番した `trace_id` / `span_id` を SDK の IDGenerator がそのまま使う。これにより **canonical log line の trace_id / span_id と span の ID が同一**になり（実測: ログの trace_id で Tempo からトレースを取得、ログの span_id = サーバ span の ID）、相関の主キーは増えない。

- **サーバ span**: `telemetry.Tracer.Middleware()` を `httpapi.Options.Tracing`（基盤スタック直後・認証より前。core は注入口だけ持つ）へ。401 で落ちるリクエストにも span が付く
- **クライアント span**: `Tracer.WrapTransport` を合成ルートで `http.DefaultTransport` に適用。W3C propagator（`TraceContext`）が traceparent を注入し、httpclient の手書きヘッダを正しい親（クライアント span）で上書きする
- **DB span**: `openDB`（otelsql）。**TracerProvider は明示渡し**——グローバルは 1 プロセス複数サービス（allinone）で後勝ちになり、span の service.name が別サービスに化ける（実測）。allinone ではクライアント span の帰属だけこの制約が残る（プロセス分離では正しい）
- **無効が既定**: `OTEL_EXPORTER_OTLP_ENDPOINT` 未設定なら何も送らず、ミドルウェアは素通し。計測の有無がアプリの挙動を変えない
- **バックエンド**: compose の obs プロファイルに Tempo（OTLP :4318 / クエリ :3200）。Grafana にデータソース済み。jaeger でなく Tempo にしたのは Grafana との統合が provisioning 1 ファイルで済むため
- 排水（10.8）との整合: serve の停止時に `Tracer.Shutdown` で未送信 span を吐き切る

実測（allinone + Tempo）: 紐付けつき投稿 1 リクエストで **25 span が 1 トレース**に載る——photo サーバ span → クライアント span → gear サーバ span（親子が正しく連鎖）+ 両サービスの SQL span（begin_tx / query / exec / commit）+ フラグ評価。検証ログ: 2026-09-30-stage-82。

### 10.3 CI/CD・リリース方式（一部確定）

リリース方式の確定部分: デプロイ（コードを置く）とリリース（ユーザーに見せる）の分離を原則とし、DBのexpandはトラフィック切り替え前、contractは後続リリースで実行する（internal/05）。トラフィック切り替えは**ECSネイティブのBlue/Green・カナリア機能**を使う（CodeDeployは不要になったため使わない）。デプロイの巻き戻し（ECS `stopDeployment`。実測32秒で本番復帰）とリリースの巻き戻し（フィーチャーフラグ、internal/08）は独立した2本のレバーとして扱う。Kayenta（ベースラインとの統計比較）は単独導入の選択肢ではなくなっており（Spinnakerの一部としてのみ現存）採用しない。統計比較が必要になった場合はECSのライフサイクルフックで比較ロジックを自作する。

**既定形は1本: expand 先行 + ゲート付き Blue/Green**（7.2 / 7.2b の実測で確定。verification-log 2026-09-30）。ゲートは `POST_TEST_TRAFFIC_SHIFT` のライフサイクルフックで、テストトラフィック経由の検証を **healthz でなく業務の書き込みまで**通す（healthz は「壊れた版」でも緑を返す。実測: 書き込み検証のゲートで被弾 0/1,679、ゲート無しのカナリア+アラームで 69/2,880）。ゲートは全サービス常設とし、「付けるか」の判断自体を設けない。切り替え中も bake 中もマネージドの閾値アラームで自動ロールバックさせる。ゲートのテスト書き込みは **create で止めて commit しない**——残る pending_upload の行は回収ジョブ（check #28）の対象に収まる。この整合は偶然でなく制約であり、フックを commit まで深くするなら合成テナント隔離か後片付けを先に設計する。テスト主体は専用の合成 subject で発行し、テスト起因を識別可能に保つ（#199）。

**カナリアはデプロイごとの選択肢ではなく、サービスの属性**とする。CANARY へ格上げするのは「実トラフィックでしか出ない壊れ方」（性能・実データ依存・キャッシュ挙動）を持つサービスだけで、IaC のサービス定義に固定し、判定理由は Atomic 判定と同じく**その行のコメント**に書く。変更はインフラ PR + レビュー。これにより判断の頻度は「デプロイごと」から「サービスの性格が変わったとき」へ落ちる。なお機能の段階公開はデプロイのカナリアでやらない——それはリリース側のレバー（フラグ）の仕事で、混ぜると2本のレバーが崩れる。

判断の軸は格上げだけでなく**格下げ**（容量）もある（#201）。B/G 既定は**切り替え中にタスク数が2倍**で走ることを前提にしており、このヘッドルームを確保できないサービスはローリングへ格下げする、という判断が本番規模では出てくる。格上げ（実トラフィック依存の failure mode）と格下げ（デプロイ中 2x を許容できない容量制約）は独立した軸なので、IaC 行コメントの判断理由はどちらの語彙でも書けるようにしておく。

**普通の開発者はデプロイについて何も選ばない。** やることはコードと expand マイグレーションを書いて PR を出すだけ。遭遇するのは（1）INSTANT で通らない DDL を CI が止めて例外プロセス（gh-ost / 保守時間。所要見積もりは Aurora fast clone のリハーサルで取る）を案内する、（2）ゲートが落とした通知（テストトラフィックでの失敗内容付き）を受けて直す、の2つで、どちらも判断ではなく手順である。判断が要る場面（カナリア組への出し入れ・COPY 系 DDL の計画）はプラットフォーム側の低頻度案件に寄せる。

残りTBD: モノレポの差分ビルド（モジュール単位）、独立パイプライン、lint群の実設定、CODEOWNERS。

### 10.4 テスト戦略（層ごとの方針、testcontainers、契約テスト、E2Eの範囲）

層ごとの方針は「その層でしか検出できないものを、その層で検出する」。上の層に押し上げるほど遅く・不安定になり、下の層に押し下げるほど検出対象が定義上存在できなくなる（fail open の事例2）。

| 層 | 対象 | 道具 | 例 |
|---|---|---|---|
| domain / usecase | 不変条件・状態遷移・規約 | 純ユニット + **振る舞いを観測するダブル** | txTracker（「tx の中か」を持つ）+ tx 内から呼ばれたら失敗するストレージ。規約違反の実装で**失敗する**ことまで確認したダブルだけを信用する |
| handler | ルーティング・エラー写像・リスナー分離 | huma のルート検査（Routes()） | 「admin の経路が external に生えていない」を構造で見る |
| 統合（実 MySQL） | GRANT・マイグレーション・outbox/inbox | CI の services: コンテナ + モジュール単位ジョブ | migrations / eventual / authz の各ジョブ。DB が要るモジュールだけ立てる |
| 契約 | API スキーマの互換 | **oasdiff + 生成クライアント** | 破壊的変更はメジャー未更新で CI が落ちる。クライアントは生成物なので、消費側の追従漏れはコンパイルエラーとして出る |
| 性質の再演（E2E） | 設計の主張そのもの | ドリルスクリプト群 | eventual-check（#8/#9）、rename-drill（#25）、shutdown-drill（10.8）、timeout-drill（10.5）、authsweep（#182） |

**testcontainers は採らない。** 開発機は `db:up` の常駐 compose、CI は services: コンテナをモジュール単位ジョブで立てる形が既にあり、テストごとのコンテナ起動は同じ検証をより遅くやるだけになる。再考する条件は「モジュール内のテスト並列化でポート・スキーマの衝突が実際に問題になったとき」。

**consumer-driven contract（Pact 系）は入れない。** API の消費者が全部このリポジトリ内（frontend と相手サービス）に居るため、生成クライアント + affected CI（消費側のジョブが自動で発火）で「契約が壊れたら消費者のビルドが落ちる」が既に成立している。oasdiff が守るのはスキーマ互換で、**挙動の互換は守らない**——そこは check #15/#25 のような再演ドリルの担当。リポジトリ外の消費者が現れた時点で consumer-driven を再検討する。

**E2E の範囲**は「設計の主張の再演」に限る。画面操作の網羅 E2E は持たない（維持費が検出力を上回る）。ドリルは常設（CI の eventual / authsweep）と手動（負荷・停止系）に分かれ、手動側も**スクリプトとして repo に置き、fail closed に書く**（前提が欠けたら空振りせず失敗。「テストの成功は問題ないことを意味しない」の規律はテスト戦略の一部である）。フラグは対象フラグの ON/OFF 両方 × 他フラグ既定で通す（internal-08）。

### 10.5 タイムアウト・リトライ・レート制限の規約（階層別の具体値、リトライ可否の線引き）

原則は1つ: **内側ほど短くする**。内側の合計が外側を超えると、外側がタイムアウトした後も内側は走り続け、クライアントには失敗が返るのに仕事は完了する（結果の行方不明）。逆なら、失敗は必ず内側から観測順に立ち上がる（#215。実測: `dev/scripts/timeout-drill.sh`）。

| 層 | 値 | 根拠 |
|---|---|---|
| エッジ（ALB idle） | 60s（既定） | 変更しない。以下は全部これより短い |
| サーバ ReadHeader | 5s | スローロリス対策。ヘッダを送らない接続を弾く |
| サーバ Read / Write | 15s / 30s | Write がハンドラ実行時間の上限。内部呼び出しの合計をこれ未満に収める |
| サーバ Idle | **65s（ALB より長く）** | 短いと LB が使い回す接続をサーバが先に閉じ、断続的な 502 になる |
| 内部 HTTP クライアント | 10s（トークン取得は 5s） | `core/httpclient`。サーバ Write 30s の内側に収まる |
| DB（DDL） | lock_wait_timeout 5s + リトライ3回 | migrate 側が fail fast する（check #19、internal-05） |
| DB（クエリ） | DSN readTimeout/writeTimeout 10s | 凍結コネクションの回収（#219 実測。下記プール節） |
| migrate ジョブ全体 | ジョブレベルの締め切り + 再実行 | DDL 中のフェイルオーバーはエラーでなくハング。中断後のテーブルは atomic DDL で無傷、再実行で完走（#219 実測） |

**接続プール**は `configureDB`（各サービスの合成ルート）で必ず設定する。既定 MaxOpen/MaxIdle 25・ConnMaxLifetime 300s（フェイルオーバー後に古い宛先の接続を持ち続けない）。**DSN には `readTimeout=10s&writeTimeout=10s` も必ず付ける**——フェイルオーバーの瞬間、確立済みコネクションはエラーでなく**凍結**する（TCP がブラックホール化し、MySQL の read timeout は既定で無限。#219 の実測ではプローブが10分以上ハングした）。ConnMaxLifetime は返却時にしか判定されないので、ハング中の接続を救えない。凍結はクエリ自体の締め切りでしか回収できない。本番値は逆算で決める: **MaxOpenConns × タスク数 × プロセス内の DB 接続数 < DB の max_connections**。Go の既定は無制限で、負荷時に max_connections を食い潰すまで観測に出ない（プール使用率メトリクスだけあって設定が無い「観測が実装より先行」の状態を #215 で解消）。

**リトライの線引き**。自動リトライしてよいのは（a）GET / HEAD、（b）冪等キーを持つコマンド（`Idempotency-Key`、紐付けキー）だけ。ただし `core/httpclient` に自動リトライは**入れない**——再試行の受け皿は relay（バックオフ持ち）と回収ジョブ（pending の照会・確定）に寄せてあり、リクエストの中で粘るより「1回で返して pending に劣化させる」が既定形。実測: 依存先（gear）が 20 秒黙る状態で投稿は **201・応答 10.1 秒で頭打ち**（クライアントタイムアウトが効き、依存先の遅さを引き継がない）、紐付けは pending に留まり回収ジョブが引き継ぐ。劣化であって欠損ではない。

**レート制限**はエッジ（ALB + WAF / API Gateway）に置き、アプリには実装しない。数を守る仕事は流量が集約される場所で1回やる——サービスごとに実装すると閾値の整合を N 箇所で保守することになる。アプリ側は 429 + `Retry-After` を語彙として予約するのみ（huma のエラー体系は 10.6）。内部リスナーには置かない（M2M の流量は呼ぶ側の設計で決まっており、絞ると pending の滞留に化けるだけ）。

### 10.6 エラー処理規約（エラーコード体系、ドメインエラー→HTTPマッピング、humaとの接続）

エラー応答は **RFC 9457（problem+json、`core/problem`）の1形式のみ**。huma が生成するエラー（バリデーション等）にも `problem.Install()` で同じ code を載せる（Register より前に呼ぶ。httpapi.New が保証）。

**code は2層。** 共通語彙（`bad_request` / `unauthenticated` / `forbidden` / `not_found` / `conflict` / `validation_failed` / `internal`）と、ドメイン名前空間 `<service>.<詳細>`（例: `photo.not_found`、`photo.already_published`、`photo.upload_not_finished`）。ドメイン code を切るのは**クライアントがそのエラーで分岐する必要があるときだけ**——409 が「公開済み」なのか「アップロード未完了」なのかで次の操作が変わる、という場合。分岐しないものに固有 code を発行しない（語彙の総量が契約の保守面積になる）。

**写像はハンドラの1箇所に集める。** usecase はドメインの語彙（`ErrForbidden`、`ErrAlreadyPublished`…）でエラーを返し、HTTP への写像は各リスナーのハンドラにある変換関数1つで行う。usecase に HTTP を知らせない（差し替え検証 #18 の前提）。写像の原則:

- 存在しない / 見る権利がない → **404 に寄せてよい**（存在の暴露が権限情報になる場合。authsweep は 403/404 の両方を正解として扱う）
- 状態が許さない → 409 + ドメイン code（何が許さないかを code で言う）
- 入力が壊れている → 400/422 系は huma のバリデーションに任せ、自前で重複実装しない
- **未知のエラーは 500 に倒す**（fail closed。写像に無いエラーを 200 や 400 に化けさせない）。500 の body は `internal` + 定型文のみで、詳細はログにだけ出す（trace_id で突合する）

**OpenAPI には実際に返しうる code だけ並べる**（監査 E で「返さないコードの列挙」を削った経緯）。列挙が実装とずれる方向は2つあり、返さないものを書く（読者を誤解させる）と返すものを書かない（契約漏れ）——後者は oasdiff では守れないので、ドメイン code を足す PR はハンドラの写像と OpenAPI の列挙を同時に変える（レビュー観点として固定）。

429 + `Retry-After` は語彙として予約済み・未実装（レート制限はエッジに置く。10.5）。

### 10.8 ヘルスチェックとグレースフルシャットダウン（3リスナー+relayの排水順序）

停止は SIGTERM を合図とする**排水**であり、順序は役割で決まる（#222。実測: `dev/scripts/shutdown-drill.sh`、verification-log 2026-09-30-stage-drain）。

**serve（3リスナー）**: 新規受付を止め、処理中のリクエストを待ってから **DB を閉じる**（処理中のクエリを道連れにしない）。上限は `SHUTDOWN_TIMEOUT_SECONDS`（既定25秒。ECS の stopTimeout 30秒から SIGKILL までの猶予に収める）。排水しきれなかった＝処理中の接続を切った、は**黙らせず警告に出す**。メトリクスの `/metrics` はリスナーの排水後に止める——停止中の観測が先に消えると、排水の失敗がどこにも出ない。実測: コミット直前で3秒待つ処理中リクエスト8本が SIGTERM 後に全部 201 で完走（SIGKILL では 8/8 切断）。

**relay / consumer**: 停止指示が来ても**処理中のバッチ・受信済みメッセージは完走させる**（上限 `DrainTimeout`、既定20秒）。途中で切ると「送れたのに記録できない」「処理したのに削除できない」が起こり、**自作の再配信＝避けられる重複**を生む（inbox が吸収するとはいえ、停止のたびに重複を作る運用にしない）。relay は停止時に未送信の残数をログへ記録する（`relay: 排水して停止 unsent=N`。残作業を停止のたびに観測可能にする）。実測: 150件中バッチ途中の SIGTERM で送信100＋未送信50の帳尻一致、context canceled ゼロ、全量ドレイン後の inbox 150件・重複スキップ0。

**正常な停止は exit 0**。SIGTERM での終了を異常扱いして exit 1 にしない（ECS のタスク停止が毎回「異常終了」として記録されるのを防ぐ）。

ヘルスチェックの使い分けは既存の実測どおり: `/healthz` は「生きている」しか言えず（fail open 事例3）、デプロイの成否は業務の書き込みまで通す昇格ゲートで判定する（§10.3）。排水中に `/healthz` を落として LB からの切り離しを早める最適化は、ECS では deregistration が SIGTERM に先行するため今は入れない（入れる場合は根拠の実測から）。

### 10.9 依存更新と脆弱性通知の運用（確定）

依存の脆弱性対応は「見つける」（govulncheck、PR ごと + 日次。#180）と「常に新しく保つ」（Dependabot weekly、`.github/dependabot.yml`。#181）の2系統で回す。gomod は全モジュールを `directories` でまとめて**1本の grouped PR** にする——片側のモジュールだけ版が上がると共有依存のドリフト（`lint:drift` が観測）になるため、同時に上げる形が構造的に正しい。major だけは group から外れて個別 PR になる。

**Dependabot alerts と govulncheck の判定が食い違ったら govulncheck を採る。** alerts は依存グラフだけを見て到達性を見ないため、呼ばれないコードパスの CVE も鳴らす。その alert は「govulncheck で到達不能」と理由を書いて Dismiss する（黙って消さない——理由の無い Dismiss は次に見た人が再調査する）。逆に govulncheck だけが鳴るケース（Go toolchain 自体の CVE）は依存でなく mise.toml の go を上げる。

**配る側の証明（#218）**: image-release ワークフローが ghcr へ push するイメージには cosign keyless 署名・SPDX SBOM の attestation・GitHub provenance が付く。デプロイ側は `dev/scripts/image-verify.sh` で3点を fail closed に検証してから使う（同一性は workflow ref で縛る。偽 identity の拒否まで実測済み）。検出系（本節の5層）が「入っているものに穴が無いか」を見るのに対し、こちらは「入っているものが本当にうちのビルドか」を見る——独立した軸。

Dependabot PR の自動マージは**まだ有効にしない**。自動マージの前提は「壊れた更新でテストが本当に落ちること」で、認可の総当たりテスト（#182）が入るまでは、検査ではなく自動デプロイの穴になる。有効化するとしても patch のみ・minor 以上は人間が読む。


### 10.10 検査自体の運用（flaky 隔離・検査の回帰テスト・定期監査）

「判断を消して手順にした」設計は、手順（ゲート・CI・計器）が信用を失った瞬間に崩れる——全員が bypass を探し始めるため。ここは**検査そのものの運用**を定める（#226）。

**ゲート・検査が誤検知（flaky）したときの規律。**
1. 隔離は「無効化」ではなく**非ブロッキング化**（warn で走らせ続ける）。観測を止めると再発の証拠が消える
2. 隔離には **issue と期限を必須**にする（Release フラグの期限規律と同型。期限なしの隔離は静かな無効化）
3. bypass の経路は1つだけ（PR に理由を書いて隔離コミットを入れる）。個人の判断で検査を避ける経路（force merge 等）を作らない
4. 復帰条件は「原因の特定」であって「しばらく緑だった」ではない

**検査の回帰テストの台帳。** 検査を足すときは「破ってみせる手段」を同時に足す。現状:

| 検査 | 自身の回帰テスト | 実行 |
|---|---|---|
| affected（CI の発火判定） | Go テスト（ADR 0015: 判定ミス=全モジュール検査漏れ） | audit:checks |
| api-breaking / baseline-diff | セルフテスト（落ちるべき形を含む） | audit:checks |
| アラートルール | promtool 単体テスト（発火する/しないの両側） | lint:alerts（check 常設） |
| 昇格ゲートの判定 | Python 単体テスト（healthz 緑・書き込み500 を落とす等） | audit:checks |
| querylint | Go テスト | audit:checks |
| fk:check / replace-check / secure-defaults | **変異ドリル**（違反を作って検査が落ちることを見る。導入時に実施済み） | 定期監査時に手動再実施 |
| eventual-check / 各種ドリル | fail closed 構造（前提欠如で失敗）+ 導入時の変異確認 | 同上 |

**定期監査。** `mise run audit:checks`（検査ツール自身の回帰テスト一括）を**四半期の scheduled workflow**（.github/workflows/audit.yml）で回し、落ちたら issue が自動で立つ。audit-2026-09-27 のような「主張と機械の乖離」の棚卸しは、この定期実行をトリガーに人間が行う（scheduled run が赤いまま放置される形にしない——通知先が issue なのはそのため）。
