### 10.1 可観測性

#### 構造化ログ（確定。#142 で実装）

ログは `core/logger` が組み、`core/middleware` が出す。**サービスは自分でハンドラを組まない。**

**1ストリーム1形式・1出力先。** 本番はJSONを**stdout**へ出す。stderrと混ぜると行の順序が保証されないため、レベルは出力先ではなく**フィールド**で表現する。人間向けテキストは開発機の逃げ道として `LOG_FORMAT=text` でのみ選べる（既定はJSON）。時刻は**RFC3339のUTC固定**（slogの既定は実行環境のタイムゾーンで出るため `ReplaceAttr` で潰す）。全行に `service.name` / `service.version` / `deployment.environment.name` が載る。

**フィールド名はOTel Semantic Conventionsに合わせる**（`http.request.method` / `url.path` / `http.response.status_code` / `http.server.request.duration_ms` / `server.address` / `user_agent.original`）。独自語彙（`method` / `path` / `status`）で始めると、APMやダッシュボードを入れた時に全部マッピングし直すことになる。**ログのスキーマ変更は破壊的変更として扱う**（ダッシュボードとアラートが壊れる）。

**相関IDの主キーは `traceparent`（W3C Trace Context）とする。** 受信したtrace-idを引き継ぎ、サーバ処理には**常に新しいspan-idを採番する**（受信したspanは親になる）。壊れた `traceparent` は黙って捨てて採番し直す（不正値で400を返すと経路上の壊れたプロキシ1つでサービスが落ちる。W3Cも未知・不正は無視して新しいトレースを始めるよう定める）。`X-Request-Id` は**外向けの取っ手として残す**: 来ていれば `request_id` として記録し、無ければtrace-idを流用し、いずれも応答ヘッダに返す（サポート問い合わせで「このIDで調べて」が成立する）。`X-Request-Id` を主キーにしないのは、デファクトだが標準ではなく**組織の外に出ると繋がらない**ため。

**アクセスログは1リクエスト1行**（canonical log line）。処理中に何行も出さず、完了時に1行へ詰める。検索が1行で完結し、ログ量が桁で減り、「遅いリクエスト」を `http.server.request.duration_ms > N` で即座に出せる。**後から行数を減らすのは難しいので最初に1行と決める。** 処理中に足したい情報はcontextのロガーに属性として載せ、逐次の実況はDebugに置く。起動時のルート一覧もDebug（常時出すと起動ごとに数十行増える）。

**レベルの意味を定義する。** Error = **人が動く必要がある**（アラート対象）。Warn = 劣化したが処理は継続した。Info = 業務イベント + リクエスト完了。Debug = 開発時のみ、ただし**実行時に `LOG_LEVEL` で上げられること**。400番台のクライアントエラーはErrorではなくInfo/Warn（ユーザーの入力ミスでアラートを鳴らすとアラートが信用されなくなる）。`LOG_LEVEL` の不正値でプロセスを落とさない（ログの設定ミスで起動しないほうが困る）。

**エラーはログするかreturnするか、どちらか一方。** 途中の層は `fmt.Errorf("...: %w", err)` で文脈を足して返すだけにし、ログするのはHTTP境界など「ここで判断した」場所だけ。両方やると同じ失敗が層ごとに何度も出る。

**秘密・個人情報は許可リスト方式。** 出していいフィールドを列挙する。禁止リスト（「`password` という名前を消す」）は必ず漏れる。`Authorization` / Cookie / トークン / パスワード / **DSN**（`user:pass@host` の形で平然と出る）/ リクエストボディ丸ごとは出さない。**クエリ文字列も出さない**（`url.path` のみ記録する。クエリにトークンや個人情報が乗りうる）。ログは複製されバックアップに入り保持期間まで残るため、**削除できない前提**で扱う。

**`core/logger` 以外の `core/*` はログしない。** 既定ロガーをライブラリから叩くと使う側が出力を制御できない。contextからロガーを取るか、エラーを返して呼び出し側に委ねる。

**基盤ミドルウェアは選択させず必ず入れる。** `httpapi.New` が相関ID→アクセスログ→パニック復帰の順で、**認証より外側に**積む。選択可能にすると「アクセスログの無いリスナー」が作れてしまい、認証で401になったリクエストが記録から消える。`Options.Middlewares`（認証の後に適用）では位置が足りない。

**パニックはRFC 9457のproblemに変換する。** これが無いと、`net/http` は接続単位でrecoverするのでプロセスは落ちないが、**クライアントが受け取るのはEOF（接続切断）**になり、「エラーはproblemで返す」から外れる唯一の経路になる。パニックは標準 `log` パッケージに出る（`http: panic serving`）ためslogの外に落ちて相関IDとも紐づかない。応答を書き始めた後のパニックは救えないので、本文を継ぎ足さずログだけ残す（壊れたJSONを作らない）。

**既知の例外: flagdのログは寄せられない**（flagd v0.7.0）。`flagd.WithLogger(logr.Logger)` は**rpcリゾルバにしか渡らず**、我々が使うin-processリゾルバ（ADR 0013）は `NewInProcessService` が無条件に自前のzapロガーを作る（`process.Configuration` に渡す口が無い。`in_process/service.go:145`、sinkは `os.Stderr` 固定・レベルInfo固定）。結果としてflagdは `{"level":"info","ts":...}` をstderrへ、アプリは `{"time":"...Z","level":"INFO",...}` をstdoutへ出す。**1形式に揃える方針の唯一の例外**であり、上流がin-process側にロガーを通すまで直せない。`WithLogger` を渡す配線は**あえて入れていない**（我々の経路ではno-opで、「書いてあるが効いていない」コードを増やすだけになる）。

#### メトリクス（確定。#59 で実装）

昇格シグナル3種を Prometheus 形式で公開する。計測コードは `telemetry/`（**core とは別モジュール**。core に入れると全利用者が prometheus クライアントの依存を抱える）に置き、使ってよいのは各サービスの合成ルートのみ。`/metrics` は契約・認証の面と混ぜず**専用ポート**（`METRICS_ADDR`。未設定なら出さない）。観測スタックは `mise run obs:up`（prometheus + grafana、ダッシュボード `昇格シグナル` は git 管理でレビューに載せる）。

| シグナル | メトリクス | 何の合図か |
|---|---|---|
| プール使用率 | `db_pool_in_use / open / max / wait_total` | 接続の飽和 → インスタンス分離・プール見直し |
| authz レイテンシ | `http_server_request_duration_seconds`（authz） | 認可の往復が高い → キャッシュ・配置の見直し |
| outbox 滞留 | `outbox_pending` / `outbox_oldest_age_seconds` | relay が追いつかない → 配送の並列化・バス見直し |

SQL 由来の gauge は「読めない」を **-1** で返す（0=滞留なし と 欠測 を混同しない。fail open にしない）。

### 10.3 CI/CD・リリース方式（一部確定）

リリース方式の確定部分: デプロイ（コードを置く）とリリース（ユーザーに見せる）の分離を原則とし、DBのexpandはトラフィック切り替え前、contractは後続リリースで実行する（internal/05）。トラフィック切り替えは**ECSネイティブのBlue/Green・カナリア機能**を使う（CodeDeployは不要になったため使わない）。デプロイの巻き戻し（ECS `stopDeployment`。実測32秒で本番復帰）とリリースの巻き戻し（フィーチャーフラグ、internal/08）は独立した2本のレバーとして扱う。Kayenta（ベースラインとの統計比較）は単独導入の選択肢ではなくなっており（Spinnakerの一部としてのみ現存）採用しない。統計比較が必要になった場合はECSのライフサイクルフックで比較ロジックを自作する。

**既定形は1本: expand 先行 + ゲート付き Blue/Green**（7.2 / 7.2b の実測で確定。verification-log 2026-09-30）。ゲートは `POST_TEST_TRAFFIC_SHIFT` のライフサイクルフックで、テストトラフィック経由の検証を **healthz でなく業務の書き込みまで**通す（healthz は「壊れた版」でも緑を返す。実測: 書き込み検証のゲートで被弾 0/1,679、ゲート無しのカナリア+アラームで 69/2,880）。ゲートは全サービス常設とし、「付けるか」の判断自体を設けない。切り替え中も bake 中もマネージドの閾値アラームで自動ロールバックさせる。ゲートのテスト書き込みは **create で止めて commit しない**——残る pending_upload の行は回収ジョブ（check #28）の対象に収まる。この整合は偶然でなく制約であり、フックを commit まで深くするなら合成テナント隔離か後片付けを先に設計する。テスト主体は専用の合成 subject で発行し、テスト起因を識別可能に保つ（#199）。

**カナリアはデプロイごとの選択肢ではなく、サービスの属性**とする。CANARY へ格上げするのは「実トラフィックでしか出ない壊れ方」（性能・実データ依存・キャッシュ挙動）を持つサービスだけで、IaC のサービス定義に固定し、判定理由は Atomic 判定と同じく**その行のコメント**に書く。変更はインフラ PR + レビュー。これにより判断の頻度は「デプロイごと」から「サービスの性格が変わったとき」へ落ちる。なお機能の段階公開はデプロイのカナリアでやらない——それはリリース側のレバー（フラグ）の仕事で、混ぜると2本のレバーが崩れる。

判断の軸は格上げだけでなく**格下げ**（容量）もある（#201）。B/G 既定は**切り替え中にタスク数が2倍**で走ることを前提にしており、このヘッドルームを確保できないサービスはローリングへ格下げする、という判断が本番規模では出てくる。格上げ（実トラフィック依存の failure mode）と格下げ（デプロイ中 2x を許容できない容量制約）は独立した軸なので、IaC 行コメントの判断理由はどちらの語彙でも書けるようにしておく。

**普通の開発者はデプロイについて何も選ばない。** やることはコードと expand マイグレーションを書いて PR を出すだけ。遭遇するのは（1）INSTANT で通らない DDL を CI が止めて例外プロセス（gh-ost / 保守時間。所要見積もりは Aurora fast clone のリハーサルで取る）を案内する、（2）ゲートが落とした通知（テストトラフィックでの失敗内容付き）を受けて直す、の2つで、どちらも判断ではなく手順である。判断が要る場面（カナリア組への出し入れ・COPY 系 DDL の計画）はプラットフォーム側の低頻度案件に寄せる。

### 10.8 ヘルスチェックとグレースフルシャットダウン（3リスナー+relayの排水順序）

停止は SIGTERM を合図とする**排水**であり、順序は役割で決まる（#222。実測: `dev/scripts/shutdown-drill.sh`、verification-log 2026-09-30-stage-drain）。

**serve（3リスナー）**: 新規受付を止め、処理中のリクエストを待ってから **DB を閉じる**（処理中のクエリを道連れにしない）。上限は `SHUTDOWN_TIMEOUT_SECONDS`（既定25秒。ECS の stopTimeout 30秒から SIGKILL までの猶予に収める）。排水しきれなかった＝処理中の接続を切った、は**黙らせず警告に出す**。メトリクスの `/metrics` はリスナーの排水後に止める——停止中の観測が先に消えると、排水の失敗がどこにも出ない。実測: コミット直前で3秒待つ処理中リクエスト8本が SIGTERM 後に全部 201 で完走（SIGKILL では 8/8 切断）。

**relay / consumer**: 停止指示が来ても**処理中のバッチ・受信済みメッセージは完走させる**（上限 `DrainTimeout`、既定20秒）。途中で切ると「送れたのに記録できない」「処理したのに削除できない」が起こり、**自作の再配信＝避けられる重複**を生む（inbox が吸収するとはいえ、停止のたびに重複を作る運用にしない）。relay は停止時に未送信の残数をログへ記録する（`relay: 排水して停止 unsent=N`。残作業を停止のたびに観測可能にする）。実測: 150件中バッチ途中の SIGTERM で送信100＋未送信50の帳尻一致、context canceled ゼロ、全量ドレイン後の inbox 150件・重複スキップ0。

**正常な停止は exit 0**。SIGTERM での終了を異常扱いして exit 1 にしない（ECS のタスク停止が毎回「異常終了」として記録されるのを防ぐ）。

ヘルスチェックの使い分けは既存の実測どおり: `/healthz` は「生きている」しか言えず（fail open 事例3）、デプロイの成否は業務の書き込みまで通す昇格ゲートで判定する（§10.3）。排水中に `/healthz` を落として LB からの切り離しを早める最適化は、ECS では deregistration が SIGTERM に先行するため今は入れない（入れる場合は根拠の実測から）。

### 10.9 依存更新と脆弱性通知の運用（確定）

依存の脆弱性対応は「見つける」（govulncheck、PR ごと + 日次。#180）と「常に新しく保つ」（Dependabot weekly、`.github/dependabot.yml`。#181）の2系統で回す。gomod は全モジュールを `directories` でまとめて**1本の grouped PR** にする——片側のモジュールだけ版が上がると共有依存のドリフト（`lint:drift` が観測）になるため、同時に上げる形が構造的に正しい。major だけは group から外れて個別 PR になる。

**Dependabot alerts と govulncheck の判定が食い違ったら govulncheck を採る。** alerts は依存グラフだけを見て到達性を見ないため、呼ばれないコードパスの CVE も鳴らす。その alert は「govulncheck で到達不能」と理由を書いて Dismiss する（黙って消さない——理由の無い Dismiss は次に見た人が再調査する）。逆に govulncheck だけが鳴るケース（Go toolchain 自体の CVE）は依存でなく mise.toml の go を上げる。

Dependabot PR の自動マージは**まだ有効にしない**。自動マージの前提は「壊れた更新でテストが本当に落ちること」で、認可の総当たりテスト（#182）が入るまでは、検査ではなく自動デプロイの穴になる。有効化するとしても patch のみ・minor 以上は人間が読む。
