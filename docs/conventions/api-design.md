## 3. API方式

### 3.1 外部公開API

フレームワークはEchoを使用し、その上にhuma v2を載せる（`humaecho`アダプタ）。humaを採用する理由は、ハンドラの入出力型からOpenAPIが生成されるため、スペックと実装が構造的に乖離しないことにある。コメントベースの生成（swaggo/swag）は乖離を検出できないため採用しない。

URL設計は厳密なRESTfulを目標としない。読み取りはGET、それ以外はPOSTを基本とし、URLは可読性を優先する。いわゆるpragmatic RESTの立場をとる。

エンドポイントの切り方はCQS（§2.1）をそのまま反映し、コマンドとクエリで規則を分ける。

コマンドはユースケース単位とし、URLは「どの集約か」と「その集約への操作」で構成する（リソース指向RPC。Google AIP-136のカスタムメソッドの系譜）。

```
POST /orders/{id}:cancel      純粋な状態遷移 → :verb
POST /orders/{id}:refund
POST /orders/{id}/shipments   操作が新しい実体（サブEntity・記録）を生む → 名詞のサブリソース
POST /orders                  作成
```

操作が新しい実体を生むなら名詞のサブリソース、実体を生まない純粋な状態遷移なら `:verb` とする。キャンセルを表すリソースを捏造する等、名詞縛りのための無理はしない。汎用更新（`PUT /orders/{id}` にstatusを含む本文を送り、サーバがフィールド差分から遷移を推測する形）は禁止する。汎用更新はEntityの状態遷移メソッド（§2.4）を迂回し、セッターにルールを押し込む劣化を招くためである。コマンドのエンドポイントはusecaseと1対1に対応し、エンドポイント → usecase → Entityのメソッド、が一直線に繋がる状態を保つ。

クエリはRead Model単位（§2.1）とし、GETで提供する。エンドポイントは「どの読む形が要るか」で切り、ユースケースではなく画面・利用側の形に対応させる。GETにすることでキャッシュ・ブックマーク・curlによるデバッグといったHTTPの意味論を活かす（RPCが全てPOSTになることで失う部分をここで回収する）。

```
GET /orders?status=paid&limit=50   一覧のRead Model（ListAccessibleでフィルタ）
GET /orders/{id}                   詳細のRead Model
GET /orders/{id}/timeline          履歴のRead Model
```

サービス間（internal）も同じ規則に従う。加えてhumaの `OperationID` を対応するusecase名と一致させ、`oapi-codegen` が生成するクライアントのメソッド名が呼び先のusecase名と一致するようにする。これによりHTTPの意味論を捨てずに、RPCの「関数呼び出しとして読める」利点を得る。

生成したOpenAPIはCIで `api/<service>/{external,admin,internal}.openapi.json` へ出力してリポジトリにコミットし、スペック変更をPRレビューの対象にする。`api/` はコンテキスト間で共有してよい唯一の契約置き場であり、手書きはしない（契約の源泉は常にhumaの型。§3.3）。あわせて `oasdiff` をCIに入れ、破壊的変更を検知する。

スペックの互換性規約: フィールドの追加は可、削除・意味変更は不可。互換性のない変更はパスバージョンを上げ（`/v1` → `/v2`）、新旧を並行提供して利用側の移行を待つ。oasdiffの破壊的変更検出とクライアントパッケージのメジャーバージョン連動（§3.4）は、この並行提供の開始合図として機能する。

### 3.2 サービス間通信

サービス間もHTTP（JSON）とする。gRPC・Connectは採用しない。サービス間APIはプライベートドメイン（例: `user.internal`）でのみ提供し、外部からはネットワーク的に到達不可能とする。

リスナー（ポート）は呼び出し主体ごとに3系統に分ける。external（:8080、一般ユーザー）、admin（:8082、社内オペレータ。§4.4）、internal（:8081、サービス間）。パスプレフィックスによる分離は、入口の設定ミス一つで別系統のAPIが露出しうるため採らない。`cmd/<service>/main.go` でEchoを3つ起動する。3系統を分ける根拠は呼び出し主体の性質差にある。externalとadminは人間（Authorization Code + PKCE）、internalは機械（client_credentials）であり、要求するAAL・レート制限・監査・到達経路がそれぞれ異なる。

サービス間の契約は次のパイプラインで維持する。内部ハンドラもhumaで実装し、生成されたOpenAPIから `oapi-codegen` で `services/<name>-client` を生成する。利用側usecaseはこのクライアントを直接使わず、必要なメソッドだけを切り出したinterfaceで受け、受け取ったデータは境界で自ドメインの型へ変換してから使う（生成型・相手の型をusecase内部へ持ち込まない。sqlc生成型の非露出と同じ規律）。これによりテスト時のモック差し替えと、将来の通信方式変更の余地を確保する。

呼び出し先URLは環境変数（`USER_SERVICE_URL` 等）で注入する。タイムアウトは呼び出し側で `context.WithTimeout` を用いて設定することを規約とする。

エラー応答はRFC 9457（`application/problem+json`）に統一し、拡張フィールドとして機械可読の `code` を必ず持たせる。HTTPステータスのみに意味を持たせない。humaのエラーモデルはRFC 9457準拠であるため、独自形式を発明せず標準に乗る。

### 3.3 将来のRPC化について

現時点でgRPC移行の予定はないが、上記の「interfaceで受ける」「契約をOpenAPIで明示する」「エラーをコードで構造化する」「タイムアウトをctxで統一する」の4点を守ることで、必要になった場合の移行コスト（proto翻訳と実装差し替え）を局所化してある。

RESTとRPCの決め手は「契約の源泉を1つに保てるか」である。外向けAPIをhuma（コードからOpenAPI生成）で決めた以上、内部だけをproto駆動にすると契約の源泉が2系統になり、型の二重定義・破壊的変更チェックの二重化・CIと生成物の重複が生じる。この重複コストは、現行規模でRPCから得る型安全の利益を上回る。内部REST（`:verb` によるユースケース単位、OperationID = usecase名、生成クライアント）は既にRPCの「関数呼び出しとして読める」利点を得ており、残る差はトランスポート機能（ストリーミング等）と全POST化のみである。

再検討の条件は次のとおり。外向けAPIもproto駆動に統一する判断をした場合。サービス間で連続データを型付きで流すストリーミングが必要になった場合（ブラウザ向けのプッシュはSSEでRESTスタック内に収まり、サービス間の通知はEventualで賄えるため、この条件はサービス間ストリーミングに限定する）。社内サービスの呼び手が多言語化し、SDK生成をprotoで一元化したくなった場合。oapi-codegenの生成クライアントの型忠実度に実害が出た場合。いずれも満たさない間はRESTを維持する。

### 3.4 クライアントの生成と配布

APIクライアントは提供側（各サービスのCI）が生成して配布し、利用側には生成させない。利用側が各自生成すると生成器のバージョン差で型の異なるクライアントが乱立するためである。humaが型から出力するOpenAPIを唯一の入力とする。

スペックはリスナー（§3.2）に対応して3つに分け、それぞれ別のパッケージとして配る。externalクライアントにadminのエンドポイント型が混ざるとフロントエンドのコードに管理APIの存在が漏れるため、リスナーの分離をパッケージ境界でも守る。

```
サービスのCI（提供側）
  huma → openapi.json（external / admin / internal）
    ├─ Go  : oapi-codegen → services/<name>/client（モノレポ内、internal用）
    ├─ TS  : openapi-typescript → @org/<name>-api（external用、private npm）
    ├─ TS  : openapi-typescript → @org/<name>-admin-api（admin用、private npm）
    └─ MCP : adminスペック → cmd/admin-mcp のツール定義（§4.4）
```

TypeScriptの生成器は openapi-typescript（型定義のみ）+ openapi-fetch（薄いランタイム）とする。生成物が型のみであるため差分レビューが容易で、生成器の更新による挙動変化のリスクが小さい。メソッド付きのリッチなクライアントを生成する系（orval、hey-api等）は生成物が大きく、現行規模では採らない。

バージョニングは破壊的変更検出（oasdiff、§3.1）とパッケージのメジャーバージョンを機械的に連動させる。CIでoasdiffが破壊的変更を検出し、かつメジャーバージョンが更新されていなければ失敗させる。非破壊の変更はマイナー/パッチとして自動公開する。利用側はRenovate等で更新を受け、メジャー更新のPRが「対応が必要」の合図となる。

生成される型パッケージ（サービスごと）とは別に、サービスに依存しない共通層 `@org/api-core` を1つ置き、認証周りの定型を集約する。トークンの注入と期限切れ時のrefresh。RFC 9470のステップアップ処理（401の `WWW-Authenticate: ... insufficient_user_authentication` から `acr_values` / `max_age` を読み取り再認可フローへ遷移する。共通層に1回実装すれば全画面がステップアップ対応になる）。コマンド呼び出しへの `Idempotency-Key` 自動付与（UUIDを生成しリトライ時は再利用）。トレースID（`X-Request-Id`）の付与。変更頻度が異なるため、型パッケージと共通層は分離して管理する。

1つのフロントエンドが複数コンテキストを同時に使う場合の合成は、SSR基盤（React Router。検証ビルドでは同リポジトリ `frontend/` に置いてよい）のloaderが担う。loaderが各コンテキストのTSクライアントを並列に呼び、1画面分に合成してHTML / propsとして返す。actionがコマンド（`POST /orders/{id}:cancel` 等）を中継する。サーバー間通信のためCORSは無関係で、ブラウザとの往復は1回に収まる。したがって専用のBFFは立てない。SSRのloaderがBFF相当の役割を既に果たしており、別途集約層を作ると全コンテキストに依存する第2の結合点が生まれ、リリース独立性がそこで詰まるためである。再検討するのはモバイルアプリ等、SSRを経由しないクライアントで往復回数が性能実測で問題化した場合のみとする。

`@org/api-core` はSSRサーバー用とブラウザ用の2つのエントリポイントを持つ。SSR用はセッションからのトークン注入、ステップアップ（401 + `WWW-Authenticate` の insufficient_user_authentication）を受けた際の `acr_values` / `max_age` 付き認可リクエストへのリダイレクト応答への翻訳、`Idempotency-Key` とトレースIDの付与を担う。ブラウザ用は直接経路（§4.3の台帳登録時のみ）向けで、ハンドオフされた短寿命トークンの管理と同等の共通処理を担う。TSパッケージは同リポジトリのpnpm workspace参照とし、npm公開は行わない（バージョンskewが「同一コミット=常に整合」に置き換わる）。

コンテキスト跨ぎの表示にはEventualの窓が画面上で見える（自コンテキストで確定した直後、他コンテキスト由来の表示が数秒古い等）。これはバックエンドで隠さない（§2.2）ため、フロントエンド側の規約として持つ。自コンテキストの書き込み結果はコマンド応答で返して即反映し（read-your-writes）、他コンテキスト由来の表示は窓がある前提でデザインする（確定待ちはpending表示、更新はSSEで補完）。
