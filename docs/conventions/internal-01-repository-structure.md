## 2. リポジトリ構成

モノレポとし、ドメイン（境界づけられたコンテキスト）ごとに縦割りする。デプロイ単位はドメインごとのバイナリである。リポジトリは初日からgo.workによるマルチモジュール構成とする（当初「単一モジュール、go.work不採用」としていた決定は撤回した。理由は§2.0）。

```
.
├── go.work                        # リポジトリ内のモジュールを束ねる。タグ付け不要
├── core/                          # 横断的関心事のみ。軽依存に保つ
│   ├── go.mod
│   ├── authz/                     # 認証・認可の差し込み口（§6）
│   ├── consistency/               # Atomic / Eventual の共通実装（§2.2〜2.3）
│   ├── middleware/
│   ├── httpclient/                # サービス間HTTP基盤（トークン付与・伝播）
│   └── logger/
├── api/                           # 生成されたOpenAPI（唯一の共有契約置き場、手書き禁止）
│   └── order/{external,admin,internal}.openapi.json
├── services/
│   ├── order/
│   │   ├── go.mod                 # 文脈固有の重依存はこのモジュールに閉じる
│   │   ├── cmd/order/main.go      # バイナリもモジュール内（切り出し時に一緒に出る）
│   │   ├── handler/
│   │   │   ├── external/          # 外部公開API（huma、:8080）
│   │   │   ├── admin/             # 社内オペレータ向けAPI（huma、:8082）
│   │   │   └── internal/          # サービス間API（huma、:8081、privateドメインのみ）
│   │   ├── usecase/
│   │   ├── domain/
│   │   ├── repository/
│   │   ├── readmodel/
│   │   └── replicaview/
│   ├── order-client/              # 生成クライアント=契約。依存ほぼゼロ
│   │   └── go.mod
│   └── ...（各サービス同構造）
└── dev/allinone/                  # ローカル開発用: 全サービスを1プロセスで起動（本番不使用）
```

`dev/allinone` は全サービスのリスナーを1プロセスで起動するローカル開発用バイナリである。サービス間通信はこの場合もHTTP（localhostの各ポート）を通し、in-process呼び出しへの近道は作らない。本番はサービスごとの個別デプロイのみとする。

### 2.0 モジュール構成（go.work + マルチモジュール）

モジュールの単位は core / 各サービス / 各サービスのclient（生成契約）とする。この構成が買うものは次のとおり。

第一に、モジュールグラフそのものが依存規律になる。orderのgo.modに他サービスの実装モジュールを書かない限り、その内部はimportしようがなく、境界をコンパイラと`go mod`が守る。他サービスへの依存は `<name>-client`（生成物、依存ほぼゼロ）に対してのみ許可する。depguardの役割はモジュールグラフへ移譲し、core内の細則（`replicaview` のimport制限等）に縮小する。

第二に、依存ライブラリが文脈ごとに分かれる。Goは1モジュール1依存1バージョンであるため、単一モジュールではgo.modが全ドメインの依存の和集合となり、バージョン更新の歩調合わせがチーム数に比例して増える。マルチモジュールでは各go.modがそのコンテキストのSBOMとなり、重いSDK（決済、PDF生成等）はそのサービスに閉じる。coreは軽依存に保ち、go.modのdiffレビューで守る。代償として共有系依存のバージョンドリフトが起きるため、四半期ごとに収斂させる運用予算を持つ。

第三に、切り出しと除却が機械的になる。長期運用では一部ドメインの別リポジトリへの切り出しや除却が想定される。切り出しはモジュールごと移動し、coreに初タグを打ち、消費側はclientモジュールをバージョン参照に切り替えるだけで、依存の考古学が発生しない。除却はgo.workから外した時点で残存参照がコンパイルエラーになり、「削除がKPI」（§8.4）と噛み合う。マルチリポ化自体は、切り出す価値が確定したモジュールに限る条件付きの先送りとし、移行期間中は横断変更をアトミックに行えるモノレポを維持する。

初日からマルチモジュールにする根拠は、変更コストの時間非対称性である。モジュール分割の作業量は依存の絡まり（コード量）に比例して増え、CI/CDパイプラインは最初の構成に合わせて硬化するため、後でやるほど高くつく。一方go.work内のモジュール再編（境界の引き直し）は同一リポジトリ内の1PRで済み、安い。「先送りしてよいのは、待つほど安くなる変更（DB物理分離）か、可逆な変更だけ」であり、モジュール分割はどちらでもない。運用は、ローカルとリポジトリ内ビルドをgo.workで束ね、CIは各モジュールを単体でビルドしてgo.modの自己完結性を毎回検証し、モジュールがリポジトリ外から消費されるまでタグは打たない。新サービスのボイラープレート増はscaffoldスクリプトで吸収する。

依存の規律として、`services/A` から `services/B` の内部（usecase・repository・domain）をimportすることを禁止する。他サービスのデータが必要な場合は `services/B-client` 経由のHTTP呼び出しで取得する。この制約はモジュールグラフで強制し、モジュール内の細則を `go-arch-lint` または `depguard` でCIにおいて機械的に強制する。

別ドメインへのアクセスは読み書きを問わずHTTP（そのサービスの公開API）経由のみとし、これを規約ではなく構造で強制する。強制は3層で行う。第一にコード層: 上記のimport lint。第二にDB層: 各サービスは専用のDBロールで接続し、自ドメインのスキーマ・テーブルにのみGRANTする。他ドメインのテーブルにはSELECT権限すら持たせず、規約をすり抜けたクエリは実行時に権限エラーで失敗する。第三にクエリ層: 各サービスの `sqlc.yaml` は自ドメインのスキーマ定義とクエリファイルのみを入力とし、他ドメインのテーブルを参照するクエリはコード生成の時点で失敗する。加えてCIでクエリ内のテーブル名を許可リストと照合する。

「読むだけ」の直接参照も認めない。読み取りであっても相手のスキーマに結合し、相手のカラム変更で壊れ、将来のDB分離を不可能にするためである。他ドメインのデータを高頻度・低遅延で参照する必要がある場合は、HTTPで取得するか、ReplicaView（後述）を持つ。相手のテーブルへの直接参照はゼロを原則とする。

**ReplicaView（他ドメインデータの読み取り専用の複製）**。他ドメインの公開データをイベント購読により自ドメインのDBへ複製したものをReplicaViewと呼び、Read Model（§2.1）とは区別する。Read Modelは自ドメインの正から組み立てた読むための形であり、ReplicaViewは正が相手にある読み取り専用の複製である。性質が異なるものに同じ名前を与えると、いつか複製で業務判断を書く者が現れるため、名前とパッケージ（`readmodel/` と `replicaview/`）を分け、Entityおよびusecaseの業務判断から `replicaview` パッケージをimportできないことをlintで強制する。

ReplicaViewの規約は3つ。第一に、業務判断に使わない。ReplicaViewは古い可能性があり、表示専用とする。判断が必要な場合はHTTPで相手に問い合わせるか、pending状態パターン（§2.2）で相手に確定させる。第二に、持つフィールドは表示に必要な最小限とし、相手のテーブルを丸ごと写さない。依存してよいのは相手が公開すると決めたイベントの契約であり、相手のテーブル構造ではない。第三に、整合性クラスはEventualであり、§2.3の冪等性・順序・再試行の規約がそのまま適用される。窓（反映遅延）が許容できない表示にはReplicaViewを使わず、HTTPで都度取得する。

他ドメインのデータを表示に要する場合の選択は、既定をHTTP取得（Batch取得APIを含む）とし、ReplicaViewを選ぶのは次の2場面に限る。一覧の行ごとに相手を呼ぶ形（HTTP越しのN+1）が避けられない場面、および相手の停止中も自ドメインの表示を維持する可用性分離が要件となった場面である。現行規模（§11）では大半がHTTP取得で足りる。独立性を最優先して既定を写し側に寄せる考え方もあるが、写しはドメインごとに結果整合の窓・購読・初期構築の維持費を発生させるため、本設計では要件が観測されてからの昇格とする。

DBは単一Postgresクラスタから始め、サービスごとのスキーマ + DBロール分離を初日から適用する。サービス間をJOINで跨がない。検証ビルドの規模では物理分離（クラスタ分割）は行わず、分離の実効性はGRANTとlintで担保する。
