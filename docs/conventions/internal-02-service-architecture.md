### 2.1 サービス内部構造

各サービス内部のアプリケーションアーキテクチャは次のとおり。

```
HTTP Request
  ↓ Request DTO / 入力検証（huma の入力型がこれを兼ねる）
UseCase（トランザクション境界）
  ↓ Domain Entity / Value Object
Repository interface（usecase/domain 側に定義）
  ↓ sqlc による Repository 実装（infrastructure 側）
Database
```

DBアクセスにはsqlcを使用する。sqlcが生成した型はRepository実装の内部に閉じ、ドメインEntityや外部APIへ露出させない。形式的な入力検証はhumaの入力型（Request DTO）が担い、業務上の不変条件・状態遷移はEntity / Value Objectが保証する。

コマンドとクエリはメソッド・経路レベルで分離する（CQS）。更新系（コマンド）はEntity + Repositoryを経由し、参照系（クエリ）はドメインEntityを復元せず、sqlcの参照用クエリからRead Model / Response DTOを直接組み立てる。クエリは状態を変更せず、トランザクション（§2.2のDo）も通らない。業務上の不変条件を持たない単純CRUDでは、UseCase + sqlcのみの構成を許容し、複雑さが生じた段階でEntityへ切り出す。

システム全体の方針としてのCQRS（読み書きのモデル・ストア分離、非同期投影）は採用しない。ただしCQRS化はサービス（ドメイン）内部の実装戦略であり外部のAPI契約に影響しないため、複雑な状態を持つドメインに限り、そのサービス単位で段階的に導入してよい。段階は次のとおりとし、飛び級はしない。

```
レベル0:   CQS（全サービスの既定）
レベル0.5: DBの機能で解決する
           インデックス・クエリ改善、リードレプリカへの参照系の逃がし、キャッシュ。
           Read Modelテーブルを作る前に必ずここを試す。追加の設計概念なし
レベル1:   Read Modelテーブルの同期更新
           表示用の形を専用テーブルに持ち、更新系usecaseが同一tx内で書く。
           結果整合なし、追加インフラなし
レベル2:   非同期投影
           Outbox（§2.3）へイベントを書き、relayがRead Modelを更新する。
           Outboxの冪等性・順序の規約がそのまま適用される。結果整合の代償を払う
レベル3:   イベントソーシング（現時点で採用予定なし）
```

参照性能の問題の大半はレベル0.5で解決する。レベル1以上はRDBの機能（JOIN・集計・レプリケーション）で解決できないことが実測で確認されてから検討する。CQRSはRDBシャーディングの自前実装になりがちであり、DBが既に提供する手段を先に使い切る。

昇格の判断基準: 状態遷移が多く履歴・監査が業務要件になる、参照のJOINが深く一覧性能が劣化する、読み書きの負荷特性が大きく乖離する、のいずれかが実測で確認された場合のみ昇格を検討する。基準を満たさないうちの先行導入は過剰設計として行わない。

トランザクションはRepository内部で個別に開始せず、UseCase単位で管理する。1ユースケースから複数Repositoryを呼ぶ場合も同一トランザクションに参加させる。認可の関係タプル書き込み（§6.2）もこの境界の中に位置づける。具体的な実装規約は§2.2に定める。

### 2.4 ドメインモデルの規約

**Entityの位置づけ**。Entityは、業務概念のモデルをメモリ上のオブジェクトとして実装したものである。DBの行そのものではなく、Repositoryが行から一時的に復元し、usecaseがメソッドを呼んで状態を変え、Repositoryが行へ書き戻す。この復元→操作→保存のサイクルの間だけ存在する。ActiveRecord系ORMの「オブジェクト＝行」という同一視を持ち込まないこと。この位置づけから次の3規約が導かれる。

第一に、同一性はIDで判定する。FindByIDを2回呼べば別のオブジェクトが2つ生じるが業務上は同一であり、比較はIDで行う。Value Object（Money等）はIDを持たず内容で等価判定する。第二に、Entityは1ユースケース呼び出しの中でのみ生き、キャッシュ・共有・長期保持をしない。長生きしたEntityはDBの行と乖離した状態で判断を下す。第三に、Entityのルールはアプリ経路でしか実行されないため、Entityを経由しない書き込み（直接UPDATE、バッチ、他システム）をすり抜ける。破られたら困る制約（一意性、参照整合性、非負）はDB制約にも置く。Entityは防御の一層であり最後の砦ではない。

**Entityに置くもの・置かないもの**。リッチさは量ではなく種類で決まる。Entityに置くのは「誰が呼んでも成り立っていなければならないこと」、すなわち不変条件と状態遷移のみである。呼び出し元によらず守られるべきルールは、呼び出し元に置くと呼び出し元の数だけ複製されるため、Entityに集約する。値レベルの制約（金額非負、形式）はValue Objectへ置き、それを使う全Entityが自動的に守られる形にする。

Entityに置かないものは次のとおり。IOと永続化（save、通知、Repositoryの呼び出し）。オーケストレーション（複数の操作の手順。手順はユースケースごとに異なるがルールはユースケースを跨いで同じ、という非対称が層の境界である）。他集約の中身（持つのはIDまで。他集約の情報を要する判断はusecaseが双方を取得して渡すか、Domain Serviceへ切り出す）。表示の都合（ラベル、フォーマット。Read Model / DTOの仕事）。単なるgetter/setter（フィールド公開で足りる）。なんでもEntityに寄せると他集約参照・Repository保持・通知発火を抱えた神クラスになり、名前だけ変わったActiveRecordに戻る。

本設計では形式検証をhumaの入力型、表示を参照系のRead Model、手順とIOをusecaseが担うため、Entityの守備範囲は不変条件と状態遷移に絞られる。Entityが小さいのは貧血ではなく純度が高い状態である。判断に迷った場合の問いは「このロジックを削除したらデータが壊れる（不整合になる）か、手順が変わるだけか」。壊れるならEntity、手順が変わるだけならusecase、壊れるが他集約の情報を要するならDomain Service。

**トランザクションスクリプト化の検出基準**。§2.1の免除規定（単純CRUDはUseCase + sqlcでよい）により、放置すると全てが免除側へ流れる。トランザクションスクリプト自体は許容しているため、問題は意図せずそうなってルールが散らばることであり、検出基準を次のとおり定める。同一フィールドに対する条件分岐が2つ以上のusecaseに現れた時点で、そのフィールドの遷移ルールをEntityへ移す。`Atomic.Do` のfn内に業務判断（状態の条件分岐）が現れた場合、fnの中はDB操作の場所でありルールの置き場所ではないため、レビューで移動先を問う。別ドメインとの連携でpending状態（§2.2）を要するユースケースは、状態遷移を型で表現する必要があるため、必然的にEntityを持つ。
