**背景（2015年以降の潮流）**。デプロイは「コードを置く（deploy）」と「ユーザーに見せる（release）」の分離が一貫したテーマであり、トラフィック分割と自動判定はクラウドの標準機能になった。マイグレーションは外部ツール（gh-ost等）→ DBエンジン自体のオンライン/INSTANT化 → 旧新スキーマの並行提供へと進み、「マイグレーションのツール」は軽くなり続けているが「マイグレーションの設計」は要る。本書はその設計を定める。ツールの選定は既定を1つ持ちつつ、代替はオプションとして検証ビルド（greenfield）で評価し、採用はADRで確定する。

**DBエンジン**。MySQL 8（本番はAurora MySQL）で確定。プロダクション（Yii既存DBがMySQL）と同一エンジンで検証するため。これに伴う表記: 本書で「スキーマ」はMySQLのdatabaseを指す（サービスごとに専用database + 専用ユーザー、database単位のGRANT）。オンラインDDLは `ALGORITHM=INSTANT` を第一候補、不可なら `ALGORITHM=INPLACE, LOCK=NONE` を明示し、どちらも通らない変更は「例外」（後述）として個別計画する。

**ツール**。既定は golang-migrate（番号式のup/down SQLファイル）を使用する（プロダクション版と同一の既定。差分を作らない）。宣言的ツール（Atlas、sqldef）を宣言的スキーマ管理としては採らない理由: expand/contract（後述）を規約とした時点でマイグレーションは「機械生成できる差分」ではなく「リリースを跨ぐ手順の設計」であり、宣言的ツールの主要な利点が使えない。

**ツールのオプション（本検証ビルドの評価対象そのもの。結果をADR草案としてプロダクションへ還流）**: 実行系の代替として goose（expand/contractの履歴テーブル分離が素直、Goマイグレーション対応）。lintとして Atlas Community版（2025年10月からlint機能は有料化、Community版は無料である点に注意）または Bytebase。INSTANT/INPLACEで捌けない巨大ALTERのfallbackとして gh-ost / pt-online-schema-change（INSTANT DDLの普及で出番は減ったが、行の再構築を伴う変更には残る）。破壊的変更の警告は、オプション採用までは自前チェック（DROP / 型変更を含むupファイルのCI警告）で足りる。PostgreSQL専用のsquawk・pgrollは本番では対象外。

**expand / contract の二系統運用**。マイグレーションを追加系（expand）と削除・変更系（contract）に分離し、ディレクトリと履歴テーブルを分ける。

```
services/order/migrations/
├── expand/     # 追加系のみ: ADD COLUMN(NULL可/DEFAULT)、CREATE TABLE、CREATE INDEX
└── contract/   # 削除・変更系: DROP COLUMN、NOT NULL化、型変更
```

expandは機能リリースに同梱し、トラフィック切り替え前（デプロイ前ステップ）に実行する。contractはキューに積み、次回以降の通常リリースで実行する。contract実行の前提条件は2つ: 対象カラム・テーブルへの参照がコードから消えていることをsqlcの再生成で機械確認する（参照が残っていればsqlcのコンパイルが落ちる。これがContractの安全確認）こと、および対応するReleaseフラグ（internal/08）が削除済みであること。この運用により**マイグレーション専用リリースを廃止**し、常に「アプリをロールバックしてもDBは戻さなくてよい」状態を保つ。downファイルは形式上維持するが本番では使用せず、前方修正で対応する。

改名の手順はフィーチャーフラグ（internal/08）と組み合わせて次のとおりとする。リリースN: expandで新カラム追加 + コードは二重書き + 読みは `release.` フラグで旧/新を切替（既定OFF=旧）。バックフィルはリリースに同梱せず**バックグラウンドジョブ**として流す（バッチ分割・冪等・進捗記録。デプロイ前ステップに長時間処理を置かない）。バックフィル完了後、フラグを段階展開して読みを新カラムへ移す。問題があればフラグOFFで即座に旧経路へ戻る（再デプロイ不要）。100%で安定したらフラグと旧読み経路を削除し、contractキューから旧カラムをDROPする。デプロイとしては実質「N + 削除」の2回で済む。

**実行**。アプリ起動時の自動適用は行わない。CDパイプラインのデプロイ前ステップとしてECSで専用タスクをrun-taskし、expandを適用してからサービスのデプロイを開始する。適用時は `lock_wait_timeout`（メタデータロック）と `innodb_lock_wait_timeout` を短く設定（数秒）し、失敗時はリトライする。INSTANT DDLで重いALTER自体は減ったが、**ロック待ちの行列に後続クエリが詰まる事故**は残るため、タイムアウトで自ら退く側に倒す。大きいテーブルのALTERはstgで所要時間とアルゴリズム（INSTANTで通るか）を確認してから本番適用する。

**例外**。巨大テーブルの型変更（行再構築を伴うもの）とDBメジャーバージョンアップは、expand/contractの枠外の個別計画とする（Aurora Blue/Green Deployment、またはgh-ost系の適用）。

**sqlcとの整合**。sqlcの入力スキーマは手書きで維持せず、CIでマイグレーション（expand + contractキュー適用後の姿）を空DBへ全適用した結果（`mysqldump --no-data`）とsqlc入力の一致を検証する。マイグレーションとsqlc入力の乖離を構造的に検出する（humaのOpenAPI差分チェックと同じ発想）。

**環境フロー**。dev（自由）→ CI（空DB全適用 + スキーマ一致検証 + 破壊的変更lint + テーブル許可リスト照合）→ stg（本番相当データでのリハーサルとALTERアルゴリズム・所要時間確認）→ prod。

### モジュール単位の運用（go.work構成との整合）

マイグレーションの所有・適用単位はサービスモジュールとする。`services/<name>/migrations/{expand,contract}/` はモジュール内にあり、`go:embed` でバイナリへ同梱し、サービスバイナリのサブコマンド（`<name> migrate expand | contract | status`）として実行する。CDのデプロイ前ステップが叩くのはexpandサブコマンドであり、contractはキュー消化として明示実行する。マイグレーション履歴と実行手段がモジュールに随伴するため、切り出し（別リポジトリ化）時にリポジトリ外の状態を持たない。

**database を跨ぐ外部キーは張らない（CIで機械的に止める）**。MySQL は `REFERENCES other_db.tbl(id)` をエラーにも警告にもしないが、跨ぐFKが1本あると親テーブルのDDLが子テーブルのメタデータロックを取るため、**他サービスのデプロイが `ERROR 1205 Lock wait timeout exceeded` で落ちる**（実測: MySQL 8.4。親の重いDDL中に子へDDLで1205、子へのINSERTは成功。つまり壊れるのはデプロイだけで日常の読み書きでは気づけない）。これは下段の「モジュール間のマイグレーションは完全に独立並行できる」という主張の前提条件そのものであり、文章だけの禁止では1行で静かに破られるため `mise run fk:check`（`information_schema.key_column_usage`）をCIに置く。同一database内のFKは集約内の不変条件として正当なので止めない。他ドメインの参照は**IDを値として持つ**に留め、存在保証が要るなら `<name>-client` 経由のHTTPかReplicaView、即時の整合が要るなら pending 状態 + 同期コマンド + 冪等キー（internal-03）で解く。

バージョン管理テーブルはモジュール×系統ごとに分離する（サービスdatabase内に `<name>_migrations_expand` / `<name>_migrations_contract`）。共有DB期間に複数モジュールの履歴が衝突しないための必須設定であり、これによりモジュール間のマイグレーションは完全に独立並行できる。順序調整は不要である（サービス間に影響する変更はスキーマではなくAPI契約として現れ、oasdiff + クライアントバージョンの経路で管理される）。

CIの検証（空DB全適用 + mysqldump一致 + 破壊的変更lint + テーブル許可リスト照合）はモジュール単位のジョブとして実行し、差分ビルドと同じ粒度に揃える。

core標準テーブル（outbox / inbox / pending回収対象等）の扱い: 物理テーブルはサービスごとに持ち、共有しない。`core/consistency` はDDLテンプレートを保持し、scaffoldが新サービスの初期expandマイグレーションへ複写する。テンプレート更新時は各サービスが追随マイグレーションを取り込む。歩調は緩くてよく、下限は「coreが要求する必須カラム集合」とのCIスキーマ検証で守る。

モジュールのマイグレーションに入れないもの: CREATE DATABASE / ユーザー・権限の作成。これらはDBレベルの操作としてplatform運用（IaC + 手順書）が持ち、サービスのマイグレーションユーザーには自database内のDDLのみを許可する。
