### 2.2 整合性クラスとトランザクション管理

外部（自DB以外）への書き込みは、その処理が求める整合性によって3クラスに分類し、クラス名をそのままコード上の語彙にする。UseCaseを書く者が考えるべきは「どの整合性が必要か」であり、トランザクションやOutboxといった実現機構ではないため、interface名は機構ではなく整合性クラスを表す。

```
Atomic:     原子性。全部成功か全部なかったことか。ローカルtxに同期参加
Eventual:   結果整合。遅延は許容するが最終的に必ず届く（at-least-once）
BestEffort: 失敗を握って進む。欠落しても業務が成立する
```

クラスの判定条件は次のとおり。**Atomic**に置けるのは、(1) 導出データ等でズレが即座に業務を壊す、(2) 相手が管理下にあり短いタイムアウトを付与できる、(3) 逆方向の不整合（外部側だけ残る）が無害、の3条件をすべて満たす書き込みのみ。関係タプル書き込み（§6.2）はこの適用第一号である。外部SaaSは条件(2)を決して満たさないためAtomicに置けない。

**オブジェクトストレージ（S3等）も条件(2)を満たさない。** 自アカウントのバケットは「管理下」に見えるが、可用性とレイテンシは自DBと独立であり、`SELECT ... FOR UPDATE` の行ロックとDB接続を握ったまま応答を待つことになる。読み取り（`HeadObject`）もこれに含まれる——書き込みでなければ安全、ではない。実際に監査 C-1（Issue #85）で、`CommitUpload` が tx 内で `HeadObject` を呼んでいる形が見つかった。**外部呼び出しはアダプタ側で短いタイムアウト（現状3秒）を必ず付ける**: 呼び出し側に任せると、リクエスト経路にタイムアウトが1つも無い状態が普通に成立する（これも同じ監査で見つかった）。

**Atomic判定の記録場所は、その `Atomic.Do` を書いた関数のコメントとする。** 別の台帳を作ると更新されずに腐る。判定を書く相手は「次にこの tx へ1行足そうとする人」であり、その人が読むのはコードだから。3条件のどれが効いて外に出したか（あるいは満たすから中に置けるか）を1〜2行で残す。**Eventual**は通知・他サービスへのイベント・分析連携・キャッシュ無効化など、ズレの窓が許容されるが到達は必要なもの（既定のクラス。標準実装は§2.3のOutbox）。**BestEffort**は行動ログ・メトリクス等。Atomicへの追加はtxを遅く脆くするため、新たな書き込みは既定でEventualとし、Atomic判定は3条件の充足をユースケースごとに記録した上で行う。

各クラスが保証する整合性の正確な意味は次のとおり。**Atomic**は原子性: 対象の書き込み群は、どの時点で観測しても全部あるか全部ないかのいずれかであり、中間状態が観測される時間が存在しない。失敗は全体の巻き戻しで扱うため、成功後の取り消しを考えなくてよい。**Eventual**は到達保証つきの結果整合: 最終的に必ず揃うこと（at-least-once）を保証するが、揃うまでの窓の間はズレが観測されうる。窓は許すが欠落は許さない点でBestEffortより強く、失敗は「なかったことにする」のではなく「成功するまで繰り返す」で扱う。この繰り返しの副作用として重複配送が発生するため、受信側の冪等性（§2.3）は保証の一部である。**BestEffort**は保証なしの一回試行であり、整合性が弱いのではなく「揃うべき相手が存在しないデータ」と判定したことの宣言である。

| クラス | 中間状態の観測 | 失敗時の扱い | 重複 | 支払う代金 |
|---|---|---|---|---|
| Atomic | されない | 全て巻き戻す | なし | ロック保持・相手との可用性結合 |
| Eventual | される（窓） | 成功まで再送 | あり（受信側で吸収） | 窓の設計・冪等性の実装 |
| BestEffort | ずっとズレうる | ログに残して忘れる | 問わない | 欠落の観測手段がなければ気づけない |

判定に迷った場合は次の2問に答える。第一に「ズレた瞬間を誰かに観測されたら業務が壊れるか」——壊れるならAtomic候補（その上で3条件を審査）、壊れないなら次へ。第二に「失敗したとき、なかったことにしたいのか、いつか必ず成功してほしいのか、どうでもよいのか」——順にAtomic・Eventual・BestEffortに対応する。

なお読み取り側の整合性ヒント（§6.2のHIGHER_CONSISTENCY相当）は、この語彙では「Eventualな書き込みの窓の中で、窓の外の最新値を要求する」オプションであり、対価としてレイテンシを払う。書き込みの整合性クラスと読み取りの鮮度要求は対概念であり、書き込みをAtomicからEventualへ降ろす変更（タプルのOutbox化等）は読み取り側の鮮度要求の再検討とセットで行う。

別ドメインの状態を変更させる書き込み（コマンド）には追加の判定が要る。別ドメインの状態変更は相手のトランザクションで起きるため、こちらのロールバックで巻き戻せず、Atomicの条件(3)を構造的に満たさない。したがって別ドメインへのコマンドは常にAtomicの外にあり、次の分岐で扱う。

```
別ドメインの状態を変えたい
 ├ 相手の結果が今の分岐を決める → 同期コマンド + pending状態 + 冪等キー
 └ 起きればよい
    ├ 相手が何をするか知らなくてよい → イベント（Eventual.Publish）… 既定
    └ 特定の相手に確実にやらせる責任がこちらにある → コマンド（Eventual経由）
```

相手の結果が今の分岐を決める場合（与信結果で注文確定が決まる等）は非同期にできない。この場合の定石は、ドメイン間の整合性の窓をインフラで隠蔽せず、ドメインモデルの状態として表に出すことである。すなわち、(1) 自ドメインの状態を「要求中」（例: PaymentPending）としてAtomicで確定し、(2) tx外で同期コマンドを冪等キー付きで発行し、(3) 結果を別のAtomicで反映する（Paid / PaymentFailed）。要求中の状態がDBに刻まれているため、途中でプロセスが停止しても、要求中のまま残ったレコードを回収して相手に冪等キーで照会し確定させるジョブが書ける。これはサーガの最小形をドメインモデルの状態遷移として実現したものである。

起きればよい場合は、コマンドよりイベントを既定とする。コマンド（「課金レコードを作れ」）は送り手が相手の業務を知る必要があり結合が強い。イベント（「注文が確定した」）は事実の公表であり、何をするかは購読側が決めるため、後から別の購読者を追加しても送り手は無変更で済む。コマンドを選ぶのは、送り手がワークフローの責任者であり特定の相手に確実に実行させる必要がある（オーケストレーション）場合に限る。

いずれの枝でも冪等キーは必須である。同期コマンドはリトライで、Eventualはat-least-onceで、どちらも同一要求が相手に複数回届く前提となる。`core/httpclient` の冪等キー付与規約（§9）はこの要件を実装する。

コード上の語彙は次のとおり。

```go
// services/<name>/usecase/consistency.go

// Atomic: 原子性の境界。fn内の操作を1つのトランザクションにまとめる。
// fnがerrorを返せば全ロールバック、nilなら確定。
type Atomic interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}

// Eventual: 結果整合の配送。最終的な到達を保証する（at-least-once）。
// 実装は§2.3のOutboxだが、usecaseの語彙には現れない。
type Eventual interface {
    Publish(ctx context.Context, event Event) error
}

// BestEffort はinterfaceを設けず、命名規約 TryXxx + 失敗時のログで表現する。
```

```go
err := u.atomic.Do(ctx, func(ctx context.Context) error {
    if err := u.orders.Create(ctx, order); err != nil { return err }
    return u.relations.WriteRelations(ctx, tuples) // Atomic判定済み（§6.2）
})
// ...
_ = u.eventual.Publish(ctx, OrderCreatedEvent{...}) // 到達すればよい
u.tryRecordMetrics(ctx, ...)                        // 欠落してもよい
```

この命名により、コードレビューにおいて「なぜこの書き込みがAtomicの中にあるのか」という問いが名前だけで成立し、判定条件（上記3条件）との突き合わせに議論が直結する。

Atomicの実装は次のパターンを全サービス共通の規約とする（従来TxManagerと呼んでいたもの）。infrastructure側の実装は、`Do` でトランザクションを開始し、`*sql.Tx` を非公開キーでctxに埋めてfnへ渡す。各Repositoryは受け取ったctxを覗き、txが存在すれば `sqlc` の `WithTx` で参加し、なければ素のコネクションで実行する。すでにtx中のctxで `Do` が呼ばれた場合は新規開始せず既存txに参加する（ネスト安全）。fnがエラーを返せばロールバック、nilを返せばコミットする。

この構成により、Repositoryインターフェースの署名にtx引数が現れず、UseCaseは `database/sql` に依存せず、テストでは「fnをそのまま実行するだけの偽Atomic」とRepositoryモックによりDBなしでユースケースの分岐を検証できる。txを埋めるctxキーは実装パッケージの非公開型とし、UseCase層から取り出せないことをコンパイラで保証する。

実装上の規約を3点定める。第一に、fnのクロージャ内では必ずfnの引数のctxを使用する（引数名を外側と同じ `ctx` にしてシャドーイングし、外側のctxを参照できなくする。外側のctxを使うとそのRepository呼び出しだけtxに参加しない事故になる）。第二に、参照系（一覧・検索）を `Do` で包まない。第三に、処理の配置は次の区分に従う。

```
Doの前:  他サービスからの読み取り・検証、ドメインオブジェクトの生成
Doの中:  ローカルDB操作 + Atomic判定済みの外部書き込みのみ
Doの後:  Eventual（Publish）と BestEffort（TryXxx）、および補償を伴う直接呼び出し
```

Atomic内の外部通信を判定制にする物理的な理由は、tx中の外部呼び出しがDBのロックとコネクションを保持したまま相手の応答を待つことになり、相手側の遅延が自サービスのコネクションプール枯渇として伝播するためである。Doの後の直接呼び出し（同期HTTP+補償）は、相手の結果が今の分岐を決める同期コマンド（pending状態パターン）に限って用い、「起きればよい」書き込みは最初からEventual（§2.3）で扱う。同期コマンドで補償が2ステップを超えて連鎖する場合は、ユースケースの設計自体を見直す。

### 2.3 Outboxパターン（Eventualの標準実装）

整合性クラスEventual（§2.2）の標準実装を「Outbox + relay + SNS/SQS」とし、最初から導入する。usecaseの語彙は `Eventual.Publish` であり、Outbox・relay・バスは実装詳細としてinfrastructure側に閉じる。直接HTTP呼び出し+補償（§2.2の「Doの後」）はEventualの実装ではなく、相手の結果が今の分岐を決める同期コマンドのための経路と位置づける。

方式は次のとおり。自サービスのDBに `outbox` テーブルを設け、業務データの書き込みと同一トランザクションでイベントレコード（イベント種別・ペイロード・イベントID・集約ID）をINSERTする。これにより「業務データがある ∧ 送信予定がある」か「両方ない」の2状態のみがローカルトランザクションの保証として成立する。実際の送信は relay（ポーリングする常駐処理）が未送信レコードを読み取ってSNSトピックへpublishし、成功したら送信済みを記録する。relayの停止・失敗は未送信レコードがDBに残ることで回復可能である。バスを介する意味は、送り手が受け手を知らずに済むこと（イベントを既定とする§2.2の方針の実現手段）と、受け手を後から追加しても送り手が無変更で済むことにある。

配送手段は次のとおり定める。トピックはSNS、購読は受け手サービスごとのSQS FIFOキューとする（1トピック→複数キューのファンアウト）。SQS FIFOの `MessageGroupId` に集約ID（例: `order:123`）を入れ、同一集約内の順序保証（後述）をバス側でも成立させる。`MessageDeduplicationId` にはイベントIDを入れ、5分窓の重複をバス側でも弾く。SNS/SQSはVPCエンドポイント経由で到達させ、TGWを経由しない。Kinesisは採用しないが、分析基盤への供給や長期保持が必要になった場合はSNSの下流にKinesis Data Firehose等を追加する（送り手は無変更）。自前のMQ（RabbitMQ/ActiveMQ等）は運用対象が増えるため採用しない。

SQSは再生（replay）ができないため、**再生の正はoutboxテーブル**とする。送信済みレコードを一定期間保持し、新しい購読者の初期構築やReplicaView（§2）の作り直しが必要な場合は、outboxから該当期間のイベントを再publishする管理コマンドを用意する。再publishもat-least-onceの一形態であり、受け手の冪等性で吸収する。

Outbox採用時に守るべき性質を次のとおり定める。

配送保証はat-least-onceとする。relayは「送信成功と送信済み記録の間」で停止しうるため、同一イベントが複数回配送されることを前提とする。exactly-onceは目標にしない。

したがって受信側は冪等でなければならない。イベントには送信側が採番する一意のイベントID（UUID）を必ず付与し、受信側は処理済みイベントIDを `inbox` テーブルに永続化して重複を弾く（または処理自体を自然冪等に設計する）。受信処理は「inboxへイベントIDを記録 + 業務処理」を同一トランザクション（Atomic）で行い、その後にSQSメッセージを削除する。削除前に停止すればメッセージは再配信されるが、inboxが弾く。SQSの重複排除は5分窓の補助であり、inboxが主たる防御である。この規約はサービス間APIにも適用し、Outbox経由で呼ばれる内部APIは冪等キー（`Idempotency-Key` ヘッダまたはペイロード内のイベントID）を受け付けるものとする。関係タプル書き込みをOutbox化する場合も同様で、タプルのwrite/deleteは同一タプルへの重複適用が無害（自然冪等）であることをauthzサービス側APIの性質として保証する。

順序は同一集約（同一リソースID）内でのみ保証し、グローバルな順序は保証しない。relayは集約ID単位で直列に送信するか、受信側がイベント内のバージョン番号・タイムスタンプで新旧を判定できるようにする。

送信の再試行は上限付き指数バックオフとし、上限超過したイベントは削除せずエラー状態として残して監視対象とする（失われた通知は障害対応の起点になるため）。送信済みレコードは保持期間を定めて定期削除する。

Eventualの通知はrelay周期+バス配送分の遅延を持つ（結果整合）。関係タプル書き込みは当面Atomic（同期）であり、Outbox化する場合は差し込み口（RelationWriter）の実装差し替えで行い、UseCaseのコードへ波及させない。その際は「作成直後の短時間、タプル未反映」の窓が生じるため、§6.2の整合性ヒントおよびUI側の考慮とあわせて判断する。
