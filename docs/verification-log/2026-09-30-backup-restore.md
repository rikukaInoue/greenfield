# [8.4] バックアップ→リストアを実際にやる: RPO/RTO の実測（#225 / gap-14）

apply→destroy 運用のため「バックアップは存在しない」状態だった。規約を宣言から
書くのではなく、使い捨てスタック（#219 と同一。RDS MySQL 8.4.6 Multi-AZ
db.t4g.micro、データ 16.7M 行 + プローブ 1,318 行）で**復元まで実際にやり**、
RPO/RTO を実測値から逆算する。

## 実測（2026-09-30）

| 工程 | 実測 |
|---|---|
| PITR の最新復元可能時刻の遅れ（= RPO 上限の実測） | **251 秒** |
| 手動スナップショット作成 | 454 秒 |
| スナップショットから新インスタンスが available まで | **396 秒** |
| PITR（use-latest-restorable-time）で available まで | **577 秒** |

**検算**: 元・スナップショット復元・PITR 復元の3台に同じ照合を流し、
`probe.beats` 1,318 行 / `ddl_lab.photos_like` 16,777,216 行 / `CHECKSUM TABLE`
2413627980 / CHECK 制約 1 件——**3台とも完全一致**。復元は「available になった」では
なく「中身が一致した」まで確かめて初めて完了と数える。

注意: available 直後の復元インスタンスは EBS の lazy load で最初のフルスキャンが
遅い（初回 CHECKSUM がウォームアップを兼ねた）。RTO に「復元後の性能回復」を
含めるかは要件次第だが、含めないなら明記が要る。

## 規約（この実測から逆算した宣言）

- **RPO**: 自動バックアップ + PITR を既定で有効（`backup_retention_period >= 7` を本番の
  既定に。検証スタックは 1）。PITR の遅れは実測 ~5 分——**「RPO ≈ 5 分」までは設定だけで
  買える**。それより短い要求はレプリカ/多重書き込みの設計問題であり、バックアップの仕事ではない
- **RTO**: t4g.micro・20GB で「復元開始→available」が 7〜10 分。**インスタンス再作成を
  含む復元は「分」でなく「十分」のオーダー**として計画する（エンドポイント張り替え・
  ウォームアップは別途）。フェイルオーバー（#219、15 秒）とバックアップ復元（10 分）は
  守る障害クラスが違う——前者は AZ 障害、後者は論理破壊（誤 DDL・誤削除）
- **リストア演習**: 「バックアップがある」は復元して検算するまで主張しない。演習の型は
  このログのとおり（restore → 3点照合 → destroy）で、コストは micro なら数十円
- スナップショットは名前でなく**検算内容**（行数・CHECKSUM）を記録に残す
