## 2026-09-29 — [4.4] 同期コマンド: pending 状態 + 冪等キー + 回収ジョブ（#54 / check #11）

### 作ったもの

- docs/02-architecture.md の同期コマンド仕様の実装。使用機材の紐付けは**相手の結果が
  今の分岐を決める**ため Eventual にできず、Atomic に載せると tx が外部応答を待つ。
  そこで: `GearLinkPending` を業務データと同一 tx で確定 → **tx 外**で
  `POST /items/{id}:link-photo`（Idempotency-Key 付き）→ 結果を**別の Atomic** で
  `GearLinked` / `GearLinkRejected` へ反映
- photo 側: photos に `gear_link_status` / `gear_link_key` 列（INSTANT な列追加）、
  domain の状態遷移（pending → linked / rejected）、`photo reclaim-links`（回収ジョブ）、
  v2 応答に `gear_link_status`
- gear 側: internal API `LinkPhoto` / `GetPhotoLink`、`photo_links` テーブル
  （**冪等キーが主キー**。同じキーの再送には最初の結果を返し、`INSERT IGNORE` で
  上書きしない——リトライのたびに判定し直すと結果が再送タイミング依存になる）。
  **拒否も受理の記録として残す**: 残さないと回収の照会が 404 になり再送が繰り返される
- photo→gear の M2M は `internal:gear` スコープの**専用トークン**（authz 用の
  `internal:platform` と分ける。1トークンに全スコープを盛ると漏洩時の被害が広がる）
- `services/photo/gearlink` — gear-client（生成）を包むアダプタ（4.1 の photocatalog と同じ流儀）
- `dev/scripts/pending-check.sh`（request / settle の2フェーズ）+ CI（authz ジョブ。
  gear 起動**前**に request を置くことで「gear 停止中」を作らずに得る）

### check #11: pending 状態は中断から回復できる（実測）

| 確認 | 結果 |

単体テストで加えて確認: 回収は**同じキー**で再送する（キーが変われば gear 側の
重複排除が効かない）／gear 受理済み・photo 反映前の中断は**照会だけ**で確定し
再紐付けは起きない／確定済みへの二重 settle は無害（`ErrLinkNotPending` → no-op）。

### 気づき

1. **settle は別 tx のフレッシュな行に対して行い、手元のエンティティにも遷移を映す。**
   前者だけだと「DB は確定済みなのに応答は pending」という混乱した応答になる（実測で踏んだ）。
   後者だけだと回収ジョブとの競合で二重確定の余地が生まれる。両方やる
2. **「gear 停止中」は CI では起動順で作れる。** authz ジョブは photo → gear の順に
   起動するので、その間に request フェーズを挟めばプロセスを殺す操作なしで
   停止中の実験ができる。kill を伴う検証は 4.3 で痛い目を見た（孤児・可視性タイムアウト）
3. **署名URLの発行はオフライン計算なので実ストレージ無しで Create が通る。**
   rustfs の無い CI ジョブでも AWS のダミー資格情報さえあれば投稿フローの
   紐付け部分を検査できる
4. **拒否の記録は photo のためにある。** gear が「知らないキー」と「拒否したキー」を
   区別して答えられなければ、photo の回収は「届いていない」と誤解して再送を繰り返す。
   404 の意味を「未受理 = 同じキーで再送してよい」と契約に書いた
