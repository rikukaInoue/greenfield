# 2026-09-30 — [8.4] Multi-AZ フェイルオーバーとバックアップ/リストアを実測（#219 / #225）

RDS Multi-AZ の耐障害性を、**アプリ層・接続層・DDL・バックアップ復元**の4面で実測した。
使い捨てスタック（RDS MySQL 8.4.6 Multi-AZ db.t4g.micro）を立て、`reboot
--force-failover` を複数回撃ち、復元まで実際にやって当日 destroy。費用は合計 $2 未満。

> この検証は2つの独立した実装で回した: アプリ経由の計測は `infra/main.tf`（`multi_az` /
> `backup_retention_days` 変数）、接続層の機構分解と PITR は専用スタック
> `infra/resilience/`（250ms 間隔プローブ + 長時間 DDL）。数字はどちらも同じ結論を指す。

## 面1: アプリ経由（#219）— 障害窓は短く、500 は出ない

photo の投稿/一覧を 0.5 秒間隔で流しながら強制フェイルオーバー:

| 測定 | 結果 |
|---|---|
| 総リクエスト | 395 件 |
| 失敗 | **2 件**（いずれも 8 秒タイムアウト。**500 はゼロ**） |
| 障害窓 | 発行から +14.6s に開始、幅 **8.5 秒**、自動復旧 |

500 が出ずタイムアウトだけで済んだのは、切替中の接続がエラーを返す前にプールが
新しい宛先へ再ダイヤルしたため。ConnMaxLifetime 300s（10.5）はこの動きの前提。
**ただしこの「2件のタイムアウト」の正体は面2 で判明する** —— アプリ側の締め切りが
無ければ、これは2本の永久ハングだった。

## 面2: 接続層（#219）— 最重要は「切断」でなく「凍結」

素の接続層に 250ms 間隔の INSERT プローブ（one-off ECS タスク）を置いて機構を分解した。

**round 1（クライアント側の締め切りなし）: プローブ自体が10分以上ハングした。**
`--connect-timeout=2` は**確立済み**コネクションには効かない。フェイルオーバーの瞬間、
確立済み TCP はエラーを返さずブラックホール化し、MySQL クライアントの read timeout は
既定で無限。**障害はエラーでなく「待ち続けるスレッド」として現れる**。

round 2 以降は呼び出し全体に 3 秒の締め切りを掛けて再計測:

| 観測 | 値 |
|---|---|
| プローブ総数 / ok / err | 1,074 / 1,045 / **29** |
| エラー窓（最初の err → 最後の err） | **11.2 秒** |
| 最長の ok 間隔（実効ダウンタイム） | **14.9 秒** |
| err の内訳 | 28× `ERROR 2003`（即時失敗=リトライ可能）、**1× 凍結**（3秒締め切りが回収） |
| DNS フリップ | failover 指示の約 15 秒後 |
| AWS イベントの「completed」 | 指示から 44 秒後——**アプリは events より 20 秒早く復旧している** |

29 エラーのうち 28 は接続拒否で即時に返る「行儀のよい失敗」。危険なのは残り1つの
凍結で、これは**クライアント側の締め切りでしか救えない**。面1 の「2 件のタイムアウト」が
まさにこれ。

## 面3: DDL 実行中のフェイルオーバー（#219）

16.7M 行への `ADD CHECK ALGORITHM=COPY`（ベースライン 105 秒）の最中に failover:

- **DDL はエラーにならずハングした**（面2 と同じ凍結。900 秒の締め切りが切るまで戻らない）
- 中断後のテーブルは**無傷**: constraint 0 件・行数 16,777,216 のまま（MySQL 8 の
  atomic DDL。中途半端な状態は残らない）
- **再実行は素直に成功**（105 秒）

migrate ジョブに必要なのは複雑な復旧でなく **ジョブ全体の締め切り + 再実行**。整合は
atomic DDL とマイグレーション履歴が持つ。**重要な訂正**: 当初は「migrate 中の
フェイルオーバーは lock_wait_timeout + リトライの受け持ち」と推定していたが、実測では
**lock_wait_timeout は発火しない**——中断の正体はロック待ちでなくネットワークの凍結で、
MySQL のロック機構の外にある。受け皿はジョブレベルの締め切りだけ。

## 面4: バックアップ→リストア（#225）— 復元して検算するまで信じない

apply→destroy 運用のため「バックアップは存在しない」状態だった。使い捨てスタックで
**復元まで実際にやり**、RPO/RTO を実測値から逆算した。

| 工程 | 実測 |
|---|---|
| PITR の最新復元可能時刻の遅れ（= RPO 上限の実測） | **251 秒（~5 分）** |
| 手動スナップショット作成 | 92 秒（20GB）／ 454 秒（直前に 16.7M 行を書いた後） |
| スナップショットから available まで | **396 秒** |
| PITR（use-latest-restorable-time）で available まで | **577 秒** |

スナップショット作成時間の差（92 秒 vs 454 秒）は増分量への従属——「スナップショットは
速い」はデータ変化量次第。

**3台照合**: 元・スナップショット復元・PITR 復元に同じ照合を流し、行数 16,777,216 /
`CHECKSUM TABLE` 2413627980 / CHECK 制約 1 件 / プローブ 1,318 行——**3台とも完全一致**。
さらにスナップショット復元先には**スナップショット後の書き込みが無い**ことも確認
（point-in-time の意味論）。復元は「available になった」でなく「中身が一致した」まで
確かめて完了と数える。注意: available 直後は EBS lazy load で初回フルスキャンが遅い
（RTO に性能回復を含めるかは要件次第、含めないなら明記）。

## 副次の発見

- **Multi-AZ の「変換」（false→true）には接続断の窓がある**（bootstrap が ERROR 2003 →
  変換完了後の再実行で成功）。「Multi-AZ 化は無停止」と思い込みがち。有効化は保守枠で
- **force-failover の開始タイミングは保証されない**: 直前の完了から 4 分未満で撃つと、
  API が `rebooting` を返してから実イベントまで 68 秒の遅延（間隔を置くと 11〜15 秒）。
  ゲームデイで「N 秒後に落ちる」前提は外れる

## 規約への反映（10.5 / internal-05）

- **10.5 の穴を1つ塞いだ**: 規約は HTTP のタイムアウトを定めるが **DB クエリの読み取り
  締め切りが未規定**だった。凍結コネクションは ConnMaxLifetime では救えない（寿命は
  返却時に判定され、ハング中の接続は返却されない）。DSN に `readTimeout`/`writeTimeout`
  を追記
- `ERROR 2003` 系の即時失敗は 10.5 の「リクエスト内で粘らず pending に劣化」がそのまま
  受け止める（15 秒窓の書き込み失敗は relay / 回収ジョブの守備範囲）
- **RPO ≈ 5 分は設定だけで買える**（PITR 遅れの実測）。それより短い要求はレプリカ/
  多重書き込みの設計問題で、バックアップの仕事ではない
- **RTO はインスタンス再作成込みで「分」でなく「十分」のオーダー**（t4g.micro・20GB で
  7〜10 分）。フェイルオーバー（15 秒、AZ 障害向け）とバックアップ復元（10 分、論理破壊
  向け）は守る障害クラスが違う
- **Keycloak / OpenFGA は単一コンテナ = HA なし**でフェイルオーバー訓練の対象外
  （本番は Keycloak ステートレス化 + 外部 DB、OpenFGA 多重化。internal-04 の範囲）
