# 2026-09-30 — [8.4] Multi-AZ フェイルオーバーとバックアップ/リストアを実測（#219 / #225）

環境: 8.1 と同じ使い捨てスタックに `multi_az = true`・`backup_retention_days = 1` を
足して apply → 実測 → 当日 destroy。費用 $1 未満。

## #219: 強制フェイルオーバー中のアプリ挙動

読み(一覧)と書き(投稿)を 0.5 秒間隔で交互に打ちながら
`aws rds reboot-db-instance --force-failover`:

| 測定 | 結果 |
|---|---|
| 総リクエスト | 395 件（うちフェイルオーバー後 332） |
| 失敗 | **2 件**（いずれも 8 秒タイムアウト。**500 はゼロ**） |
| 障害窓 | 発行から +14.6s に開始、幅 **8.5 秒**、自動復旧 |

500 が出ずタイムアウトだけで済んだのは、切替中の接続がエラーを返す前に
プールが新しい宛先へ再ダイヤルしたため。ConnMaxLifetime 300s（10.5）と
プール設定はこの動きの前提で、**「フェイルオーバー時に古い接続を持ち続けない」は
規約でなく実測になった**。migrate 中のフェイルオーバーは lock_wait_timeout +
リトライ（check #19）が受け持ち範囲で、今回の窓 8.5 秒はリトライ間隔（3 秒×3回）に収まる。

### 副次の実測: Multi-AZ「変換」は無停止ではない

`multi_az=false → true` の変換開始直後、DB への新規接続が一時的に拒否された
（bootstrap タスクが ERROR 2003 で失敗 → 変換完了後の再実行で成功）。
「Multi-AZ 化はいつでも無停止でできる」と思い込みがちだが、**変換自体には接続断の
窓がある**。本番で有効化するなら保守枠で。

## #225: バックアップ→リストアの実測（RPO/RTO の材料）

| 区間 | 実測 |
|---|---|
| スナップショット作成（20GB） | **92 秒** |
| スナップショットからリストア（接続可能まで） | **366 秒（約6分）** |
| データの正しさ | 復元先 = **スナップショット時点ちょうど**（197 行。スナップショット後に書いた 5 行は存在しない） |

- 「復元先にスナップショット後の書き込みが無い」ことまで確認して初めて
  **point-in-time の意味論**を検証したことになる（行数一致だけでは足りない）
- RTO の目安 = リストア 6 分 + アプリの DSN 切替（SSM パラメータ更新 + サービス再デプロイ）。
  RPO はスナップショット間隔（自動バックアップ + PITR なら最終リストア可能時刻まで、
  遅延 ~5 分）
- リストア先は Multi-AZ でも公開でもない最小構成で作れる（検証・退避用はこれで足りる）
