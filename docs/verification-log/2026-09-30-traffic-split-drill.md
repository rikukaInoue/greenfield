## 2026-09-30 — トラフィック分割のローカル予行: B/G・カナリア・切り戻し・新旧同時稼働（#172）

2.3/2.4 で実測したのは**順序と並列**まで（release はコンテナ差し替え = 1台ローリング相当）。
トラフィック分割そのものは未実測だったので、7.2（#63、ECS ネイティブ）の前哨として
Caddy の weighted_round_robin でローカル予行した。

### 作ったもの

- `core/httpapi`: 全応答に `X-Service-Revision` ヘッダ（`SERVICE_REVISION` env、
  ECS ではタスク定義リビジョンを入れる想定）。**どちらの版が応答したかを外から
  観測できないと、重み・切替・ロールバックの検証は成立しない**。認証より外に置き、
  401 や healthz にも載る
- `deploy/compose/traffic-drill.yaml`: photo を blue / green の2版で並走 +
  `caddy-drill`（:8088）。重み変更はスクリプトが Caddyfile を生成して `caddy reload`
  （ECS のターゲットグループ重み変更に相当する操作）
- `dev/scripts/traffic-split-drill.sh`: a〜e を一式実行。負荷は既存の `dev/loadgen`
  （エラー1件で exit 1 = 断ゼロの証跡になる）

### 気づき

1. **「どの版が応答したか」は自明ではない。** 同じイメージ・同じバージョン番号の
   2コンテナは応答から区別できない。デプロイ識別子（リビジョン）を応答に載せる
   観測口を先に作らないと、分割の検証は「重みを設定した」で止まる（設定と実測の区別）
2. **カナリアの失敗数はゼロにならない**（c の 6/60）。カナリアの価値は「失敗を
   10% に閉じ込めて全量事故を防ぐ」ことであって、失敗をなくすことではない。
   実機（7.2）ではこの 6 件相当を**アラーム発火までの時間**として測り直す
3. Caddy の weight は正整数のみ。「重み 0」は表現できないので、cutover は
   upstream から外す形で表現した（ECS の B/G も切替は重みでなくターゲットグループの
   付け替えなので、意味論はむしろ近い）
4. 旧イメージのビルドは `git worktree add <tmp> <ref>` → docker build が素直
   （checkout での作業ツリー汚染なし。ビルド後に worktree remove）

### ローカルで測れなかったもの（= 7.2 の本命）

- ヘルスチェック不合格の新版を**そもそも昇格させない**ゲート
- d の2レバー同時操作の通し
