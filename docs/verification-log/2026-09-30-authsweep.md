# 認可の総当たり: 全ルート × 他人のトークン / 無認証（#182）

水平権限昇格（他人の ID を入れると 200 が返る）は、どの既製の道具からも出てこない。
ZAP は「そのレスポンスが返っていいのか」を知らないので 200 を正常応答として通す。
#194 のセットで一番効くと位置づけた自前の検査を `dev/authsweep` として実装し、
CI（frontend ジョブ、allinone スタック起動後）に常設した。

## 形

- **ルート一覧はハンドラ登録の実体から取る**: `app.APIs()` → chi の `Routes()`。
  経路が増えれば検査対象も自動で増える。新しいパスパラメータに代入値が未定義なら
  検査はエラーで止まる——「新経路が検査から漏れて素通り」を構造的に作らない
- **的は実リソース**: alice の写真（ready まで実際にアップロード）・gear item を作り、
  bob のトークンと無認証で photo/gear × external/admin/internal の全経路に当てる
- **陽性対照つき**: alice 自身が自分の詳細と一覧を見られることを先に確認する。
  これが無いと「サーバーが全部 404 を返す壊れ方」でも検査が緑になる
- **免除は理由つきで明示**: gear の `/items` は共有カタログ（所有の概念が無い）なので
  bob の 200 が正しい。黙って除外せず、免除表に理由を書かせる

## 実測（ローカル tier2 スタック）

14 経路 × 2 面（無認証 + bob）+ 陽性対照 + pending 漏れ検査 = 31 検査、すべて拒否の形。

| 面 | 期待 | 結果 |
|---|---|---|
| 無認証（全 14 経路） | 401 | すべて 401 |
| bob → alice の photo（detail / :commit / :publish） | 404（存在を伏せる決定） | すべて 404 |
| bob → photo 一覧 | alice の行が混ざらない | 混ざらない |
| bob → pending の詳細（監査 #85 の形） | 404 | 404 |
| 人間のトークン → internal 全経路（#27） | 403 | すべて 403 |
| bob → admin 経路 | 拒否 | 403 / 401(下記) |

## 書いてみて分かったこと

1. **Read Model は status='ready' しか返さない**ので、pending のままの写真を的にすると
   404 の理由が「認可」なのか「状態フィルタ」なのか区別できず、検査として空になる。
   的はアップロードを完了させた ready の写真を使う（種まきに PUT + :commit まで要る）
2. **アカウント削除の 401 は脆弱性ではない**: AAL2 要求の経路は認可（403）より先に
   RFC 9470 のステップアップチャレンジ（401 insufficient_user_authentication）が返る。
   拒否の語彙は 403/404 だけではない
3. 署名付きアップロード URL は Host が署名に含まれるため、コンテナ内ホスト名を
   単純に書き換えると 403 になる。接続先だけ差し替えて Host ヘッダは元の値を送る
   （`UPLOAD_URL_REWRITE`）

## 運用

- ローカル: スタック起動後に `mise run authz:sweep`
- CI: frontend ジョブ（photo/gear/core の変更で発火）で毎 PR 実行
- 経路数のフェイルオープン防止: 検査済み経路が現状の半分（8）を割ったら列挙を疑って落とす
