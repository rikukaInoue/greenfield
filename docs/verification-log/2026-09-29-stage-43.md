### 気づき

1. **SNS FIFO の5分窓は「意図した再生」まで黙って落とす。** Republish が
   `MessageDeduplicationId`=イベントID のままだと、5分以内に流れたイベントが
   SNS で捨てられ、**キュー深度 0・エラー無し**で再構築が空振りする。
   イベントの `DedupID` を分離し、Republish だけ run ごとの値を使うようにした
   （受信側の重複排除の鍵は常にイベントID = inbox。バスの窓は事故の二重送信用）
2. **孤児プロセスは検査の結果を静かに壊す。** 検査スクリプトの `kill $!` は
   ラッパー関数のサブシェルにしか届かず、実バイナリ（consumer）が孤児として残り、
   後続の検査のメッセージを横取りしていた。旧バイナリの孤児は inbox に記録するが
   複製に書かないため、「イベントは消えたのに複製が増えない」という手強い見え方をする。
   対策: 常駐は `( exec … ) &` で起動して kill が本体へ届くようにし、go run を
   常駐に使わない（スクリプトが先にビルドする）
3. **kill したプロセスの受信中メッセージは可視性タイムアウト（30秒）後に戻ってくる。**
   欠けた1件が数十秒遅れて再配信され正しく適用された——at-least-once の回復が
   実地で観測できた（3.3 の「kill したつもり」に続き、プロセスの死は二度測る）
4. **再構築の検査は「消す前との一致」より「2回の再構築の一致」が正しい。**
   ローカルの複製は過去の検証でドリフトしており、replay はそれを outbox 由来の
   状態へ**正しく**戻すため、ドリフト分だけ不一致になる。不一致は欠陥ではなく
   outbox が正である証左。決定性（同じ入力→同じ指紋）を検査対象にした
5. **replay の `--since` 窓が狭いと境界のイベントが黙って落ちる。** 1時間窓で
   古いイベントが除外され、部分再構築を「完全」と誤認しかけた。検査は全期間
   （24時間）を replay する
