## 2026-09-27 — 検証ログを1エントリ1ファイルに分割

### なぜ

複数のセッションが並行して作業しており、**どちらも `verification-log.md` の EOF に追記するため
main が動くたびに必ず競合していた**。1日で複数回、同じ解決作業を繰り返した。
ファイルは 1147行・22エントリまで育っていた。

競合そのものは軽い（追記同士なので並べるだけ）が、そのたびに次の副作用が出る。

- **競合している PR には CI が一切走らない。** GitHub の `pull_request` はマージ参照を使うので、
  参照が作れない間はワークフローが起動しない。`gh pr checks` は「no checks reported」と言うだけで、
  **CI が走っていないことに気づかないまま放置される**。実際に一度これで止まった

### やったこと

- 既存22エントリを `docs/verification-log/<日付>-<識別子>.md` に分割した
- `docs/verification-log.md` は索引（日付とリンクの表）にした
- 階層が1つ深くなったので相対リンク（`adr/...` → `../adr/...`）を修正した
- `04-milestones.md` と `README.md` の案内を「1エントリ1ファイルで追加し、索引に1行足す」に更新した

**新しいエントリは新しいファイルを作る。既存のファイルには触らない。** 索引の1行追加だけは
同じ行に当たらない限り競合しない（追加位置が末尾なので、最悪でも1行の並べ替えで済む）。

### 気づき

1. **追記専用のファイルは並行作業と相性が悪い。** 「追記するだけだから安全」ではなく、
   EOF は全員が触る1点なので**必ず**衝突する。1エントリ1ファイルにすれば構造的に起きない
2. **競合が CI の不在を招く**という間接的な害の方が重い。競合に気づいていても
   「CI が走らない」まで結びつけるのに時間がかかった

### 還流

- [ ] 検証の証跡は1エントリ1ファイルにする。複数人・複数セッションで書く前提なら、
      追記専用の単一ファイルは競合点になる
- [ ] 競合している PR では CI が走らない（マージ参照が作れないため）。
      「チェックが無い」は「通った」ではないので、PR の mergeable 状態を先に見る
