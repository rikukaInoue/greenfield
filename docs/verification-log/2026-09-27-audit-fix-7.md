## 2026-09-27 — 監査の修正 7: 本番の既定値を fail-closed にする（#87）

`docs/audit-2026-09-27.md` の D-1 / D-2。どちらも「dev の既定が本番で静かに使われる」形だった。

### D-2 `staticauthn` のガードが拒否リスト

```go
if env := os.Getenv("ENV"); env == "production" || env == "prod" { ... }
```

`ENV` が未設定、あるいは `prd` / `staging` のような綴りだと**通り抜ける**。
`app.LocalDeps` が唯一の Deps 生成経路なので、出荷される `photo` バイナリに他の認証経路は無い。
つまり `ENV` を設定し忘れた本番デプロイは、**署名検証のない base64 トークンを受け付ける**。

### D-1 S3 の既定値が IAM 認証チェーンを殺す

`AccessKeyID` の既定が `"test"`（非空）で、`blobstore` は非空ならスタティック認証に切り替える。
**IAM のタスクロール運用（環境変数を設定しないのが普通）では AWS の既定の認証チェーンが使われず**、
`test` / `testtest` で接続しに行く。エンドポイントも `localhost:9000` を向く。

### 直したこと

`core/runtimeenv` を追加し、環境の判定を一元化して**許可リスト**にした（[ADR 0016](../adr/0016-development-guard-is-an-allow-list.md)）。

- `ENV` が `dev` / `development` / `local` / `test` / `ci` のいずれかでなければ **Prod**（未設定も Prod）
- 開発用の実装は `RequireDevelopment` を通らなければ組み立てられない
- **S3 の既定値を production のパスから外した。** ローカル用の値は「開発環境であることを確かめた後」に補う
- `blobstore` に最低限の検証（バケット名が空なら起動しない、`AccessKeyID` があるのに秘密が無ければ起動しない）
- `mise.toml` に `ENV = "dev"`、CI に `ENV: ci`

### 実測

| `ENV` | 結果 |
|---|---|
| 未設定 | **起動しない**（`staticauthn: ... ENV=(未設定) では使用できない`） |
| `prd`（綴り違い） | **起動しない** |
| `staging` | 起動しない |
| `dev` | 起動し、投稿が 200 |

`core/runtimeenv` の単体テストで10通りの `ENV` 値について種別と許否を固定した。

### 気づき

1. **拒否リストは「知っている本番の名前」しか止められない。** 未設定・綴り違い・新しい環境名
   （`staging`、`sandbox`）が通り抜ける。差し込み口 + ローカル実装という設計では、
   この判定が**最後の防波堤**なので許可リストにする必要がある
2. **「環境変数が無ければ dev の値」は、環境変数を設定しない運用を抑止する。**
   IAM ロールやシークレット注入は「設定しない」ことで成立するので、
   非空の既定値があると本番の解決機構が働かない。この形の失敗は落ちずに**別の場所へ接続しに行く**ので
   気づきにくい
3. ガードが2箇所に別々にあると、片方だけ直しても守られない。判定は1箇所に集める
4. 副作用として **`ENV` の設定が必須**になった。これは望ましい変更だと考える
   （「設定を忘れると開発用の実装が本番で動く」より「設定を忘れると起動しない」方が安全）

### 還流

- [ ] 本番ガードは許可リストにする。拒否リストでは未設定・綴り違いが通り抜ける
- [ ] 開発用の既定値を production コードのパスに置かない。置くなら「開発環境であることを
      確かめた後」に限る。既定値は環境変数を設定しない運用（IAM ロール等）を抑止する
- [ ] 環境の判定を1箇所に集める
