### G: 昇格ゲート — テストトラフィックで落ちる版は本番被弾ゼロ

壊れた版（`PHOTO_FAULT=before_commit`、healthz は正常・書き込みだけ落ちる）を
B/G + `POST_TEST_TRAFFIC_SHIFT` フック付きでデプロイ:

| 測定 | 結果 |
|---|---|
| フックの判定 | `verdict: create 500` — **healthz 検査だけなら素通りする版を、書き込み検証が捕捉** |
| デプロイの結末 | `ROLLBACK_SUCCESSFUL`、reason に "POST_TEST_TRAFFIC_SHIFT lifecycle hook(s) failed ... returned FAILED status" が明記 |
| 所要 | 開始 → ロールバック完了 **103 秒** |
| 本番への被弾 | デプロイ全体をまたぐ 4rps の実 API 負荷 **1,679 リクエスト（写真作成 335 件含む）エラー 0**。本番は v1 のまま |

### A: アラーム自動ロールバック — 被弾は 2.4% に閉じ、自動で戻る

同じ壊れた版を、ゲートを外して（= テストトラフィックでは検知できない壊れ方の代役）
CANARY 20% + `alarms{greenfield-71-target-5xx, rollback:true}` でデプロイ:

| 測定 | 結果 |
|---|---|
| タイムライン | 開始 05:13:29 → カナリア窓で 5xx 蓄積 → **アラーム OK→ALARM と同刻に ROLLBACK_IN_PROGRESS**（20:17:44Z）→ ROLLBACK_SUCCESSFUL 05:18:19（**計 4分50秒**） |
| reason | "Service deployment rolled back because of one or more active alarms." |
| 被弾 | **69 / 2,880 リクエスト（2.4%）**が 500（`photo.injected_fault`）。ロールバック後はゼロ、本番 v1 復帰 |

**G と A の対比が本命の数字**: 同じ壊れた版でも、ゲートで捕まえれば被弾 **0/1,679**、
カナリア + アラーム頼みなら **69/2,880**。ローカル予行 c（手動切り戻しで 6/60）の実機版の
答えがこれで、「カナリアは失敗を消さない。全量事故を防ぐだけ」に加えて
**「テストで落とせる壊れ方は、そもそも本番に触らせない」**という層の順序が確定した。

### 気づき

1. **フックの検証は「healthz より深く」が要点。** healthz は静的 ok を返すだけなので、
   DB 経路が壊れた版を素通しする。テストトラフィックで**書き込みまで**やる設計にして
   初めて、PHOTO_FAULT の版が本番前に落ちた。ゲートの価値は検証の深さで決まる
2. **アラーム発火とロールバック開始が同刻**だった（ECS がアラーム状態をポーリングではなく
   即応で拾っている）。遅延の内訳はほぼ「メトリクス集計 60 秒 + ALB 計測の遅延」で、
   これが被弾 69 件の正体。窓を縮めたければアラームの period を縮めるしかない
3. **stopDeployment の 32 秒は「ターゲットグループ掛け替え」の速さ**。旧タスクは bake 中
   なら生きているので、ロールバック = ルールの向き先変更だけで済む。bake を長めに取る
   運用は「戻り先を温存する保険料」として意味がある
4. update-service に hooks / alarms を**毎回明示**で渡す運用にした。terraform が service を
   管理している環境では、tf apply が CLI で付けた設定を黙って剥がすため（provider は
   これらを知らない）、どちらを正にするかを決めないと消える
