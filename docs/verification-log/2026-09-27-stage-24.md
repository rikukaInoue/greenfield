## 2026-09-27 — ステージ 2.4 並列と直列（#47 / check #26）

### 作ったもの

2.3(#46)で入れた `concurrency: deploy-<service>` がそのまま該当する。このステージで足したのは
**検証できる状態**: gear をデプロイ可能にし(#132)、self-hosted ランナーを 2 台にした
(1 台だとジョブがランナー待ちで直列化し、**並列性を観測できない**)。

### 実験

check #26 の設計どおり「photo と gear を同時投入 + photo を連投」。3 本を 3 秒間隔で dispatch した。

### 確認（実機・修正後）

| run | dispatch | migrate | release | healthcheck |
|---|---|---|---|---|
| photo #1 | 18:28:40 | 18:28:44 → 18:28:57 | 18:29:01 → 18:29:13 | 18:29:15 → 18:29:25 |
| **gear** | 18:28:43 | **18:28:46 → 18:28:58** | **18:29:02 → 18:29:18** | 18:29:21 → 18:29:32 |
| photo #2 | 18:28:46 | **18:29:28** → 18:29:40 | 18:29:43 → 18:29:54 | 18:29:57 → 18:30:06 |

- **別サービスは互いに待たない**: photo #1 と gear は migrate / release / healthcheck の全段が**重なっている**
  (migrate は 18:28:46–18:28:57 が共通区間)。3 本とも success
- **同一サービスは追い越さない**: photo #2 は 18:28:46 に dispatch されたのに migrate の開始が **18:29:28**。
  photo #1 の healthcheck 完了(18:29:25)の直後で、**42 秒待っている**。
  待たせたのはランナー不足ではない——gear が 18:29:32 に終わって以降もランナーは空いており、
  photo #1 の完了を待っている。`concurrency: deploy-photo` が効いている証跡

### 見つけたバグ（この実験が掘り当てた）

**修正前は gear の release が落ちた。**


`docker compose up` が `depends_on` を辿って**共有インフラ(mysql)の再作成に手を出す**ため、
photo と gear の release が同時に走るとコンテナ名を奪い合う。

`--no-deps` を付けて、release が触るのは自分のサービスだけにした(#133)。

### 気づき

1. **concurrency group は「スケジューリング」しか分けない。** 実行が共有物に触れば、並列に動いた
   瞬間にぶつかる。「別サービスは互いに待たない」を主張するなら、**待たない状態で同時に走っても
   壊れない**ことまでが範囲。ジョブグラフの宣言だけ見て緑にすると、この穴は残る
2. **1 台のランナーでは #26 を検証できない。** ジョブがランナー待ちで直列化するので、
   「待っているのは concurrency group なのかランナー不足なのか」が区別できない。2 台にして初めて
   「別サービスは重なる / 同一サービスは重ならない」が同じ条件で比較できた。
   計測のための 2 台目は常設にしていない(`run.sh` の一時起動)
3. **インフラの起動をデプロイに含めない**のは分離の条件でもある。`mise run db:up` の持ち物にして、
   落ちていれば healthcheck が失敗して deploy も失敗する。黙って起動するより、何が前提かが見える
