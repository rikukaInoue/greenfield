## 2026-09-29 — [4.1] サービス間: gear → photo の M2M 結合（#51）

### 作ったもの

- gear の実装一式（items）: migration（expand/contract）、sqlc 二系統
  （repository / readmodel）、domain（kind は VARCHAR。D-4: ENUM の変更は COPY）、
  usecase、external ハンドラ。photo と同じ構造を**2例目**として踏むことで、
  reference 実装の形が写せるかを確かめた
- `services/gear/photocatalog` — 生成クライアント（photo-client）を包むアダプタ。
  生成型（`Id int64` / `ImageUrl *string` / `*[]ServicePhoto`）はここで
  `usecase.PhotoRef` に変換し、**生成型を usecase から見せない**（境界での型変換）
- usecase は `PhotoCatalog` interface だけを見る。作例の取得に失敗したら詳細ごと
  失敗（502 gear.upstream）にする——「photos だけ欠けた半端な応答」は
  空と失敗を区別できなくするため作らない（監査 B-1）
- `core/httpclient` 拡張 — `TokenProvider` interface（TokenSource / StaticTokenSource）、
  変更系リクエストへの Idempotency-Key 自動付与（呼び出し側が明示したキーは
  上書きしない——リトライで同じキーを送り直せなければ重複排除として機能しない。監査 C-7）、
  `middleware.FromContext` からの traceparent 伝播
- gear の `OIDCDeps` + `OIDC_ISSUER` での配線切替（photo と同じ規約）。
  dev ループは devtoken の StaticTokenSource で同じ `core/httpclient` を通す
- `dev/scripts/s2s-check.sh` — 一気通貫の機械検査。CI の authz ジョブが
  authn-check.sh の後に gear を起動して実行する

### 生成→配布→interface受けの一連（実 Keycloak、実測）

| 確認 | 結果 |
|---|---|
| gear external: トークン無し 401 / 壊れたトークン 401 | ok |
| alice が POST /items で 201 | ok |
| GET /items/{id} が 200（= svc-gear の client_credentials で photo internal 往復） | ok |
| photo 側に公開作例を用意すると詳細に**非空で**併合（caption 一致） | ok |
| private / pending_upload の作例は出ない | ok |
| photo 停止時は 502 gear.upstream（photos:[] にしない） | ok |

「photos が空」は photo まで行って公開作例が無かったことを、「502」は行けなかったことを
意味する。この区別が設計で保証されているため、CI の 200 は M2M 経路の成立の証明になる。

### 気づき

1. **`httpapi.AddMajor(1, …)` は panic する（v1 は New が作る）。** 実行して初めて分かった。
   スペック生成（`mise run api`）が組み立てコードを実際に実行する構造のおかげで、
   規約違反が CI 到達前に落ちる
2. **502 の応答に上流のエラーをそのまま載せると内部 URL が漏れる。** `problem.New` の
   errs 可変長引数は本文に直列化される。外向けは概要だけにし、原因は
   `slog.ErrorContext` でログへ——AccessLog（canonical log line）はステータスしか
   持たないので、ここで落とすと原因が消える
3. **「プロセスを kill したつもり」の検証は嘘をつく。** 修正後の再検証で古いバイナリが
   ポートを握ったままになっており、修正前と同じ応答を見て混乱した。3.3 の
   「listen している ≠ 目的のプロセス」と同型。再起動を伴う検証は PID まで確かめる
4. **CI に rustfs が無くても非空の併合を検査できる。** photo の DB に公開済みの行を直接
   用意すれば、アップロードフローを踏まずに表示経路だけを検証できる。presign 失敗は
   soft（ImageURL が付かないだけ）という photo 側の設計に依存している
5. **photo-client の replace は消費側 go.mod ごとに要る。** dev モジュールは replace が
   無いまま GitHub の published バージョンを黙って拾った（public リポジトリの副作用）。
   気づけたのは `go mod tidy` のダウンロードログだけ
