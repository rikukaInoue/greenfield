## 構成の要点

- ネイティブ B/G はターゲットグループ2枚 + **リスナールール**（default_action は不可）+
  ECS インフラロール（`AmazonECSInfrastructureRolePolicyForLoadBalancers`）が要る
- ECS がルールの forward 重みを書き換えるため、tf 側は `ignore_changes = [action]`
- taskdef の改版トリガーは env の `deploy_marker`（イメージ再ビルド不要）

## 実測2: BLUE_GREEN と CANARY は別 strategy（発見）

「B/G のオプションとしてのカナリア」は存在しない。API が排他を強制する:

```
InvalidParameterException: Canary configuration can only be present with CANARY deployment strategy
```

さらに **Terraform provider (aws ~>6.x) は `strategy=BLUE_GREEN` + `canary_configuration`
という無効な組を黙って受理し、canary を落とす**（AWS 側 null、tf state にも残らない。
plan も apply もエラーなし）。3秒間隔のサンプリングで 80/20 が一度も出ないことから発覚し、
CLI で直接設定を試みて API エラーで確定した。**fail open の6例目**（無効な設定が
「設定されなかった」ではなく「成功」として出てくる）。

## 実測3: CANARY strategy で 20% の重みを捕捉

`strategy=CANARY, canary_percent=20, canary_bake=1m` で v4 デプロイ、2〜3秒間隔で追跡:

```
12 サンプル  st=IN_PROGRESS  w=0/100      (旧が全量)
16 サンプル  st=IN_PROGRESS  w=200/800    (= 新20% : 旧80%。カナリア窓 ≈1分)
33 サンプル  st=IN_PROGRESS  w=100/0      (全量切替 → bake)
 1 サンプル  st=SUCCESSFUL   w=100/0
```

ALB の重みは 200/800 という整数比で表現される。可用性ループは引き続き非 200 ゼロ。
なお terraform provider は CANARY デプロイの完了を待たずに apply を返す
（BLUE_GREEN は完了まで待った）。デプロイの完了判定は
`aws ecs list-service-deployments` の status で行うこと。

## 実測4: check #24 / #26 の再演

- **#24（migrate 失敗 → デプロイを始めない）**: わざと壊れた DSN で migrate の
  one-off タスク → exit 1 → ゲートが release 工程をスキップ → サービスの taskdef は
  revision 5 のまま不変。**成立**
- **#26（同一サービス直列）**: デプロイ進行中に `--force-new-deployment` を投げると
  受理され、PRIMARY 1 + ACTIVE 2 が並んで**新しいデプロイが supersede** する
  （待ち合わせではなく置き換えの直列化）。別サービス並列は、ECS ではサービスが
  独立リソースなので構造的に干渉しない（gear を立てるまでもなく設計上成立）
