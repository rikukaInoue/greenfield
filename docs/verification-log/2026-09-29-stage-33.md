## 2026-09-29 — [3.3] 差し替え: localauthz/Static → oidcauthn + authzhttp（#50 / check #18・#27）

### 作ったもの

- `core/authz/oidcauthn` — OIDC の JWT 検証（ディスカバリ → JWKS、RS256）。外部ライブラリを
  使わない。検証対象を「既知の issuer が RS256 で署名したトークン」に固定すると、JWT
  ライブラリの危険な自由度（alg 取り違え）ごと消えるため、stdlib の rsa 検証で足りる
- `core/httpclient` — M2M トークンの取得・キャッシュ・自動付与（client_credentials）。
  冪等キーとトレースID伝播は 4.1 以降（#138、docs/03-platform.md §9）
- `core/authz/authzhttp` — platform/authz を裏にした Authorizer / Lister / RelationWriter
  （本番アダプタ）。subject は localauthz と同じ流儀で ctx の Principal から引く
- photo の配線: `OIDCDeps`。`OIDC_ISSUER` の有無で LocalDeps と切り替える。誤って本番で
  LocalDeps を選べば staticauthn / localauthz 自身の許可リストが起動で落とす（ADR 0016）
- authz サービス自身の認証: `internal:platform` スコープ必須。無認証待ち受けは
  runtimeenv の許可リスト環境のみ（「プライベートネットワークを理由とした無認証は採らない」）
- realm に `internal:platform` client scope を追加（svc-photo / svc-gear の optional）
- `mise run authn:check` — 一気通貫の検証（下表）

### 気づき

1. **JWT の検証はライブラリ無しで書けたが、書けたのは前提を3つに固定したから。**
   issuer 固定・RS256 固定・JWKS は OP から取得。この固定を緩める（複数 issuer、
   ES256 対応）ならライブラリ導入を再検討する。alg 検査を先頭に置き、`none` / `HS256` は
   宣言の時点で拒否する（署名検証に到達させない）
2. **Keycloak の M2M トークンは `client_id` クレームで見分ける。** 人間のトークンには無い。
   preferred_username の "service-account-" 接頭辞より頑丈（表示名は設定で変わる）
3. **ローカル検証で photo が誤って別の MySQL に繋がっていた。** ホスト 3306 をネイティブの
   mysqld（別業務のもの）が握っており、コンテナのポート公開が潰されていた。compose の
   `3306:3306` は bind 失敗を黙って飲む形になっていて、healthcheck はコンテナ内で通るため
   気づけない。読み取り失敗（500）だけで実害無し。検証は socat で 13306 → コンテナに
   橋を架けて完了した。**「ポートが listen している」と「そのポートが目的のプロセスである」は
   別の主張**——同型の罠は本番の ALB ターゲット取り違えでも起きる
4. **oidcauthn の起動は issuer 不一致で落とす。** ディスカバリの issuer と設定値の食い違いは
   Tier 1/2 の罠（conventions/internal-07）の典型なので、リクエスト時ではなく起動で検出する
