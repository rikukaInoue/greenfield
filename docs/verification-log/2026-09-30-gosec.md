# gosec を段階導入する（#188）

静的解析は依存の層と性質が違い、誤検知が出る。issue の鉄則——最初から FAIL にせず、
①件数を見る ②明らかに正しい指摘だけ扱う ③残りをルール単位で理由つき除外
④それからゲート——をそのまま踏んだ記録。CI ジョブは増やしていない
（既存の `.golangci.yml` に同居、`lint:imports` 経由）。

## ① 初回計測: 80 件

| ルール | 件数 | 所在と正体 |
|---|---|---|
| G104 未処理エラー | 29 | `defer db.Close()` 等の慣用句。予告どおりの筆頭ノイズ |
| G115 整数変換 | 23 | ID の uint64↔int64、ポートの int→uint16 等 |
| G304 変数によるファイルパス | 11 | ほぼ dev/ の CLI（引数で受けたパスを開くのが仕様） |
| G301/G302/G306 パーミッション | 10 | dev/ の生成物書き出し |
| G201/G204/G702/G703/G704 | 8 | 全て dev/。SQL 整形=columncheck、サブプロセス=scaffold/affected、SSRF=authsweep（環境変数の URL へ意図的に当てる検査ツール） |
| G118 goroutine の context | 1 | telemetry のバックグラウンド送信（リクエストより長生きする設計） |

**本体コード（core / services / platform）から出た「直すべき実弾」は 0 件**だった。
taint 系（G70x）が全て dev/ の検査ツール自身を指したのは筋が通っている——
authsweep は SSRF「する」ためのツールで、gosec はそれを正しく SSRF と呼んだ。

## ② ③ 仕分け → 理由つき除外

`.golangci.yml` の `exclusions.rules` に4本（各行に理由）:
G104 全体 / G115 全体 / dev/ の taint・パーミッション系 / telemetry の G118。
除外に無いルールの新規検出は落ちる = ここからゲート。

## ④ ゲート化と対象の拡大

`lint:imports` の対象を services だけから**全9モジュール**へ広げた。SAST の価値が
一番高いのは認証・認可・HTTP を持つ core のため。`mise run check` green を確認。

**負のテスト**: photo に `crypto/md5` を使う一時ファイルを置くと G501（weak crypto の
import）と G401（weak primitive 使用）で即落ちる。除外だらけで骨抜きになっていないことの裏取り。

## frontend 側の相当物（eslint-plugin-security 等）の判断

**今回は見送り。** 理由: (1) React は既定でエスケープし、`dangerouslySetInnerHTML` は
現状 0 箇所（grep で確認）、(2) SSR の実害側（ハイドレーション漏れ・ヘッダ・SSRF）は
#186 が e2e で実挙動を固定済み、(3) eslint 基盤自体が未導入で、導入は lint 体系の設計
（規約との整合）を伴う別サイズの話。`dangerouslySetInnerHTML` が最初に入る PR で
再判断する——それまでは「使っていない」ことが最強のルール。
