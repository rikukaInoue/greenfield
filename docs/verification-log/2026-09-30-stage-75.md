# 2026-09-30 — [7.5] AppConfig の OpenFeature プロバイダを自作し #18/#21 を再演（#79）

環境: AppConfig のアプリケーション/環境/プロファイル/デプロイ戦略だけを Terraform で
使い捨て(`infra/appconfig/`)。**VPC もコンピュートも不要**(appconfigdata はパブリック API)で、
アプリは手元の allinone を実資格情報で動かした。費用は構成リクエスト課金のみ。当日削除済み。

## 作ったもの

- `flagprovider/appconfig`: `openfeature.FeatureProvider` の実装(約300行 + テスト)。
  `StartConfigurationSession` / `GetLatestConfiguration` をポーリングし、定義を
  プロセス内に保持して評価する(ADR 0013 の「同期してローカル評価」と同じ形)。
  go-sdk-contrib に AppConfig のプロバイダは無い(ADR 0011)ので還流物
- `dev/scripts/flags-deploy.sh`: フラグ専用パイプライン。git 管理の flagd 形式定義を
  AppConfig feature flags 形式へ変換し、構成バージョン登録 → デプロイ → 完了待ち
- `infra/appconfig/main.tf`: application / environment / profile(FeatureFlags 型) /
  デプロイ戦略2種(即時、50%×2分+ベイク1分)

ADR 0011 は定義の置き場所を `deploy/flags/*.json` と書いたが、実装では既存の
`deploy/compose/flagd/flags.json` を単一ソースのままにした(ローカル flagd と AWS の
定義を二重管理しない。パイプラインが形式変換を担う)。

## 発見1: AppConfig のフラグキーは "." を受け付けない → 命名規約を変更

`ops.photo_disable_uploads` の反映が `BadRequestException` で弾かれた。フラグキーの
制約は `^[a-z][a-zA-Z0-9_-]{0,63}$` で、**旧命名規約 `<種類>.<機能名>` の "." が使えない**。

ユーザー判断で**命名規約側を `<種類>_<機能名>` に変更**した(internal-08 更新、
`ops_photo_disable_uploads` へ改名)。マネージド基盤で使えない文字を規約に入れない。
変換層(パイプラインで "."→"_"、プロバイダで逆引き)も実装したうえで比較したが、
両端で対の規則を保守する複雑さより規約変更のほうが安い。パイプラインにはキー制約の
機械検査を残した(規約はパイプラインでも止まる)。

## 発見2: deletion protection が destroy を止める

検証後の `terraform destroy` が environment / profile の削除で
`BadRequestException: actively being used` になった。AppConfig の deletion protection は
**直近(既定1時間)にポーリングしたクライアントがいる資源の削除を拒む**。
provider(aws ~>6.x)にバイパスの口は無く、CLI の
`--deletion-protection-check BYPASS`(+ hosted バージョンの個別削除)で解消した。
使い捨て運用では「検証直後に消す」が典型なので、毎回ここに当たる。

## 実測(完了条件の4項目)

| 確認 | 結果 |
|---|---|
| flagd → AppConfig 差し替えで usecase / handler 無変更 | **変更 0 行**(変更は flagsource の分岐追加と新モジュールのみ。usecase の diff はフラグ改名で、差し替え起因でない) |
| 切替にアプリのデプロイ不要(#21 再演) | パイプライン実行から **14 秒**で `can_create` が反転(再起動なし。即時戦略3秒 + ポーリング≤15秒) |
| 取得失敗時に宣言した既定値へ倒れる | 存在しないプロファイルで起動 → WARN「フラグ基盤に接続できないので既定値で動く」+ 既定値(投稿可=既存動作)で稼働。stale(取得失敗後に前回定義で継続)は単体テストで固定し、変異(失敗時に定義を消す)で検査が落ちることも確認 |
| 段階デプロイ中の評価が安定 | 50%×2分+ベイク1分の戦略で 193 サンプル(1秒間隔)中**遷移1回のみ**(OFF→ON の行き来なし)。全体 3分04秒 |

補足: AppConfig の段階デプロイの % は**クライアント(セッション)単位**の配布割合であり、
flagd の fractional(主体キーのハッシュで振り分け)とは意味が違う。同一クライアントは
旧定義か新定義のどちらかを一貫して見るため、主体単位の安定はこの構造から従う。
