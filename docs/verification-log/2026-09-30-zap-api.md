# ZAP API scan（active）を週次で回す（#190）

baseline（#189、passive）に対し、こちらは**実際に攻撃を撃つ**。時間がかかるので週次
（日曜 04:47 JST + 手動）。#194 のセットの最後の1本。

## 形

- **スパイダーを使わない**: リンクを辿る探索器は REST API をほぼ発見できない。
  生成済みの `api/photo/external.v2.openapi.json` を食わせ、全エンドポイント・
  全パラメータ・全スキーマを知った状態から始める（external は v2 のみ。v1 は廃止済み）
- **認証は replacer で devtoken を差し込む**。何を検査していることになるかを明示:
  検査している認証実装は staticauthn であって本番の oidcauthn では**ない**
  （「ZAP が通ったから本番の認証は安全」とは読めない。oidcauthn は authn:check の担当）。
  一方、**認可・入力検証・エラーハンドリングの検査としては有効**（handler/usecase は
  認証アダプタの内側で共通）。この線引きはワークフローの冒頭コメントにも書いた
- active はデータを壊す前提 → CI の service コンテナ（毎回まっさら）に対してだけ回す。
  reclaim / db:reset は不要（環境ごと捨てる）
- 既知の検出は #189 と同じ `.zap/rules.tsv`（理由つき IGNORE）。`-I` 無しなので
  **新規 alert だけ**が落ちる。HTML レポートは artifact（14日）

## 学び

- zap-api-scan の `-c` は `/zap/wrk` からの相対で解決される（`.zap/rules.tsv` を
  サブディレクトリごとマウントすれば #189 と1ファイルを共有できる）
- `-O` でスペックの server URL を上書きできるので、スペックは本番向けのまま
  検証環境へ向けられる
