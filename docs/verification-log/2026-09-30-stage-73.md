## 発見: キューポリシーが無いと配送が黙って落ちる（fail open 7例目）

初回実行は check #8 前半（Publish 成功）まで通り、**consumer に届かなかった**。
原因は SQS キューポリシーの欠如。SNS がキューへ SendMessage する許可
（`Principal: sns.amazonaws.com` + `aws:SourceArn` 条件）が無いと、

- **Publish は成功する**（published_at も付く）
- 配送だけがエラーなしで捨てられる（DLQ が無ければ痕跡ゼロ）
- **LocalStack はキューポリシーを強制しない**ため、ローカルでは無くても全チェックが通る

「送れた」は「届く」を含意しない。届いたことは受信側でしか確認できず、
それを LocalStack で確認しても実 AWS の認可は検査されていない。
対策として eventadmin がポリシーを必ず設定するようにした（LocalStack でも無害）。

## 実測2: 5分デデュープ窓の挙動差

同一 `MessageDeduplicationId` で本文を変えて2回 Publish:

| | 実 AWS | LocalStack |
|---|---|---|
| 2回目の Publish | 成功（エラーなし） | 成功（エラーなし） |
| 配送 | 1通のみ（2回目は飲まれる） | 1通のみ（同じ） |
| **MessageId** | **2回とも同一**（重複と分かる唯一の信号） | **2回とも別** |

配送のデデュープ自体は LocalStack も再現するが、publisher が重複を検知できる
唯一の手掛かり（同一 MessageId が返る）は再現しない。relay は
`MessageDeduplicationId = event_id` を明示しているので、再送が5分窓に入っても
バスが吸収し、窓の外でも inbox が吸収する（#9）— 二段の防御が実測で揃った。

## 実測3: 順序保証

同一 `MessageGroupId` に 5 イベント連投 → 受信は 1..5 の完全順序（実 AWS）。
MessageGroupId = aggregate_id の設計（集約内は順序、集約間は並行）が実バスで確認できた。
