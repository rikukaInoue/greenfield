# 2026-09-30 — タイムアウト予算とプール設定を規約化して実測（#215 / 10.5）

環境: ローカル。`dev/scripts/timeout-drill.sh` で再現可能。

## 直す前の状態（コードで確認）

- サーバ側タイムアウトが**全て無制限**（ReadHeader / Read / Write / Idle いずれも未設定）。
  遅いクライアントが接続とゴルーチンを無期限に握れる
- 接続プールが**無制限**（SetMaxOpenConns 等の呼び出しがゼロ）。プール使用率の
  メトリクスはあるのに設定が無い——観測が実装より先行していた
- クライアント側だけは実装済み（httpclient: 一般 10s / トークン 5s）

## 実装

- 3リスナー全部に ReadHeader 5s / Read 15s / Write 30s / **Idle 65s（ALB の 60s より長く**。
  短いと LB の使い回し接続をサーバが先に閉じて断続 502）
- `configureDB`: MaxOpen/MaxIdle 25・ConnMaxLifetime 300s を全ての長寿命接続
  （serve×2 DB・relay・consumer）に適用。本番値は
  MaxOpenConns × タスク数 × プロセス内接続数 < max_connections で逆算
- 規約 10.5 を執筆（内側ほど短く / リトライの線引き / レート制限はエッジ）

## 実測: 依存先が遅いときの劣化が有界であること

gear の代わりに「20 秒黙ってから応える」スタブを立て、photo へ紐付けつき投稿:

| 確認 | 結果 |
|---|---|
| 投稿の成否 | **201**（依存先の遅さで投稿を落とさない） |
| 応答時間 | **10.1 秒で頭打ち**（クライアントタイムアウト 10s。依存先の 20s を引き継がない） |
| 紐付けの状態 | **pending に残留**（回収ジョブが引き継げる。劣化であって欠損ではない） |

「1回で返して pending に劣化させ、再試行は relay と回収ジョブに寄せる」という
既存の設計が、タイムアウト予算と噛み合って実際に機能していることの通し確認になった。
