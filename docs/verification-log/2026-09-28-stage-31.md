### 確認（Keycloak 26.0.8、実測）

realm.json は Admin API で組んだ realm を partial-export して作り、**手で組んだコンテナを破棄 →
compose で import からの再現**を確認した。realm-as-code の主張（毎回同一状態）はこの往復で成立している。

| 確認 | 結果 |
|---|---|
| ユーザトークン（alice）に `org=rikuka` | **載る**（oidc-usermodel-attribute-mapper、client scope 経由で全クライアント共通） |
| M2M トークン（svc-photo / svc-gear）に `org=greenfield` | **載る**（oidc-hardcoded-claim-mapper、クライアント個別） |
| `amr` キーの存在 | **存在する**（oidc-amr-mapper。値は下記の気づき2） |
| `scope=internal:gear` を svc-photo が要求 | **付く**（optional client scope。svc-gear → internal:photo も同様） |
| `iss` | `http://localhost:8180/realms/greenfield`（02 の Tier 1 前提と一致） |
| export の冪等性 | `keycloak:export` を通しても `git diff` 無し |

### 気づき

1. **Keycloak 26 の宣言的 User Profile は未宣言の属性を黙って捨てる。** `attributes: {org: [...]}` を付けて
   ユーザを作っても、User Profile に `org` が宣言されていなければ保存されず、エラーも出ない。
   mapper は正しいのにクレームが載らない、という遠い場所で初めて気づく。realm.json には
   `userProfile` の宣言を含めてあるので import では再現しないが、**新しい属性を足すときは
   User Profile への宣言とセット**という手順は覚えておく必要がある（還流候補: プロダクションの
   Kratos でも identity schema の宣言漏れは同型の罠になる）
2. **`amr` は direct grant（password grant）では空配列になる。** oidc-amr-mapper は認証フローが
   記録した AuthnContext を写すだけで、direct grant はフローを通らないため記録が無い。
   `keycloak:check` は「キーが存在する」ことまでを検証し、値の中身はブラウザフロー（Phase 5 の
   SSR / 任意課題のステップアップ）で扱う。ACR↔LoA マッピングも同じ場所で効く
3. **ユーザの部分更新は存在しない。** Admin API の user PUT は全体置換で、`attributes` だけ送ると
   email や firstName が消え、"Account is not fully set up" で direct grant が落ちる。
   export スクリプトが alice を毎回固定で書き戻すのはこのため
4. **partial-export はシークレットを `**********` に伏せ、通常ユーザを含めない。**
   `keycloak:export` はこの2つを補って realm.json を完成させる。シークレットは開発用の
   固定値（`*-dev-secret`）で、本物を書かない前提をスクリプトのコメントに残した
5. **services: コンテナは command を渡せないので `--import-realm` で立てられない。**
   flagd と同じ制約（ci.yml 冒頭コメント）。CI では docker run で compose と同じ形に立てた
