# Trivy: 設定・シークレット・イメージの検査（#187）

依存 CVE（#180 govulncheck / #183 osv-scanner）が見ない層——Dockerfile・compose・
Terraform の危険設定、ハードコードされた鍵、コンテナイメージの OS パッケージ——を
Trivy で検査する。スキャナは設定とシークレットに**絞る**（依存 CVE を重複検査しない）。

## 形

- `mise run trivy:check`（PR ゲート、ci.yml の trivy ジョブ・毎回実行）
  1. `.trivyignore.yaml` の検品: **statement（理由）と expired_at（期限）の無い除外は
     受け付けない**。期限切れは trivy 自身が除外を無効化するので、ゲートが再び落ちる
     （ADR 0021 の「放置の検出」が道具ネイティブで手に入る）
  2. **canary**: ダミーの AWS キーを置いた一時ディレクトリを先にスキャンし、検出器が
     生きていることを毎回証明してから「検出0件」を報告する（空振り防止）
  3. `trivy config --severity HIGH,CRITICAL`（Dockerfile / compose / Terraform）
  4. `trivy fs --scanners secret`（リポジトリ全体）
- `mise run trivy:image`（日次、security.yml）: 上に加えてイメージ3本を実際にビルドして
  `trivy image --ignore-unfixed`。**ビルド時にクリーンだったイメージは翌日公表の CVE で
  脆弱になる**（1バイトも変わっていないのに状態が変わる）ので、日次が本体。
  `ignore-unfixed` は「落ちているが誰も直せないゲートは翌週 continue-on-error を
  付けられて死ぬ」ことへの予防

## 初回実測（2026-09-30）

`trivy config` の HIGH/CRITICAL は **23 件**。全てが既知の gap 群と一致した:

| 検出 | 件数 | 対応先 |
|---|---|---|
| DS-0002（Dockerfile に USER が無い）| 3 | #213（non-root 化）|
| AWS-0079/0080/0132（保存時暗号化なし）| 4 | #212 |
| AWS-0054（ALB リスナーが HTTP）| 3 | #211 |
| AWS-0030/0031（ECR スキャン無効・タグ可変）ほか SG/S3/サブネット | 13 | #210〜#213（使い捨て検証スタックの構成）|

新規のゼロデイ的発見は無し——だが「機械が gap 一覧を再導出した」こと自体が
検査の妥当性の証拠になる。全件を `.trivyignore.yaml` に**対応 issue と期限つき**で
固定し、以後は新規だけが落ちる。シークレットは 0 件（canary は検出できる状態で）。
イメージ3本（golang:1.26-alpine → alpine:3.22）は修正可能な HIGH/CRITICAL **0 件**。

## 学び

- `.trivyignore.yaml`（paths / statement / expired_at が書ける方）は **`--ignorefile` で
  明示しないと読まれない**。自動で読まれるのは無印 `.trivyignore` だけで、そちらには
  理由も期限も書式が無い——明示指定の一手間で ADR 0021 の規律が道具ネイティブになる
- issue 起票時は「Dockerfile が無い」だったが、その後 Phase 7 で3本できていた。
  検査を入れる時点の現物に合わせて `trivy image` まで前倒しで入れた
