## 2026-09-30 — Tier 1.5: アプリはホスト `go run`、認証だけ Caddy 経由は成立するか

Tier 1（ポート直・ループ最速）と Tier 2（全コンテナ・issuer 統一）の中間、
「**アプリは全部ホストの `go run` のまま、issuer だけ `auth.localhost`（Caddy）に統一する**」
が成立するかを実測した。動機は、認証まわりを触る期間に Tier 2 の rebuild コストを
払わずブラウザと同じ issuer 名で開発できるか。

## 前提の測定: ホストプロセスは auth.localhost を解決できるか

| リゾルバ | 結果 |
|---|---|
| Go 既定（macOS = cgo/getaddrinfo） | `[::1 127.0.0.1]` に解決。discovery 200 |
| Go 純リゾルバ（GODEBUG=netdns=go） | DNS(100.100.100.100)に問い合わせて **no such host** |
| python getaddrinfo / 素の curl | ループバック解決（curl は RFC 6761 の自前実装） |

→ **macOS の既定ビルドなら成立**。Linux ホストや `CGO_ENABLED=0` のホスト実行は
/etc/hosts に `127.0.0.1 auth.localhost` が要る。

## 一気通貫

authz と photo をホストで起動（env は issuer / AUTHZ_URL / M2M_TOKEN_URL を
auth.localhost 系に差すだけ。コード変更なし）:

| 測定 | 結果 |
|---|---|
| authz の判別 readiness（無トークン /check） | 401（OIDC 実体） |
| alice トークン（auth.localhost 発行）→ /v2/photos | **200**（JWKS 取得も Caddy 経由） |
| 旧 iss（127.0.0.1:8180 発行）トークン | **401** |

→ **Tier 1.5 成立**。ポート直のループ速度のまま、ブラウザと同じ issuer 名で動く。

## 副産物: ポート衝突はスタック割れで静かに起きる

初回測定で /v2/photos が 404 になった。photo は起動成功・healthz も通っていたのに、
**アクセスログに /v2/photos が1件も無い**ことから異物を検出。`lsof` の結果、
別プロセス（sashikid）が **IPv4 の 127.0.0.1:8080** を先に保持しており、
Go の `:8080` は **IPv6 側で bind に成功**していた。healthz の `localhost` は
`::1` に解決されて自分に当たり「起動成功」、curl の `127.0.0.1` は別プロセスへ。

readiness が「誰が応答しているか」を言わない問題（#160）の変奏で、
**bind 成功もポートの占有を意味しない**（v4/v6 で割れる）。検出の決め手は
「自分のアクセスログに来ているはずのリクエストが無い」だった。
