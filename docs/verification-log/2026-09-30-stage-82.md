# 2026-09-30 — [8.2] 分散トレーシングを入れて「ログの ID でトレースを引く」を実測（#214 / 10.2）

環境: ローカル（allinone + compose obs プロファイルの Tempo）。

## 設計の要点

- **ログとトレースの ID を同一にする**: OTel の IDGenerator が `Correlate`（core/middleware、
  stdlib のまま）の採番した trace_id / span_id をそのまま使う。「ログの trace_id で
  トレースを検索する」が変換なしで成立する
- core に OTel を入れない当初判断は維持。core は `httpapi.Options.Tracing` という
  注入口（ただの func）だけ持ち、実装は telemetry モジュール
- 無効が既定（OTEL_EXPORTER_OTLP_ENDPOINT 未設定なら素通し）

## 実測

紐付けつき投稿 1 リクエスト（photo → M2M → gear）で:

| 確認 | 結果 |
|---|---|
| ログの trace_id で Tempo からトレース取得 | **取得できる**（`/api/traces/<log の trace_id>` が 200） |
| ログの span_id とサーバ span の ID | **一致**（base64→hex デコードで確認） |
| span の親子 | photo サーバ → クライアント → gear サーバが正しく連鎖 |
| span 数 | **25 / 1 トレース**（両サービスの SQL・フラグ評価込み） |
| service.name の帰属 | photo の DB span は photo、gear は gear（プロバイダ明示渡しで解消） |

## 踏んだ罠（他の人がここで死ぬ）

1. **resource.Merge の schema URL 衝突**: SDK の `resource.Default()`（semconv 1.43.0）と
   別バージョンの semconv を混ぜると NewTracer がエラー → 本アプリは「無効で続行」する
   設計のため、**トレースだけが静かに消える**。semconv は SDK 既定と同じ版に揃える
2. **グローバル TracerProvider は 1 プロセス複数サービスで後勝ち**: allinone で photo の
   DB span が service.name=gear になった。otelsql / otelhttp にはプロバイダを明示で渡す
   （allinone ではクライアント span の帰属のみ制約が残る。プロセス分離では正しい）
3. **グローバル propagator は既定 no-op**: `otel.SetTextMapPropagator(TraceContext{})` を
   忘れると otelhttp は traceparent を注入せず、クライアント span が親子連鎖から抜ける
   （httpclient の手書きヘッダが生きていたため trace 自体は繋がり、気づきにくい）
4. 検証中に fail open 事例3（残留プロセスが応答して新プロセスの bind 失敗を隠す）を
   自分でもう一度踏んだ。201 が返ることは、意図した版が返したことを意味しない
