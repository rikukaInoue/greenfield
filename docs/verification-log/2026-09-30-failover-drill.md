# [8.4] 追補: フェイルオーバーの接続層の機構と DDL 競合（#219 / gap-10）

[stage-84](2026-09-30-stage-84.md) が**アプリ経由**（photo の投稿/一覧、障害窓 8.5 秒・
500 ゼロ）で測ったのに対し、この追補は**素の接続層**にプローブを置いて機構を分解し、
DDL 実行中の競合とフェイルオーバーのタイミング特性まで踏み込む。両者は矛盾しない——
stage-84 で「8 秒タイムアウト」として観測された 2 件の正体が、ここで言う**凍結**である
（アプリ側のクライアントタイムアウトが回収したから 500 にならなかった。逆に言うと、
その締め切りが無ければ 2 件のタイムアウトは 2 本の永久ハングだった）。

B/G・カナリアの検証熱量に対して DB フェイルオーバーの機構は一度も分解していなかった。
使い捨てスタック（`infra/resilience/`。RDS MySQL 8.4.6 Multi-AZ db.t4g.micro、
1a↔1c）で `reboot --force-failover` を計4回撃ち、プローブ（250ms 間隔の INSERT、
one-off ECS タスク）と長時間 DDL で挙動を観測した。

## 結果1: 最重要の発見は「切断」ではなく「凍結」

**round 1（クライアント側の締め切りなし）: プローブ自体が10分以上ハングした。**
`--connect-timeout=2` は**確立済み**コネクションには効かない。フェイルオーバーの瞬間、
確立済み TCP はエラーを返さずブラックホール化し、MySQL クライアントの read timeout は
既定で無限。障害はエラーとして観測されず、**待ち続けるスレッドとして観測される**。

round 2 以降は呼び出し全体に 3 秒の締め切り（`timeout` ラップ）を掛けて再計測:

| 観測 | 値 |
|---|---|
| プローブ総数 / ok / err | 1,074 / 1,045 / **29** |
| エラー窓（最初の err → 最後の err） | **11.2 秒** |
| 最長の ok 間隔（実効ダウンタイム） | **14.9 秒** |
| err の内訳 | 28× `ERROR 2003`（即時失敗=リトライ可能）、**1× 凍結（3秒締め切りが回収）** |
| DNS フリップ | failover 指示の約 15 秒後（10.81.1.139 → 10.81.0.66） |
| AWS イベントの「completed」 | 指示から 44 秒後——**アプリは events より 20 秒早く復旧している** |

29 エラーのうち 28 は接続拒否で即時に返る「行儀のよい失敗」。危険なのは残り1つの
凍結で、これはクライアント側の締め切りでしか救えない。

## 結果2: migrate（COPY DDL）実行中のフェイルオーバー

16.7M 行への `ADD CHECK ALGORITHM=COPY`（ベースライン 105 秒）の最中に failover:

- **DDL はエラーにならずハングした**（round 1 と同じ凍結。900 秒の締め切りが切るまで戻らない）
- 中断後のテーブルは**無傷**: constraint 0 件・行数 16,777,216 のまま（MySQL 8 の
  atomic DDL。中途半端な状態は残らない）
- **再実行は素直に成功**（105 秒）

つまり migrate ジョブに必要なのは複雑な復旧ではなく、**ジョブ全体の締め切り + 再実行**。
中身の整合は atomic DDL と goose のバージョン管理が持っている。

なお stage-84 は「migrate 中のフェイルオーバーは lock_wait_timeout + リトライの
受け持ち」と推定していたが、実測では **lock_wait_timeout は発火しない**——中断の正体は
ロック待ちでなくネットワークの凍結で、MySQL のロック機構の外にある。受け皿になるのは
ジョブレベルの締め切りだけ（規約 10.5 に追記済み）。

## 結果3: force-failover の開始タイミングは保証されない

直前のフェイルオーバー完了から 4 分未満で撃った回は、API が `rebooting` を返してから
実際の「failover started」イベントまで **68 秒**の遅延があった（間隔を置いた回は 11〜15 秒）。
訓練やゲームデイで「今から N 秒後に落ちる」を前提に組むと外れる。

## 10.5（タイムアウト規約）との突き合わせ

- 「内側ほど短く」「ConnMaxLifetime 300s」は方向として正しいが、**穴が1つ**:
  規約は HTTP クライアントとサーバの締め切りを定めるが、**DB クエリ自体の読み取り
  締め切りが未規定**。凍結コネクションは ConnMaxLifetime では救えない（寿命は
  返却時に判定される。ハング中の接続は返却されない）。→ 10.5 に DSN の
  `readTimeout` / `writeTimeout` を追記（本ログとセットの規約改定）
- `ERROR 2003` 系の即時失敗は 10.5 の「リクエスト内で粘らず pending に劣化」の
  設計がそのまま受け止める（15 秒窓の書き込み失敗は relay / 回収ジョブの守備範囲）

## 注記: Keycloak / OpenFGA の単一コンテナ前提

検証ビルドの認証・認可基盤は単一コンテナで HA なし。フェイルオーバー訓練の対象外と
することを明示する——ここが落ちると新規ログイン・認可判定が止まるが、検証ビルドの
目的（デリバリーと守りの機構の実測）には影響しない。本番設計では Keycloak は
ステートレス化 + 外部 DB、OpenFGA は多重化が前提（internal-04 の範囲）。
