### 「メジャー連動で consumer へ PR」をどう実現したか

ロードマップは「api/ コミット → oasdiff → client 生成 → メジャー連動で consumer へ PR」とする。npm や Go モジュールを
別リポジトリへ配る構成なら、提供側の CI が利用側へ更新 PR を送る（Renovate 等）。このモノレポでは次の形で同じ性質を得た。

- client の再生成は**提供側の同じコミット**で強制される（`client:check` / frontend の `gen:check`）。古い client のまま main に入らない
- 破壊的変更は新しいメジャーのファイル（新しいアダプタ）として入る（ADR 0017）。旧版が並行提供されるので利用側は壊れない
- 利用側の移行は**別の PR**にする（#116 が実例）。差分検知 CI（ADR 0015）が、利用側だけの PR では利用側のジョブだけを走らせる

自動で PR を作る仕組みは置かない。モノレポでは「利用側がどこか」をリポジトリ内の grep で確定でき、移行 PR は人（エージェント）が作れば足りる。
