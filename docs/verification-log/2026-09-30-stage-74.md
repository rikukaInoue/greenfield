# 2026-09-30 — [7.4] Aurora MySQL の INSTANT DDL と fast clone を実測（#65）

環境: 使い捨ての Aurora クラスタ（`infra/aurora/`。VPC + Aurora MySQL + one-off ECS
タスク）。DB は非公開のまま、SQL は 7.1 と同じ VPC 内 one-off タスク（mysql:8.4）で流す。
当日 destroy 済み。費用は Aurora db.t4g.medium 2台（本体 + clone）×1時間弱で $0.3 前後。

## 交絡を消す選択: Aurora にも 8.4 互換版がある

ローカルの実測は MySQL 8.4.11。Aurora MySQL の主流は 3.x（8.0 互換）だが、それを選ぶと
「Aurora の差」と「8.0/8.4 の差」が混ざって切り分けられない。エンジン一覧に
**8.4 互換の `8.4.mysql_aurora.8.4.8`** があったのでこれを使い、Aurora だけを変数にした。

## 実測1: DDL の ALGORITHM 判定は完全一致

リポジトリ実物の expand / contract と同型の DDL を、2,097,152 行のテーブルに
ALGORITHM 明示で適用（`infra/aurora/ddl-measure.sh`。ローカルにも同一スクリプトを実行）:

| DDL（マイグレーションの同型） | Aurora 8.4.8 | ローカル 8.4.11 |
|---|---|---|
| ADD COLUMN（NULL 許容）ALGORITHM=INSTANT | ok 48ms | ok 58ms |
| ADD KEY ALGORITHM=INPLACE | ok 8.6s | ok 2.9s |
| ALTER COLUMN … SET DEFAULT ALGORITHM=INSTANT | ok 41ms | ok 35ms |
| ADD CHECK ALGORITHM=INSTANT | **ERROR 1845** | **ERROR 1845** |
| ADD CHECK ALGORITHM=INPLACE | **ERROR 1845** | **ERROR 1845** |
| ADD CHECK ALGORITHM=COPY, LOCK=SHARED | ok **56.4s** | ok 7.0s |
| DROP COLUMN ALGORITHM=INSTANT | ok 124ms | ok 44ms |

**判定（どの方式が通るか）は1行も違わない。** internal-05 のマイグレーション規約
（INSTANT で通る形に揃える、通らない変更は例外として個別計画）は Aurora にそのまま持ち込める。

絶対時間はハードが違うので比較にならない（手元は Apple Silicon の NVMe、向こうは
db.t4g.medium）。読むべきは比率でなく **COPY の絶対値**の方で、2M 行 56 秒なら
1億行では 45 分超の見積もりになる。「ADD CHECK は COPY のみ」の行は本番規模では
gh-ost / 保守時間の計画対象、という contract 000002 の注記が Aurora でも変わらず生きる。

## 実測2: fast clone（copy-on-write restore）

`restore-db-cluster-to-point-in-time --restore-type copy-on-write` で 2M 行入りの
クラスタを clone:

| 区間 | 所要 |
|---|---|
| clone クラスタが available | **60 秒** |
| clone 内の DB インスタンスが available | 274 秒 |
| **合計（接続可能になるまで）** | **5 分 34 秒** |

- ストレージの複製は copy-on-write なので**データ量に依存しない**（60 秒はメタデータの時間）。
  待ち時間の 8 割はインスタンスのプロビジョニングで、これはデータ量と無関係の固定費
- clone は 2,097,152 行をそのまま継承。clone への INSERT 後も**元クラスタは不変**
  （行数・当該行とも波及なし）を実測で確認

### 位置づけ（フィーチャーフラグ + オンラインマイグレーション運用への答え）

デプロイのたびに clone を作る運用は、この 5〜6 分 + インスタンス課金からして
**デプロイの部品には向かない**。B/G・カナリア（7.2）とマイグレーションゲート（#24）が
デプロイ側の答えで、clone の出番は**リハーサル**——本番同等データで COPY 系 DDL の
所要時間を事前に測る、壊す予行をする——に限られる。5 分半で本番同等の使い捨て DB が
出てくるのはリハーサル用途には十分速い。

## 片付け

clone（instance → cluster の順で削除、約 8 分）→ `terraform destroy`。
削除待ちが作業時間の大半で、操作自体はコマンド数個。
