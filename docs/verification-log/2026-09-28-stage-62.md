# 2026-09-28 ステージ 6.2: goose 比較1周（#60 / check #20）

環境: MySQL 8.4（使い捨てコンテナ、ポート13306）、goose v3.28.0、golang-migrate v4.20.1。
スパイクは photo の実マイグレーション5本（expand 3 / contract 2）を goose の1ファイル形式へ
機械変換して使用。ホストの 3306 は常駐 mysqld に取られるため 13306 を使う（既知の罠）。

## 実験1: 二系統×別履歴テーブル

`database.NewStore(DialectMySQL, "photo_goose_"+series)` + Provider で適用。
→ `photo_goose_expand`（v1-3）と `photo_goose_contract`（v1-2）に分かれた。**成立**。
INSTANT 3本・COPY 1本（CHECK 制約）を含む実物がそのまま通った。

## 実験2: 途中失敗（3文の2文目で失敗）

- 部分適用が残る（1文目の ADD COLUMN a は当たったまま）— golang-migrate と同じ
- 履歴には**何も記録されない**（dirty フラグという概念がない）
- そのままリトライ → `Duplicate column name 'a'` で落ちる（= 止まることは止まる）
- 部分適用を手で戻してリトライ → 成功

## 実験3: 先頭マイグレーションの失敗（#125 の場面）

`partial migration error (type:sql,version:1)` で失敗、履歴は空のまま。
ファイルを前方修正してリトライ → **そのまま成功**。
golang-migrate ではここで dirty=1/v=1 が残り、自作の resetDirty が Force(-1) で
履歴を全消しするバグ（#125）を踏んだ。goose にはその形のバグを書く場所がない。

## 実験4: 欠番（v1,v3 適用済みに v2 が後から届く）

- goose 既定: `detected 1 missing (out-of-order) migration lower than database version (3): version 2` で**明示エラー**
- `WithAllowOutofOrder(true)`: v2 が適用される（履歴順は 1,3,2）

## 実験5: 同条件の golang-migrate

`Up err=no change / version=3 dirty=false` — **v2 は黙って無視**。g2 テーブルは作られず、
エラーも警告も出ない。並行ブランチのマージで連番が交錯すると、適用漏れに気づくのは
schema:check-live の乖離検出まで遅れる。

## その他

- ロック: golang-migrate は GET_LOCK が既定で有効。goose は既定無効で、
  `lock.NewMySQLTableLocker`（lease 30s + heartbeat 5s）を `WithSessionLocker` で明示する必要
- 空の系統: goose は Provider 構築時に `no migrations found` で落ちる
  （golang-migrate は Up 時 fs.ErrNotExist。ラッパーの握る場所が変わる）

## 結論

check #20「ツール選定はオプション（設計はツール非依存）」— **成立**。
系統×モジュール別テーブル・embed・サブコマンドの形は両ツールで組める。
比較所感と乗り換え時の注意は ADR 0020（草案）へ。
