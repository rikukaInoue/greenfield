### 作ったもの

- `services/photo/Dockerfile` — デプロイ用イメージ。**ビルドは `GOWORK=off`** でこのモジュールだけを閉じて固める
  （ワークスペースを効かせると require の無い import が通り「モノレポだから動く」イメージができる）
- `deploy/compose/compose.yaml` に `photo` サービス（`profiles: ["deploy"]`）。デプロイ先は手元マシンの compose。
  既定では起動しないので、`mise run run`（allinone）の日常は変わらない
- `dev/scripts/deploy.sh <service> migrate|release|healthcheck` — **3段を1段ずつ**実行する
- `.github/workflows/deploy.yml` — `migrate → release → healthcheck` を `needs` で連結。
  `concurrency: deploy-<service>` で同一サービス直列・別サービス並列（2.4 の前哨）

3段を1つのスクリプトにまとめなかったのは check #24 そのもの: まとめると「migrate が落ちたら続きを走らせない」
保証が**スクリプトの制御フロー**になる。ジョブグラフに置けば保証は**実行機構**の側になり、スクリプトを
読まなくても成り立つ。

### 見つけたバグ（check #24 が掘り当てた）

`resetDirty` が **「dirty なバージョンが source に無い」を「失敗したのが最初のマイグレーション」と誤判定**し、
`Force(-1)` で**履歴を全消し**していた。

失敗した expand を**消す/番号を変える**のは前方修正の普通の形で、そのとき `src.Prev(v)` は「見つからない」を返す。
旧コードはそれを最初のマイグレーションと読み、履歴を空にする。次の実行は `CREATE TABLE photos` から始まり
`Error 1050 already exists` で落ちる。**以後どのデプロイも通らない**（実測: `version=1, dirty=1` で固着）。

修正は「source の先頭と一致するか」で判定し、一致しなければ dirty を残したまま理由と直し方を出して止める形。
推測で履歴を書き換えない。

| 復帰経路 | 旧 | 新 |
|---|---|---|
| 壊れたファイルを**消す**→再実行 | 履歴を全消し → `already exists` で固着 | dirty を保ったまま停止。`migrate force <version>` を案内 |
| 壊れたファイルの**中身を直す**→再実行 | 通る | 通る（dirty は自動解消され、直した版が適用される） |

### 気づき

1. **「環境は無傷」は2つに分かれる。** 動いているサービスとスキーマは無傷だが、**マイグレーション履歴は無傷ではない**
   （dirty が残る）。check #24 の期待を「デプロイ不開始・稼働中のサービスとスキーマは無傷・履歴は dirty が残り
   復帰手順が要る」と読み替えた。前者だけ確認して緑にすると、上のバグを見逃す
2. **前方修正（ファイルを消す）と dirty の復帰が噛み合っていなかった。** internal-05 は「down は使わず前方修正」と
   定めているのに、実装は「消される」ことを想定していなかった。規約と実装のこの手のズレは、規約側を読んだだけでは
   出てこない
3. **self-hosted ランナー（macOS / arm64、ラベル `self-hosted,macos,arm64,deploy`）を登録して実機で回した。**
   `runs-on` は `${{ vars.DEPLOY_RUNNER || 'self-hosted' }}` のままで、変数は未設定＝既定ラベルで解決する。
   compose のプロジェクト名は compose ファイルの親ディレクトリ名（`compose`）なので、**ランナーの
   チェックアウトから deploy しても開発用と同じコンテナ群**を差し替える（デプロイ先が1つであることが保たれる）。
   ランナーは `run.sh` を常駐させているだけで、ログイン時に自動起動する service（`svc.sh install`）にはしていない
4. **ホストの mysqld が 3306 を掴んでいると、ホストから TCP で繋ぐ検証が全部そちらへ当たる。**
   `schema-dump.sh` も migrations のテストも踏んだ。別ポートで publish した使い捨てコンテナに逃がした
