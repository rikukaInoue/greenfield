# 監査記録 2026-09-27

Phase 0 と Phase 1 の完了時点で、コードと `verification-log.md` / `adr/` の主張を突き合わせた。
観点を3つに分けて独立に当てた（ログの主張の反証 / 規約適合 / デッドコードと設定）。

**結論**: 構造の芯（モジュール境界、sqlc 封じ込め、CQS、Atomic の ctx 規約、migrations のロック待ち処理、
RFC 9457、フラグの4規約）は健全。一方で **検証ログに事実でない主張が複数あり、ゲートが嘘をつく箇所がある**。
このビルドの成果物は「動くコード」ではなく「検証の証跡」なので、後者は最優先で直す。

`verification-log.md` の該当箇所には本ファイルへの参照を追記し、誤った主張は取り消さず訂正を併記する
（何を間違えたかも還流物であるため）。

## A. 検証ログ・ADR の主張が事実でないもの

`dev/scripts/rename-drill.sh` が3箇所で死んでいる。

### A-2. `contract` を流す自動経路が存在しない — 生成と実行が別のスキーマを見ている 〔修正済み #84〕

- 新しいローカル環境と CI の `photo.photos` には `caption VARCHAR(1000) NOT NULL DEFAULT ''` が**残っている**
- `db/schema.sql`（sqlc の入力、`schema:check` の基準）は「消えた」と言っている
- **sqlc は contract 後のスキーマに対して生成され、テストは expand のみの DB に対して走る**
- `schema:check` は使い捨て DB と比較するので、この乖離を検出できない

`verification-log.md` の「`caption` 消滅」は手元の1回の手動実行の事実であって、環境の性質ではない。

## B. ゲートが嘘をつくもの

### B-1. `api:breaking` は base ref が解決できないと緑になる 〔修正済み #83〕

`dev/scripts/api-breaking.sh` は `set -uo pipefail`（`-e` なし）。`git cat-file -e "$base:$spec"` が失敗すると
全スペックについて「base にスペックがない（新規API）— 検査をスキップ」を出し、`found_any=0` のまま **exit 0**。

将来 ref や fetch の問題が起きたとき、破壊的変更ゲートが**安心できるメッセージ付きで無条件に通る**。
チェック #16 の根拠がこれに乗っている。`found_any=0` かつ base ref 自体は解決できる場合は非ゼロで落とすべき。

### B-2. CI の flagd は飾りで、OpenFeature 経路は1つもテストされていない

`ci.yml` の flagd サービスコンテナは `command` を渡せないため `--uri` が無く、何も配信しない。
GitHub は `--health-cmd` を宣言したサービスしか待たないので（mysql のみ）、**死んでいても見えない**。

一方 `usecase/photo_flag_test.go` は `flags.WithValues` で値を注入し、`core/flags` には `Evaluator` の
テストが無い。つまり**プロバイダ登録を通る経路をリポジトリ全体で誰も実行していない**（C-2 のバグが見逃された理由）。

## C. 規約違反（ADR に記録なし）

### C-1. `Atomic.Do` の中でネットワーク呼び出し

`usecase/photo.go:152-169`（`CommitUpload`）:

```go
err := c.atomic.Do(ctx, func(ctx context.Context) error {
    p, err := c.photos.Get(ctx, id)                   // SELECT ... FOR UPDATE
    info, err := c.images.Stat(ctx, p.ObjectKey())    // ← S3 HeadObject（ネットワーク）
```

`internal-03` が最も強く禁じている形。tx が `photos` の行ロックと接続を握ったまま S3 の応答を待つ。
しかも**リクエスト経路に `context.WithTimeout` が1つも無い**（非テストの `WithTimeout` は shutdown と loadgen のみ）。

**ADR 0009 自身が「オブジェクトストレージは Atomic の3条件を満たさない」と書いている**のに、
実装は HeadObject を Atomic の中に置いた。規約どおりなら検証は「Doの前」、`Do` は状態遷移と `Save` だけ。
`internal-02` の「`Atomic.Do` の fn 内に業務判断が現れたらレビューで移動先を問う」にも当たる（`p.CommitUpload` が fn 内）。

### C-2. OpenFeature のプロバイダ登録がグローバルで、ドメイン名が無効

SDK のソース（`go-sdk@v1.19.0`）で確認:

- `openfeature.SetProviderAndWait` は `WithDomain` を渡さないため `setProvider` を呼び、
  単一の `defaultProvider` を上書きして**古いプロバイダを `shutdown` する**
- `apiInstance` はパッケージレベルの `atomic.Pointer`、つまり**プロセスに1つ**
- `NewClient("photo")` のドメイン名は `ClientMetadata` に記録されるだけ。`SetNamedProvider` を呼んでいないので
  `domainProviders` は空で、全評価が default に落ちる

結果:
1. allinone に2つ目のサービスが `core/flags` を使った瞬間、後から登録した方が前のプロバイダを殺す
2. **サービスごとにスコープされているように読めるコードが、実際はされていない**

`SetNamedProviderAndWait("photo", provider)` にすれば両方解決する。
ADR 0010 も規約も「合成ルートが注入する」しか言っていないので、これは記録された判断ではなく実装の滑り。

### C-3. `DeleteByOwner` が認可もタプルもオブジェクトも扱わない

`usecase/photo.go:224-232`。サービス中で最も破壊的な操作（アカウントの全写真削除、AAL2 必須の
`handler/admin/router.go:112`）が:

- `authorizer.Can` を呼ばない（`internal-04` の「今固定するもの」その1に違反）
- `relations.DeleteRelations` を呼ばない → `owner` タプルが永久に残る
- `images.Delete` を呼ばない → **全画像がバケットに残り、DB 行が消えるので二度と辿れない**

`Reclaim`（`photo.go:175-198`）は両方やっているので、対比で抜けが明らか。
`reclaim` は `status='pending_upload'` しか見ないので回収できない。

さらに悪いことに、孤児 owner タプルは無害ではない: `localauthz` の operator 経路
（`localauthz.go:98-100`）は **owner タプルの存在をリソースの存在証明として使う**。

関連: `ActionDelete = "photo.delete"` は宣言され relation へマップされているが、**どこからも `Can` に渡されていない**
（固定した語彙のうち1つだけコードで使われていない）。

### C-4. `replicaview` の import lint も depguard も存在しない

`internal-01` は「Entity および usecase の業務判断から `replicaview` を import できないことを**lint で強制する**」、
「モジュール内の細則を `go-arch-lint` または `depguard` で CI において機械的に強制する」と定める。

実際: `.golangci.yml` も `.go-arch-lint.yml` も無く、`golangci-lint` も入っていない。
`dev/querylint` は SQL のテーブル許可リストだけを見る。**Go の import を検査するものは何も無い。**

`replicaview/doc.go:3` は「domain / usecase からこのパッケージを import することは lint で禁止する」と
書いている — 裏付けの無い主張。現在 `replicaview` が空なので無害だが、最初の ReplicaView が入るまで気づかない。

モジュール**間**の境界（ADR 0006 + `GOWORK=off`）は実装済み。欠けているのは意図的に残したモジュール**内**の半分。

### C-5. `core` の依存が規約の想定を超えている

`core/go.mod` の直接依存: `huma/v2`, `chi/v5`, `go-sql-driver/mysql`, `open-feature/go-sdk`。

- chi は ADR 0001、openfeature は ADR 0010 で記録済み
- しかし **`core/httpapi` というパッケージ自体が規約の core ツリーに無い**
  （`internal-01` は `authz/ consistency/ middleware/ httpclient/ logger/` を挙げる）。
  huma + chi を core の全利用者に持ち込む判断が無記録
- `go-sql-driver/mysql` が direct require にいる（`localauthz_test.go` 由来）。
  **ADR 0004 の「core は `database/sql` にしか依存しない」は現状と不一致**

依存4つという重さ自体は問題ではないが、`internal-01` は go.mod の diff をまさに強制ポイントに指定している。

### C-6. 規約の矛盾: `Eventual.Publish` の置き場所が Outbox の原子性と食い違う

`internal-03` の §2.2（配置ルールとコード例）は `Doの後: Eventual（Publish）` と書き、
§2.3 は「業務データの書き込みと**同一トランザクション**で outbox へ INSERT する。これにより
『業務データがある ∧ 送信予定がある』か『両方ない』の2状態のみがローカルトランザクションの保証として成立する」と書く。

`Publish` を `Do` の後に呼ぶと outbox の INSERT は別 tx になり、業務データをコミットした直後に
プロセスが落ちれば**イベントが永久に失われる**。Eventual の「窓は許すが欠落は許さない」定義にも反する。

現時点で `Eventual` の実装・呼び出しはゼロなので実害はない（選べる整合性クラスは実質 `Atomic` だけ）。
Phase 4.2 で顕在化する。

→ [ADR 0012](adr/0012-eventual-publish-inside-atomic.md) で「`Publish` は `Do` の中」と決定。Issue #93。

### C-7. `core/httpclient` が存在しない

`internal-03` は「いずれの枝でも冪等キーは必須。`core/httpclient` の冪等キー付与規約はこの要件を実装する」と定める。
そのパッケージは無い。フロント（`api-core/src/server.ts`）は `Idempotency-Key` を毎回**新しい UUID** で送るが、
**サーバ側で読んでいる Go コードは1行も無い**ので、リトライの重複排除として機能しない。
サービスが1つでサービス間コマンドが無い現状では優先度は低い。

### C-8. `RequireAAL` の決定が external 側で未記録

`internal-04` の「どのハンドラが `RequireAAL` を持つかは今決めてコードに残す」に対し、
admin は記録済み（`handler/admin/router.go:106`）。一方 `external.Deps.Assurance` は
宣言・注入されているが**誰も使っていない**。`AssuranceChecker.Require`（MaxAge 版）は非テストの呼び出し元がゼロ。
external の全面について決定が暗黙（= 未決）のまま。注入して未使用のフィールドがその印。

## D. 本番の足元

### D-1. S3 の既定値が IAM 認証チェーンを殺す

`app/app.go:88-89` の既定が `AWS_ACCESS_KEY_ID="test"` / `AWS_SECRET_ACCESS_KEY="testtest"`（非空）。
`blobstore/s3.go:42-45` は `AccessKeyID != ""` なら `StaticCredentialsProvider` を入れる。

ECS のタスクロール運用（環境変数を設定しないのが普通）では、**既定の認証チェーンが使われず
`test`/`testtest` で接続しに行く**。`AWS_ENDPOINT_URL` の既定も `http://localhost:9000` なので
実 S3 にも到達しない。危険というより混乱する形の失敗だが、「dev の既定が本番の解決機構を抑止する」という形そのもの。

既定を空にして明示必須にすべき。

### D-2. `staticauthn` のガードが拒否リスト

`staticauthn.go:20-25` は `ENV=production` / `prod` でだけ止まる。
`ENV` 未設定、`ENV=prd` などでは**署名検証のない `dev.` トークンを受け付ける**。
`app.LocalDeps` が唯一の Deps 生成経路なので、出荷される `photo` バイナリに他の認証経路は無い。
許可リスト（`ENV` が dev/ci/test のいずれかでなければ拒否）にすれば fail-closed になる。

### D-3. SSR の dev-login ガードは Go 側より弱い（別セッションのコード）

`frontend/apps/web/app/.server/env.ts:3` は `NODE_ENV === "production" && ENV ∈ {production, prod}` の
**両方**を要求する。`ENV=production` でも `NODE_ENV` 未設定（`pnpm dev` 等）なら `/login` は
`dev.` トークンを発行し続け、`SESSION_SECRET` も `"dev-session-secret"` に落ちる。
Go 側は `ENV` だけで止まるので、「同じガード」と記録したのは不正確。

### D-4. `status ENUM(...) NOT NULL DEFAULT 'ready'` に DB レベルの守りが無い

`migrations/expand/000002_photo_objects.up.sql:7`。既存行を見えるままにするための既定だが、
守りはコメント（「新規挿入は必ず明示的に指定する」）だけ。`object_key` / `content_type` / `size_bytes` は
全て NULL 許容で、`status='ready'` と `object_key IS NOT NULL` を結ぶ制約が無い。

忘れた挿入や手動挿入が起きると: 即座に一覧へ出る → `withImageURL` が存在しない鍵に署名 → クライアントは 404 →
`CommitUpload` は `ErrNotPending` で直せない → `reclaim` は `pending_upload` しか見ないので回収もできない。

`DEFAULT 'pending_upload'` + 同一マイグレーション内で既存行を `UPDATE` するほうが fail-closed。
`CHECK (status <> 'ready' OR object_key IS NOT NULL)` で構造にできる。

## E. 契約の空約束・デッドコード

- **`gear_name`**（`handler/external/router.go:91`、「ReplicaView 由来」）— 契約と TS 型に出ているが
  `fromView` は一度も設定せず、`replicaview/` は空の `doc.go`
- **`gear_item_id` の説明**（`router.go:102`、「指定すると gear への紐付けが pending で始まる」）—
  `Create` は gear に一切接触せず pending 状態も記録しない
- **403 が到達不能**: `GetPhotoDetail` / `CommitPhoto` / `PublishPhoto` は `Errors` に 403 を宣言し
  スペックにも出ているが、拒否は全て `ErrNotFound`（「存在を伏せる」決定）なので 403 は返らない。
  0.4 の気づき「実際に返しうるコードは明示的に列挙する」と矛盾
- **`PhotoView.Title`**（`usecase/query.go:18-20`）— 「contract 後に消す」とコメントしたまま残り、
  書かれも読まれもしない。コメントは削除済みのフラグ名を指している
- **`domain.Photo.Unpublish` / `domain.Photo.Edit`** — 呼び出し元ゼロ（テスト含む）
- **`usecase.Eventual` / `Event`** — 実装も呼び出し元も無い（Phase 4.2 の予定なので計画済みの穴）
- **`services/photo-client`** — `doc.go` が「CI が oapi-codegen で生成する」と書いているが、
  ツールも CI ステップも生成物も無い（2.2 の予定）
- **`ListPhotos` の `visibility` フィルタが SQL の `LIMIT` の後**（`router.go:205`）→
  `?visibility=public` は件数が減り、limit の先にある一致を取りこぼす。5.2 のログが通ったのはデータが少なかったため
- **`Reclaim` のタプル削除失敗は回復不能**（`photo.go:175-198`）— 行を消した後にタプル削除が失敗すると、
  候補は `photos` 由来なので再実行でも届かない。ADR 0009 の「再実行で回収できる」はこの段について偽

## F. 運用・設定

### F-1. `infra:up` が競合し、flagd を待たない

- `depends = ["db:up", "s3:up", "flags:up"]` の3タスクが**並行して `docker compose up`** を呼ぶ。
  同一プロジェクトのネットワーク／ボリューム作成で競合する（`network ... already exists` 系の間欠失敗）
- flagd は healthcheck が無い（distroless でシェルも curl も無いため）ので `flags:up` は `--wait` していない。
  `infra:up` は flagd の起動中に戻るので、直後の `mise run run` が競合すると
  `SetProviderAndWait` が失敗し、警告1行を出して**プロセスの生涯ずっと宣言済みの既定値で動く**（リトライなし）

現在のキルスイッチは既定 `false` なので安全側だが、無言で縮退する。
ホスト側からの TCP プローブ（`nc -z localhost 8013`）で `--wait` 相当を回復できる。

### F-2. `localstack` は死んだサービス定義

起動するタスクも、使うコードも無い（Phase 4.2 まで）。

### F-3. loadgen のゴミが溜まり続け、`reclaim` は手動のみ

`loadgen` の `createPhoto` は画像を上げず `:commit` も呼ばないので、1回の書き込みごとに
`pending_upload` の行 + owner タプルが残る（既定 `-rps 20 -write-every 5` で 4 行/秒。70秒のドリルで約280行）。

`reclaim` は正しく実装されている（オブジェクト → 行 → タプルの順）が、リポジトリ全体で
`mise.toml` の手動タスクにしか現れない。compose にも CI にもスケジューラにも無い。
既定（`--older-than 1h --limit 100`）では1回で最大100行、かつ1時間以上前の行のみなので、
1回のドリルの後片付けに1時間待って3回実行する必要がある。

ゴミを作る2つの経路（loadgen の放置アップロード、アカウント削除）の回収機構が、
それぞれ**手動のみ**と**存在しない**（C-3）。

### F-4. CI の `concurrency`

`cancel-in-progress: true` を `github.ref` で切っているので、`main` への連続 push も進行中のものを止める。

## G. 健全だったもの

反証を試みて崩れなかったもの。記録として残す。

- **モジュール境界**: `services/photo/go.mod` に兄弟サービスの require が無く、ガードコメント付き。
  ADR 0006 + `GOWORK=off` が CI で自己完結性を強制。`go build -overlay` プローブで両モードの非対称性を実証
- **sqlc 型の封じ込め**: `internal/sqlcgen` は `usecase` / `domain` / `handler` から到達不能（全 importer を確認）
- **CQS**: sqlc の設定ブロック2つとクエリディレクトリ2つまで分離。`Do` で囲まれたクエリは無い
- **Atomic**: 4箇所の `Do` すべてで ctx シャドーイング規約を守っている。ネスト安全、tx キーは非公開型
- **migrations**: `CREATE DATABASE` / ユーザー / GRANT を含まない（`deploy/compose/mysql/init/` が持つ）。
  expand / contract の系統別履歴テーブル、`ALGORITHM=INSTANT` 宣言、起動時自動適用なし、
  `lock_wait_timeout` 設定、ロック待ちリトライと dirty 回復
- **フラグ**: 規約の4項目（既定値は安全側 / 入口で1回 / フラグ同士を依存させない / 配信は Eventual）を満たす。
  命名も正しく、ON/OFF 両方をテスト
- **RFC 9457 + `code`**: 全エラーに `code`、全 4xx/5xx が `application/problem+json`、
  huma 生成のエラーにも載る
- **CORS**: どのリスナーにも入っていない
- **`Principal.Subject`** を不透明な識別子として一貫して扱い、タプル表記は `core/authz/ref.go` に集約
- **compose のローカル資格情報**: S3 の既定値（D-1）以外は compose 内に閉じている
- **httpapi のミドルウェア順序**: 認証 → スコープ → フラグ。`intlOpts := base` はスライスを共有しない
- ドキュメントの参照（タスク名・パス・ADR 間リンク）に切れなし。秘密情報・生成物のコミットなし

## I. プロダクション版へ還流すべきもの（本監査から）

本ビルドの目的は規約の検証なので、**規約側に足りていないこと**も成果物になる。

1. **`internal-05`: スキーマの二重化は起きる。** 「sqlc の入力はマイグレーション全適用後の dump」と
   「expand だけを本番へ流す」を同時に採ると、sqlc が見るスキーマと実行時のスキーマがずれる。
   contract キューの消化を CI/CD の経路として明示しないと、この乖離は検査をすり抜ける（A-2）
2. **`internal-03`: 「Doの中」の判定に外部ストレージの例を加える。** ADR 0009 のように
   「Atomic に載せられない」と正しく判断した上で、実装で中に入れてしまう事故が起きた（C-1）。
   判定を記録する場所（per-usecase の登録簿）が規約に無い
3. **`internal-01`: モジュール内の細則を強制する lint を「入れる」ではなく「入っていることを CI で示す」形にする。**
   `replicaview` の制限をコメントで書けてしまう状態は、書いた側が守られていると誤認する（C-4）
4. **`internal-08`: OpenFeature のプロバイダ登録はドメイン付き（`SetNamedProvider`）を既定にする。**
   グローバル登録は1プロセス複数サービス（allinone / サイドカー相当）で壊れ、
   ドメイン名を渡すコードが動いているように見えてしまう（C-2）
5. **`api-design`: 「実際に返しうるコードを列挙する」は、返さないコードを列挙しないことも含む。**
   認可拒否を 404 に倒す設計と 403 の宣言は両立しない（E）
6. **ゲートは fail-closed で書く。** 比較対象が見つからないときに「スキップ」で成功にする検査は、
   壊れたときに緑になる（B-1）。CI の検査は「実際に何かを検査した」ことを主張できる形にする
7. **シミュレータと実装の差**（ADR 0008）と同じ話が CI にもある。
   設定を渡せないサービスコンテナは、立っているだけで何も検査しない（B-2）
